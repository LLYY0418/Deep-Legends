## 播报行为

新增项复用原 `position-broadcast` 的开关、可见范围、自定义暂停、会话去重及安全 conversation ID 校验。多项合为一条 POST，不拆成多次发送。原有读取数据未齐的有界重试保留；写请求失败或结果不确定均不重发。

己方英雄只在队伍频道启用，来自选人会话 `myTeam` 和现有内存英雄名称表，不额外请求外部来源，不发送玩家身份或对方英雄；名称不完整则整项省略。本人分路必须通过明确、有效的本地 cell ID 匹配，并由客户端提供已识别的 `assignedPosition`，没有就省略。前端说明和实际消息前缀使用后端同一份元数据；日志记录选项及省略原因，不记录消息正文或身份。

实现入口：`watch_broadcast.go:positionBroadcastMessage`、`watch_rules.go`、`main.go` 的 `broadcastChampionNames` 注入及 `web/suite.js` 设置项。隐私与行为边界同步在 PRODUCT.md、DESIGN.md，更新日志保留原有未发布内容。

## 性能证据

离线 Headless Chrome、相同本地演示数据、阻断外部网络：总览首次加载 JS/CSS 从 **1,460,017 B 降至 1,134,340 B，减少 325,677 B（22.3%）**。此口径是资源正文大小之和，不含两边相同且仅演示模式加载的 `demo-data.js`，不是压缩后传输量、启动时间或 Windows 内存收益。

浏览器通过八个直达刷新入口、重复进入不重复脚本、收藏进入工具子页、资源失败后的重试，未出现未处理页面错误。原始结果见 [browser.json](r115-validation/browser.json)。真实 Electron/Windows/LCU 尚未实测。

最终五次离线基准中，三个路由样本旧/新中位数分别为 122.4/38.39、173.5/95.57、53.12/29.86 ns/op。混合大小写样本从 48 B、1 次分配降到 0；旧实现对已经小写的字符串本来就没有分配。此结果只反映路由微基准，不代表应用整体提速。其余五类记录当前基线，未声称被优化。见 [基准报告](r115-validation/bench/20260919-232358.md)。

复跑：`scripts/run-benchmarks.sh` 生成五次结果和中位数，可传此前原始报告作比较。FIFO 取消样本确实阻塞第二个入队者再取消；总览淘汰样本循环 257 个键穿过 256 个缓存位，避免只测初始一次淘汰。

## 秒退自动匹配核查

`watch_rules.go:handlePhase` 没有直接用 Lobby 阶段触发匹配；`scheduleAutoMatchmaking` 会拦截 `autoMatchStarted`、进行中和耗尽状态。但 `handleLobby` 在用户开启自动匹配、本人队长、人数达标时可以调用该调度器。手动开始匹配不保证已设置 `autoMatchStarted`，因此不能仅凭 phase 分支就宣布秒退后绝无重启风险。

结论：**代码路径已核查，真实秒退事件序列未验证，未作无风险保证。** 需要 Windows 下手动/自动开局、秒退返回 Lobby 的脱敏事件顺序才能确定是否存在应修复的行为；本轮没有凭推断改动自动匹配策略。
