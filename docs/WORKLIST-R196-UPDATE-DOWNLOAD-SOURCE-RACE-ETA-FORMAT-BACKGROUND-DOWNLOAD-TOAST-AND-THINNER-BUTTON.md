# WORKLIST-R196：更新下载太慢（卡在直连 GitHub 不切镜像）；剩余时间格式；后台下载与完成提示；顶部升级按钮变细

诊断人：Claude（看截图 + 读日志 + 只读核对源码）。执行人：GPT。日期：2026-10-03。基线：0.12.59（R195 已发布）。

## 现象

用户截图：0.12.58 → 0.12.59 一键升级已经能开始，但下载窗口显示 `92.1 KB / 106.2 MB · 5.8 KB/s · 约剩 18792 秒`，按这个速度要 5 个多小时。

## 证据

日志 `lol-loot-diagnostics-1003-1410.jsonl`，0.12.58 运行 `fa9e139a…`：

| 时间 (UTC) | 事件 |
|---|---|
| 06:02:29 | `update_install_detection result=registry_location_mismatch`（0.12.58 的旧判断，R195 已修，预期内） |
| 06:02:37 | `update_check_failed mirror_prefix=direct error_kind=timeout`：**直连 GitHub 取清单 8 秒超时** |
| 06:02:39 | `update_check_succeeded latest_version=0.12.59`：换镜像后 1.5 秒成功（成功事件**没有记是哪条线路**） |
| 06:02 ~ 06:10 | **下载过程没有任何日志**：没有开始、线路、速度、切换、结束事件 |

也就是说，用户这台机器直连 GitHub 很差（清单都超时），而镜像是通的；但下载时又回头去走直连。

## 根因（源码已核对）

1. `update.go:26`：`updateMirrors = ["", "https://ghfast.top/", "https://gh-proxy.com/", "https://ghproxy.net/"]`，第一项 `""` 是直连。
2. `update_download.go:151 downloadAsset` 按这个顺序**一条一条**试，只有某条线路**报错**才换下一条。
3. `downloadSource` 的保护只有"8 秒内一个字节都没收到就断开"（`updateSourceTimeout`）。直连 GitHub 能连上、每秒还能收到几 KB，**永远不会触发 8 秒无数据**，所以不会报错，也就永远不会切到镜像。结果就是 5.8 KB/s 一直下 5 小时。
4. 取清单阶段已经知道直连不行、镜像可以，但这个结果没有被下载阶段使用；下次启动检查更新还会再白等 8 秒直连超时。
5. 下载全程没有诊断事件，日志里看不出用了哪条线路、多快、有没有切换。

另外：`newUpdateManager` 的 `http.Client` 用的是 `http.DefaultTransport` 克隆，Windows 上**不会读取系统代理设置**（只认环境变量）。用户如果平时开着系统代理，浏览器下载 GitHub 很快，而软件走不到代理。本工单不改代理行为，只把这件事记进诊断（见 P1-6），先靠测速选线解决。

## P1　下载测速选线，慢了自动换线

1. **开始下载前并行测速。** 对全部线路（直连 + 3 个镜像 + 用户自定义的）**同时**发 `GET`，带 `Range: bytes=0-1048575`（前 1 MB），每条最多 6 秒。按"6 秒内收到的字节数 ÷ 实际用时"算速度。测速收到的数据丢弃，不写入 `.part`。
2. **测速结果校验，防止镜像返回错误页。** 只认：状态 206 且 `Content-Range` 总长度等于 `asset.Size`；或状态 200 且 `Content-Length` 等于 `asset.Size`。其他（HTML 页、长度不对、4xx/5xx、超时）一律记为不可用。
3. **从最快的线路开始下载。** 已有的断点续传逻辑不变。
4. **下载中持续看速度，慢了就换。** 当前线路下载满 15 秒后，如果最近 10 秒平均速度低于 **150 KB/s**，且还有测速可用、没换过的线路：保留 `.part`，换到下一条最快的线路续传（沿用现有 `Range` 续传和 HEAD 探测）。每条线路一轮里最多用一次。所有线路都慢时，**留在最快的那条继续下**，不报错、不中断。
5. **记住好用的线路。** 下载成功后，把这次的线路前缀存进更新设置（新字段 `preferredSource`，只存前缀，不存完整 URL）。下次**检查更新**和**测速排序**都先试它。取清单成功的线路也同样记住。这样这台机器下次检查更新就不会再先白等 8 秒直连超时。
6. **诊断**（都不记完整 URL；自定义镜像只记 scheme+host，沿用 `updateDiagnosticMirrorPrefix`）：
   - `update_check_succeeded` 增加 `mirror_prefix`（成功的是哪条线路）。
   - `update_download_probe`：每条线路一条，`mirror_prefix`、`http_status`、`bytes`、`duration_ms`、`speed_kbps`、`ok`、`error_kind`。
   - `update_download_source_selected`：`mirror_prefix`、`speed_kbps`、`resume_offset`。
   - `update_download_source_switched`：`from`、`to`、`reason`（`slow` / `error`）、`speed_kbps`、`received_bytes`。
   - `update_download_finished`：`mirror_prefix`、`duration_ms`、`avg_kbps`、`switches`、`resumed_bytes`。
   - `update_download_failed`：`mirror_prefix`、`error_kind`、`received_bytes`。
   - `update_download_cancelled`：`received_bytes`。
   - 下载开始时记一次 `update_proxy_env`：`http_proxy_set`、`https_proxy_set`（布尔，只记有没有设置，不记值）。

## P2　剩余时间显示成"分 秒"

`app.js` 约 3865 行现在是 `约剩 ${etaSeconds} 秒`。改为：

- 小于 60 秒：`约剩 45 秒`
- 小于 1 小时：`约剩 3 分 12 秒`
- 1 小时及以上：`约剩 5 小时 13 分`

速度为 0 或还没测出来时保持现有"正在连接下载线路…"。测速阶段显示 **`正在选择最快的下载线路…`**。

## P3　下载中可以放到后台；下载完右下角提示

### 下载窗口

1. 下载中（`downloading` / `verifying`）的按钮改为两个：**`取消下载`**、**`后台下载`**。去掉现在下载中显示的灰色"立即升级"按钮（下载中点不了，留着让人困惑）。
2. 点 `后台下载`：关闭弹窗，下载继续。顶部升级按钮显示进度圈（现有 `busy` 样式），悬停提示改为 `正在下载新版本 37%`（百分比实时更新）。点顶部按钮重新打开下载窗口，看到当前进度。
3. 窗口里那句说明改为：`可以点「后台下载」继续使用软件，下载完成后右下角会提示你。`（替换现在"下载可以放着不管…关掉这个窗口不会中断下载"）。关闭按钮 `×` 的行为和"后台下载"相同。

### 下载完成提示（应用窗口右下角）

4. 下载并校验完成（状态变为 `ready`），且更新窗口**没有打开**时，在应用窗口右下角弹出提示卡片：
   - 标题：**`新版本下载完成`**
   - 正文：**`Deep Legends 0.12.60 已准备好，升级时软件会自动重启。`**（版本号取 `latest`）
   - 按钮：**`立即升级`**（主按钮）、**`稍后再说`**
   - 卡片宽约 320px，距窗口右边和下边各 20px，用现有弹层的背景、边框、阴影和圆角；不自动消失，直到用户点按钮；有轻微进入动画，`prefers-reduced-motion` 下不动画。
   - 同一个版本、同一次运行只弹一次。更新窗口正开着时不弹（窗口自己会切到"准备就绪"）。
5. 点 **`立即升级`**：走现有升级流程（`/api/update/apply`）：关闭软件 → 安装界面显示进度 → 装完自动重新打开。沿用现有的对局检查：如果此刻在选人或对局中，**不直接升级**，而是打开更新窗口（准备就绪状态），显示现有提示"你正在对局中，建议打完再升级"，由用户再确认。
6. 点 **`稍后再说`**：只关闭这个提示卡片。顶部按钮保持"已就绪"状态，悬停提示 `新版本已下载，点击升级`。之后点顶部按钮，打开的更新窗口直接是"准备就绪"状态，按钮为 `稍后再说` 和 **`立即升级`**（把现在的"立即重启升级"统一改为"立即升级"），**不会再下载**。
7. 准备就绪窗口的说明文字保持现有那句（"安装包已下载并通过校验……装完自动重新打开"），只把其中的「立即重启升级」改成「立即升级」。
8. 窗口最小化或不在前台时完成下载：提示卡片照常放在应用里，同时让任务栏图标闪烁提醒（desktop 端 `BrowserWindow.flashFrame(true)`，窗口获得焦点后停止）。不使用系统通知。
9. 软件重启后如果后端仍处于 `ready`（安装包已校验、还没装），启动后同样弹一次这个提示卡片。后端目前不恢复 `ready` 的话，这条不做，账本写明。

现状：`app.css:1014` 把这个图标单独放大到 30px，同时用通用的 `stroke-width: 2.15`，比旁边的按钮图标粗、大；准备就绪时六边形整个填实色（`app.css:1084`），更显得粗重。

2. 六边形和进度圈 `stroke-width: 1.6`，箭头 `1.8`。
3. 准备就绪状态不再整块填色：六边形描边用 `--primary`，箭头用 `--primary`，保留右上角红点提示。
4. 红点位置随新尺寸调整，仍贴在图标右上角。
5. 进度圈（下载中）的线宽同第 2 条。

## 测试

Go（`update_download` 相关）：

1. 三个假线路：直连 5 KB/s、镜像 A 2 MB/s、镜像 B 返回 200 + HTML（长度不对）→ 测速后选 A；B 记 `ok=false`；`update_download_probe` 三条。
2. 只有一条快线路，下载 20 秒后变到 50 KB/s，另一条测速 1 MB/s → 触发 `source_switched reason=slow`，`.part` 续传，最终 SHA-256 正确。
3. 所有线路都慢（<150 KB/s）→ 不报错，留在最快线路下载完成，`switches` 不超过线路数。
4. 下载成功后 `preferredSource` 为成功线路；下次检查更新**先**请求该线路（直连排第二）。
5. 测速全部失败 → 回退到现有顺序逐条尝试，行为与改前一致。
6. 取消下载 → `update_download_cancelled`，`.part` 删除（现有行为）。
7. 诊断事件里不出现完整 URL、路径或代理值。

Node：

8. ETA：45 → `约剩 45 秒`；192 → `约剩 3 分 12 秒`；18792 → `约剩 5 小时 13 分`。
9. 下载中：按钮只有 `取消下载` / `后台下载`，没有"立即升级"。点 `后台下载` 后弹窗关闭，顶部按钮为 busy、提示含百分比。
10. 弹窗关闭时状态变 `ready` → 右下角卡片出现，标题、正文、两个按钮文字正确；弹窗打开时变 `ready` → 不出现卡片。
