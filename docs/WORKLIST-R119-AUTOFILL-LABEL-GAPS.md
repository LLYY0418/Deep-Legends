# WORKLIST-R119：R119「补位」标签的真实缺口

**撰写日期：** 2026-09-21　**基线版本：** 0.12.13
**触发：** 对 R119（对局详情队友/对手「补位」标签）的独立校验与测试。构建、`go vet`、R119 的 6 个 Go 测试与 3 个 JS 测试均通过；真 Chromium 渲染（浅/深色主题、长名字、960/1200 宽度）正常。**下面全部是「判定依据」和「测试护栏」问题，不是代码写错。**
**本轮性质：** 纯审查，未改动任何代码文件。

## 0. 三句话结论

1. **判定口径没有依据**：R119 把「`teamPosition` 有值、`individualPosition` 缺失或 `Invalid`」判成补位。Riot 官方 `ParticipantDto` 文档里，这两个字段**都是游戏服务器按对局中实际表现推算的「最可能打的位置」**（`individualPosition` 孤立地看该玩家；`teamPosition` 再加「每队各一个上单、打野……」的约束），并不记录大厅选位，也不记录是否补位。所以这条规则检测不了补位。
2. **界面提示把没有证据的话说成了事实**：标签提示写「客户端没有给这名玩家分配个人位置，最终分路 X 由系统补位」，违反项目红线「数据不准就降级、不用推断值冒充」。
3. **护栏有漏洞**：一条对应 Riot 已知数据异常的保护没有测试；「整场有证据」的门槛太松，实测一场里只有 1 人带个人位置，另外 9 人全被打上补位标签。

> 我没有拿到真实的国服/韩服对局响应，也没有真机。所以本工单说的是「没有依据」，不是「实测标错」。P1-1 的默认动作就是让真机数据来裁决。

# P1

## P1-1　补位判定口径无依据：默认关闭，等真机数据裁决

**证据**
- Riot match-v5 `ParticipantDto` 文档：两个位置字段「都由游戏服务器计算，是同一玩家『最可能打的位置』的两个版本；`individualPosition` 是不考虑其它任何因素时的最佳猜测，`teamPosition` 是加上『每队各有一个上单、一个打野、一个中单……』约束后的最佳猜测；一般建议使用 `teamPosition`」。文档没有任何一处说它们反映大厅选位或补位。
- Riot 官方 developer-relations 仓库 issue #554：JP1 排位约 0.9% 的对局 `individualPosition=INVALID` 且 `teamPosition` 为空，属数据缺失。
- 仓库内 `docs/r119-execution-ledger.md` §2 自己承认「`individualPosition` 与 `teamPosition` 谁代表选位前、谁代表最终，仓库内没有真实抓包样本可佐证」（全仓库 grep `individualPosition` 只命中代码与手写测试桩），但 `backend/riot_api.go:960` 的注释和前端提示已经按「他自己选到的那一路」表述。
- 用户原话规则是「最终位置不在他选择的两个位置中，并且没有选择任意位置」，需要大厅里的**两个位置偏好**。match-v5 里没有这两个值，R119 降级成「一个个人位置」后语义已经变了，不再是同一条规则。

**影响：** 标签要么几乎不出现，要么出现在「行为上认不出位置」（提前退出、挂机、极端打法）或数据异常的玩家身上，属于误标；用户会把「补位」当事实。

**修复方向（默认动作，不需要再询问）：**
1. 给补位判定加**总开关，默认关闭**。可在 `feature_gates.go` 新增一个默认 `false` 的 gate，或用一个具名常量；关闭时 `riotAutofillFlags` 一律返回全 false、`evidence=false`，JSON 里不出现 `autofill` 键（既有响应逐字节不变，`omitempty` 保持）；**诊断计数 `autofill_tagged / autofill_swapped / autofill_no_evidence` 仍然照常统计**，用来收集真机数据。
2. 前端 `autofillChip` 保持「只认后端下发的布尔 true」，不动。
3. 是否打开该开关，由 P3-2 的真机对照结果决定；没有结果之前保持关闭。

**验收判据：**
- 开关关闭：R119 相关的端到端测试改为断言「整场没有任何 `autofill` 键」；变异（把开关判断去掉 / 反向）→ 测试必须 FAIL；
- 开关打开：R119 原有 6 个 Go 测试与 3 个 JS 测试全部仍然通过；
- 关闭状态下诊断事件里 3 个计数键仍存在。

## P1-2　提示文案与命名把未证实的含义当事实

**证据：**
- `backend/web/gameplay.js:3045`：`data-tooltip="客户端没有给这名玩家分配个人位置，最终分路 ${...} 由系统补位"`；
- `backend/riot_api.go:951–974` 与 `backend/gameplay.go:495–500` 的注释同样把 `individualPosition` 表述为「他自己选到的」；
- 「两值不一致 = 英雄选择阶段换过位置」（计入 `autofill_swapped`）同样没有依据，不一致更可能是「孤立推算」与「加队伍约束后的重新分配」之间的差别；
- 标签文字「补位」本身是对这名玩家的事实陈述。

**修复方向：**
1. 提示文案改为只陈述数据事实，例如「对局数据里没有该玩家的个人位置（推算位置：XX）」，不出现「由系统补位」；标签文字的最终措辞留给用户看到真机结果后再定，本工单期间开关关闭，用户看不到，因此文字可以先保守；
2. 注释里把「他自己选到的那一路」改成「Riot 推算的孤立位置（不等于大厅选位）」；
3. `autofill_swapped` 改成中性名字（例如 `position_mismatch`），台账与测试同步；`autofill_tagged` 可以保留但注释里写明「候选，未经真机验证」。

**验收判据：** grep 全仓库业务代码与前端，「由系统补位」「他自己选到的」不再出现；诊断键名变更后相关测试通过；变异（把旧文案改回去）→ 若有文案断言测试必须 FAIL，没有就补一条对提示文案的真实执行断言（像 `r119.test.cjs` 那样跑真实的 `autofillChip`，不做源码正则）。

# P2

## P2-1　「`teamPosition` 为空则跳过」的护栏没有测试（变异存活）

**证据：** `backend/riot_api.go` `riotAutofillFlags` 里：
```go
if riotLaneKeyValue(raw.TeamPosition) == "" {
    continue
}
```
去掉这段，`go test -run R119` 与更宽的相关子集（Riot|Gameplay|Match|Season|SGP|Participant）**全部仍通过**。这条护栏恰好对应 issue #554 的形状：某个玩家 `individualPosition=INVALID` 且 `teamPosition` 为空。没有它，这类玩家会被误标补位。

**修复方向：** 补一个测试：10 人对局里，9 人正常，1 人 `teamPosition=""` 且 `individualPosition="Invalid"`（以及 `individualPosition=""` 的变体），断言这 1 人 `Autofill=false`，其余 9 人不受影响。
**验收判据：** 去掉上述 `continue` 的变异使新测试 FAIL；R119 既有测试保持通过。

## P2-2　「整场有证据」的门槛太松

**证据（用特征化探针实测，420，10 人）：**

| 输入 | 结果 |
|---|---|
| 只有 1 人有 `individualPosition`，其余 9 人缺失 | `evidence=true`，**9 人被打补位标签** |
| 5 人缺失、5 人正常 | 5 人被打标签 |
| 1 人 `Invalid`、其余正常 | 1 人被打标签 |

原因：`individualKnown` 只要**任意 1 人**有个人位置就为 true。响应残缺或半场数据时会大面积误标。

**修复方向（仅在 P1-1 的开关将来被打开时生效，但可以现在做，开关关闭期间无副作用）：**
1. 把整场护栏改成「几乎全员都有 `individualPosition`」（例如至少 9/10 有值，具体阈值由执行方定并写进测试）；
2. 增加「一局里被判补位的人数占比过高就整场降级」的保护（同一局同时有多人补位是可能的，但「10 人里 9 个」几乎一定是数据问题），降级时计入 `autofill_no_evidence`。

**验收判据：** 「1 人有值、9 人缺失」「5 人缺失」两种输入分别被新测试锁住（前者必须整场降级、0 个标签）；把新阈值改回「任意 1 人」的变异使测试 FAIL。

# P3

## P3-1　探测：LCU 里到底有没有真正的补位数据（探测工单，只读不改）

**背景：** 用户原始设想是「客户端应该有这个数据」。据我所知，大厅/选人阶段的位置偏好与最终分配位置只出现在 LCU 的实时接口里，且主要覆盖己方队伍，对手与事后回看历史局拿不到；但**我没有实测**，需要探测确认。
**做法：** 沿用 `backend/augment_contract_probe.go` 的模式（扫 LCU openapi 契约，环境变量门控，不进生产路径），只读地列出下列接口里所有与「位置偏好 / 分配位置 / 补位」有关的字段与类型：`/lol-lobby/v2/lobby` 成员、`/lol-champ-select/v1/session` 成员、`/lol-gameflow/v1/session`、`/lol-end-of-game/v1/*`、匹配历史相关接口。产出「有 / 没有 / 只有己方 / 只有实时」的结论表。
**验收判据：** 结论表写入台账，每一行注明证据来源（契约字段名或真机抓到的样例，脱敏）；不新增任何生产调用方。若确有字段，另起工单设计「对局进行时记录己方补位信息」，届时涉及 `features.go` `stores`，文案由用户拍板。

## P3-2　真机对照（**需要你操作**）

打若干局单双排 / 灵活组排，**包含你明确知道谁被补位的对局**（自己被补位，或队友在语音里说了）。对照：
- 开关暂时打开（或看诊断计数）后，标签是否出在正确的人身上；
- `autofill_tagged` 相对总人数的比例是否明显偏离常识；
- `autofill_no_evidence` 是否等于场次数（若是，说明该数据源根本不下发 `individualPosition`，本功能无法在历史局成立）。
结果回填到 `docs/r119-execution-ledger.md` 的 §5 观测栏。没有回填之前 P1-1 的开关保持关闭。
