## P1　单场评分不公正：改成 v3，用 OP.GG 的真实评分做对照校准

### 用户反馈

“有些应该是我的 MVP 对局却不是”，要求参考 OP.GG 的评分系统仔细检查。

### 现状（`backend/web/gameplay.js` `computeMatchScores`，约 2939 行）

- 6 项：KDA 30%、参团 20%、伤害 22%、经济 8%、补刀 12%、视野 8%。
- 每项贡献 `8 × 权重 × x/(x+b)`，KDA 先开平方；总分 `2 + Σ`。
- 单双 / 灵活等 5v5 分路完整时，伤害 / 经济 / 补刀 / 视野的基准 `b` 取**本场同位置两人的中位数**（两人取平均，包含自己）；KDA、参团取全场中位数。
- MVP＝胜方最高，SVP＝败方最高。
- 只在前端算，后端和赛季统计拿不到。

### 问题（已用现有公式实算复现）

把下面这场按现有公式原样算了一遍（32 分钟单双，胜方）：

| 玩家 | K/D/A | 伤害 | 经济 | 补刀 | 视野 |
|---|---|---|---|---|---|
| 胜方 ADC | 14 / 3 / 6 | 42,000（对位 14,000） | 17,500 | 300 | 20 |
| 胜方辅助 | 1 / 2 / 24 | 8,000（对位 6,000） | 8,500 | 30 | 85 |

结果：**辅助 6.79 分拿 MVP，ADC 6.67 分**。ADC 伤害是对位 3 倍、占全队 36%，伤害项只拿到 1.06 分，辅助伤害 8k 拿 0.94 分，几乎一样。把 ADC 改成 15/2/6 也只领先 0.13 分。原因：

1. **同位置基准把自己算进去**：`b = (自己+对位)/2`，`x/(x+b)` 的上限只有 0.667。对位打穿了，也只比持平多 0.17。
2. **完全不看队内占比**：伤害占比、经济占比是 OP.GG 类评分里区分“谁在 carry”的主要信息，现在没有。
3. **助攻被算了两遍**：KDA 里助攻与击杀等价（R115 去掉了 0.8 折扣），参团又按 (K+A) 算一遍；KDA 再开平方压缩死亡惩罚。高助攻低伤害的位置系统性偏高。
4. **缺维度**：没有承伤 / 减伤（坦克）、治疗护盾 / 控制（软辅）、推塔 / 资源。坦克和软辅只能靠 KDA 吃分。
5. **整体过度压缩**：胜方前三名经常在 0.2 分以内，名次（也就是 MVP）由噪声决定。
6. 评分悬停里写了公式和“非官方能力分”，违反 CLAUDE.md 的 R128 §2.5 界面文案红线。

### OP.GG 已公开的部分（以此为准，不要臆测更多）

来源：OP.GG 帮助中心《OP Score explained》《What do the timeline OP Score keywords mean?》。

- 0～10 分，按本局表现估算；仍是 beta。
- **MVP：胜方 OP Score 最高；ACE：败方最高**（我们沿用 MVP / SVP 的名字，不改成 ACE）。
- 时间线评分：峡谷每 5 分钟、大乱斗每 3 分钟算一次，结算时记录最终分。
- 时间线形状生成 14 个关键词（见 P2）。
- **具体输入因子和公式没有公开**。所以我们不能“照抄”，只能自定义一个可解释的模型，再用 OP.GG 真实打分去校准、量化差距。

#### 3. 维度与基准

| 维度 key | 原始值 | 基准（不含自己） |
|---|---|---|
| `kp` 击杀参与 | (K+A)/队伍击杀 | 全场其他 9 人中位数 |
| `kill` 击杀占比 | K/队伍击杀 | 全场其他 9 人中位数 |
| `death` 死亡（反向） | D | 全场其他 9 人中位数 |
| `dmg` 伤害占比 | 对英雄伤害/队伍合计 | 同位置对手 |
| `gold` 经济占比 | 金币/队伍合计 | 同位置对手 |
| `cs` 分均补刀 | (小兵+野怪)/分钟 | 同位置对手 |
| `vision` 分均视野 | visionScore/分钟 | 同位置对手 |
| `tank` 承伤占比 | (承伤+减伤)/队伍合计 | 同位置对手 |
| `util` 辅助 | 治疗+护盾队友/分钟 与 控制秒数/分钟 两项各自归一后取平均 | 同位置对手 |
| `obj` 资源 | 推塔参与 + 龙 / 先锋 / 男爵参与（有 challenges 时）；否则推塔参与 + 建筑伤害归一 | 全场其他 9 人中位数 |

映射（替换 `x/(x+b)`）：`n = 0.5 + 0.5·tanh( ln((x+ε)/(ref+ε)) / k )`，初值 `k = 0.9`；`death` 用 `ln((ref+1)/(x+1))`。持平＝0.5，3 倍于对手≈0.9，真实 0≈0。各维度 ε：占比类 0.01、分均类 0.1、计数类 1、`util` 5。
总分 `score = 10 × Σ wᵢ·nᵢ`，钳在 [0,10]，持平＝5.0。

### 关键词判定

1. **时间线评分**：峡谷每 5 分钟、大乱斗 / 海斗每 3 分钟取一个检查点，再加结算点。每个检查点用 P1 同一模型、只用截至该时刻的累计数据算全员分数：击杀 / 死亡 / 助攻 / 参团来自 `CHAMPION_KILL` 事件，金币 / 补刀来自 `participantFrames`，伤害占比来自帧里的 `damageStats`（来源没有就剔除该维度），资源来自 `BUILDING_KILL` / `ELITE_MONSTER_KILL`；视野、承伤、辅助不进时间线。结算点直接用 P1 的最终分。
2. 需要 ≥3 个检查点，否则不给关键词（例如 12 分钟投降）。斗魂不给关键词。
3. 特征：`early`＝前 1/3 检查点均值，`late`＝后 1/3 均值，`Δ = late − early`，`low`＝除首尾外的最低点，`amp`＝最高减最低，`turns`＝相邻差值 |≥0.8| 时方向改变的次数，`final`＝结算分。
4. 按顺序取第一个命中的（初始阈值，用 P1 第 6 步样本校准，报告一致率，不设硬门槛）：
   - **胜方**：势不可挡（MVP 且所有检查点 ≥6.5）→ 坚韧（low ≤4.5 且 final−low ≥2.0）→ 大器晚成（Δ ≥1.5）→ 胜者（early ≥6.5 且 Δ > −1.5）→ 领导者（MVP）→ 下坡路（Δ ≤ −1.5）→ 过山车（turns ≥2 且 amp ≥3）→ 奉献（final <5.0）→ 平凡。

## P5　英雄胜率里 KDA 全是 0.00:1、场均 0 / 0 / 0（真 bug）

### 证据（用户截图 4）

- 每个英雄 `0.00:1 KDA`、`0 / 0 / 0`，但补刀正常（如探险家 CS 182.6）。
- “全部英雄”行 `0.4 / 0.4 / 0.8`，KDA 3.09。
- 表头“已统计 1106 场”，“全部英雄”却是 634 场。

### 根因（`backend/season_stats.go`，已核对）

1. `seasonStatsFinalize` 把 `Kills / Deaths / Assists` **原地**除以场次变成场均，结果存进缓存 `Stats`。
2. 下一次扫描（前台每次打开总览、后台回补每一轮）把缓存 `Stats` 读回 map 当作累计值，再加上新对局的击杀数，`finalize` 又除一次场次。
3. 每轮都再除一次，场次越多的英雄越快归零（33 场的英雄：第二次就只剩场均 / 33，四舍五入到 0.0）。`TotalCS` 是独立的整数累计，没被改写，所以补刀正常。
4. “全部英雄”行用已坏的场均乘回场次，所以也偏小；KDA 3.09 是近乎 0 的数相除。
5. 1106 ≠ 634：`GameIDs` 记录了扫描到的所有对局（含匹配、大乱斗等不计入的队列），表头却拿它当“已统计”。

### 修改

1. 缓存只存原始累计：新增 `TotalKills / TotalDeaths / TotalAssists`（int），`Kills / Deaths / Assists / KDA` 只在生成响应时从累计值算，**不写回缓存、不修改 map 里的对象**。
2. `seasonStatsCacheSchemaVersion` 升到 10（与 P6 合用这一次），旧缓存的累计值已经损坏、无法还原，必须整季重扫；扫描量与 R132 回补一致（分轮、有上限），账本记一次实际耗时和下载量。
3. 表头“已统计 N 场”的 N 改为实际计入统计的场次（各英雄场次之和），与“全部英雄”行一致。

### 测试

- 同一份缓存连续 `finalize` 3 次，K/D/A 不变（幂等）。
- 加载缓存后再累计 1 场新对局，场均 = (旧累计 + 新值) / (旧场次 + 1)。
- 表头场次 = 全部英雄场次。
- 变异：把 finalize 改回写回缓存，上面第 1 条必须失败。

1. 当天 6 局全是海克斯大乱斗（queue 2400，`lcu_gameflow_session_shape`）。
2. 10:17:26 用户把筛选切到「灵活组排」（`sgp_match_filter_resolved filter=flex`），之后一直停在这个筛选。
3. 10:35:12 对局结束（WaitingForStats），重拉在 **10:35:19、10:35:28、10:35:36** 共 3 次，`filter=flex`，三次拿到的 q_440 第一页都是 **2,325,447 字节**，与 07:47 那次完全一样。新的一局是海斗，灵活组排列表当然不会变，所以 3 次都被判为“没刷新到”。第 2、3 次的 `automatic_read_client` 被日志去重吞掉了，只能从 `overview_load_cost` 的间隔（8～9 秒）认出来。
4. 之后页签停在 `dirty=true, attempts=3`。下一次总览请求是 **11:20:57**（45 分钟后，从前后事件看是用户自己切到「全部」触发的），期间没有任何自动刷新。
5. 10:35:19 那次 `sgp_history_cache_hits=1`：筛选不是「全部」时，后端还会读一份 30 天汇总历史（`gameplay.go` 约 1513 行，`matchHistoryOn(..., 0, maximumSummaryMatchCount, true)`）。这里**不管 force 都写死用缓存**（TTL 5 分钟），所以刚打完时“最近一起玩 / 活跃时段 / 位置”等区块拿到的是赛前数据。由于重拉随后放弃，这些区块也一直停在旧数据。
6. 筛选是「全部」时，重拉都在第一次就成功：07:47:40、08:18:24、08:36:13、08:57:48、09:52:37、10:17:09，每次「全部」第一页的字节数都变了，说明 SGP 在对局结束后几秒内就有新局，**不是上游延迟**。
7. 结束到重拉的延迟（如 07:46:56 → 07:47:40、09:50:21 → 09:52:37）对应 `live_refresh_client hidden=true`：应用在后台时暂停，回到前台立即补拉。这是预期行为，保留。

另有一处源码确认、日志里没有触发的同类问题：筛选视图缓存 `tab.matchViews`（60 秒内切回某个筛选直接用缓存）在对局结束时没有清空，打完立刻切回「全部」可能看到赛前列表。

### 修改

1. **判定改成“刚结束的那一局是否已经进了战绩”，与当前筛选无关**：
   - `markOverviewAfterGame` 记下刚结束的 gameId（`state.liveExpectedGameId` / 对局会话里的 gameId，本日志是 9014822625）和 queueId。
   - 重拉时请求带 `expectGameId`；后端用**不走缓存**的「全部」第一页（国服 SGP / 本机客户端，韩服 Riot match ids）检查这局是否存在，响应返回 `expectedGamePresent: true|false`。筛选恰好是「全部」时直接复用已经拉到的这一页，不多发请求。
   - `expectedGamePresent=true` 就清 `dirty`，不管当前筛选列表有没有变化（灵活组排里本来就不会出现海斗局）。
   - 拿不到 gameId 时（异常情况）退回用「全部」第一页的 gameId 与 baseline 比较，仍然不看筛选列表。
2. **不再永久卡住**：重试间隔 7 s → 15 s → 30 s → 60 s → 120 s，共 5 次；用完就清 `dirty`，回到正常的“超过 120 秒重载”规则。应用在后台时暂停计时，回到前台继续（保持现状）。
3. **`force` 必须真正绕过缓存**：`gameplay.go` 30 天汇总历史那次读取的 `useCache` 改成 `!force`。只影响 force 刷新，普通打开总览仍走缓存。
4. 对局结束标记时清空该页签的 `tab.matchViews`。
5. **诊断**：新增 `overview_dirty_rescan` 事件，每次重拉记一条：`attempt`、`filter`、`finished_game_id`、`finished_queue_id`、`expected_present`、`outcome`（resolved / retry / gave_up / paused_hidden）、`since_end_ms`。`attempt` 不同的事件不能被去重合并。

### 测试

- Node：筛选为「灵活组排」，刚结束的是 2400 局，第一次重拉返回 `expectedGamePresent=true` → `dirty` 清掉，不再重拉。
- Node：一直返回 false → 按 7/15/30/60/120 s 共 5 次后 `dirty=false`；之后超过 120 秒切回总览会正常重载。
- Node：对局结束后 `matchViews` 为空，切回「全部」会发请求。
- Node：后台（`document.hidden`）时不重拉，`visibilitychange` 后立即补拉。
- Go：`force=true` 时 30 天汇总历史读取的缓存命中数为 0；`expectGameId` 检查不使用历史缓存，筛选为「全部」时不额外请求。
