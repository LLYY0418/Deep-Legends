## 诊断：v2 自己错在哪（Claude 用 260 局实算）

260 局 = R211 的原 152 局 + 新账号 108 局，全是 KR 单双。OP.GG 的 MVP / ACE 用官方的 `is_opscore_max_in_team` 标记判定。

| | MVP 一致 | SVP（对 ACE）一致 |
|---|---:|---:|
| v2 原样 | 73.1% | 73.8% |

70 场 MVP 不一致的分布：

| 位置 | 我们错选成 MVP 的 | OP.GG 实际选的 |
|---|---:|---:|
| 辅助 | **22** | 8 |
| 打野 | 12 | **35** |
| 下路 | 16 | 17 |
| 中单 | 11 | 6 |
| 上单 | 9 | 4 |

- **辅助被系统性高估**：KDA 里助攻和击杀等价，参团率又按（击杀+助攻）再算一遍，所以 0/1/9、3/4/23、0/5/36 这类高助攻辅助常常压过 14/3/18 的打野。这是 R211 当时列的问题 3。
- **分数过度压缩**：70 场里有 59 场，我们给胜方前两名的分差小于 0.2 分，所以名次几乎由噪声决定。
- **有些局谁都判不准**：70 场里有 25 场，OP.GG 自己胜方前两名的分差小于 0.3（含多场并列 10 分）。所以 MVP 一致率不可能接近 100%，现实上限大约在 80% 出头。

试过的方向（只在这 260 局上试，用来判断值不值得做，**不是最终参数**）：

| 方向 | MVP | SVP | 结论 |
|---|---:|---:|---|
| KDA 里助攻 ×0.5 | 75.0% | 79.6% | **有效**：辅助错选从 22 降到 7 |
| 加资源维度（推塔 / 龙 / 男爵 / 先锋参与） | 68.5% | 65.8% | 变差：打野被过度高估 |
| 同位置基准不含自己 | 63.5% | 65.0% | 变差 |
| 视野权重 .08→.04、伤害 .22→.26 | 73.1% | 72.3% | 无变化 |

助攻 ×0.5 在两半样本上的稳定性：

| | 原 152 局 MVP / SVP | 新 108 局 MVP / SVP |
|---|---|---|
| v2 | 74.3 / 72.4 | 71.3 / 75.9 |
| 助攻 ×0.5 | 73.0 / 79.6 | 77.8 / 79.6 |

- SVP 两半都稳定提高 4～7 个百分点。
- MVP 一半 −1.3、一半 +6.5，**在噪声范围内**。

所以这次调优只动“助攻折扣”加少量权重微调，不加新维度、不改基准。必须用从没见过的新样本验证（P3），才能证明它确实更好。

## P1　v2 原样搬到 Go，成为唯一评分（先做，与调优结果无关）

### 修改

1. **新文件 `backend/match_score.go`**，实现**当前前端 `computeMatchScores` 的 v2**，逐项一致：
   - 6 项：KDA .30、参团 .20、伤害 .22、经济 .08、补刀 .12、视野 .08。
   - 贡献 `8 × w × x/(x+b)`，KDA 开平方；总分 `2 + Σ`。
   - 分路完整时，伤害 / 经济 / 补刀 / 视野按同位置中位数作基准，否则按全场。
   - 缺维度剔除后权重重新归一；名次和 MVP / SVP 规则不变。
2. **参数做成一个结构体** `scoreParams{AssistFactor, Weights[6]}`。当前值 `AssistFactor=1.0`。P4 判定 v2.1 通过时只换这一组数，不改代码路径。
3. **对局详情响应**里每个参与者带 `score: {value, rank, total, badge, parts:[{key, value, norm}]}`：
   - 前端删除 `computeMatchScores`，战绩卡、详情概览、队伍分析三处改读后端字段。
   - R214 的悬停（名次 / 总分 / 条形）改读 `parts`，显示不变。
   - 依赖旧函数的 `r115-scoring.test.cjs`、`champions.test.cjs` 断言迁到 Go 测试，不能删了事。
4. **补字段**按 R211 P1 §2 原样做，P2 / P6 要用：
   - 承伤、减伤、治疗护盾、控制时间、建筑伤害、推塔、双杀～五杀、`challenges` 的龙 / 男爵 / 先锋。
   - 指针区分缺失与 0。对局详情缓存版本 +1。
   - **这些字段不进评分**，只给标签和英雄表用。
5. **诊断日志 `match_score_computed`**（`features.go` 白名单）：
   - 每局第一次算分时记一条，同一 gameId 本次运行内只记一次。
   - 内容：`source`、`gameId`、`queueId`、分路是否完整、参数版本（`v2` / `v2.1`）。
   - 每人一行：participantId、位置、胜负、K/D/A、6 项原始值、基准、归一值、总分、名次、徽章。
   - 不记玩家名称，只记 participantId 和英雄 ID。
   - 用途：用户觉得某局“应该是我的 MVP”时，可以直接从日志看出每项算了多少。

### 测试（Go）

- **一致性**：
  - 把 R211 的 260 局 match JSON 做成 fixture 输入。Go 版与现有 Python `v2()`（`scripts/r211-score-calibration.py`）逐人比较，|差| < 1e-9，名次和 MVP / SVP 全部相同。
  - 再取 20 局，用前端旧 `computeMatchScores` 的输出做 golden，Go 输出与之一致（迁移前先导出）。
- 缺视野、全场为 0 的维度剔除；重开 / 结果未知不评分；斗魂只出名次。
- `match_score_computed` 同一局第二次请求不重复记录；日志里没有玩家名。

## P2　v2.1 候选：在 260 局上选参数并冻结（必须在 P3 采集之前完成）

### 搜索范围（刻意收窄，避免重演 v3 的过拟合）

- `AssistFactor ∈ {0.3, 0.4, 0.5, 0.6, 0.7, 0.8, 1.0}`。

- 只用 260 局。按账号分组做 5 折交叉验证：同一源账号的对局不跨训练 / 验证折。

- 输出：选中参数、每折结果、与 v2 的逐折对比。

### 冻结

- 参数写进 `docs/history/reports/r216/v21-candidate.json`，记录 SHA-256，写进账本。
- 冻结后不得再改，P3 的新样本不得用于选参数。
- 新脚本 `scripts/r216-select-candidate.py`：候选文件已存在时拒绝覆盖。

## P3　新留出集：用户提供职业 / 高分段 + 普通段位账号，GPT 采集

### 为什么不能用应用内查询的日志代替

### 账号清单（用户填）

文件：`docs/history/reports/r216/holdout-accounts.json`，格式与 R211 的 `new-validation-accounts.json` 相同（`gameName` + `tagLine`，区域 KR）。

- **至少 20 个账号**：一半职业选手或王者 / 宗师；**另一半钻石到铂金的普通玩家**。只用职业选手会偏向高分段，而应用的用户大多是普通玩家。
- GPT 拿到清单后先校验：
  - 不得与 R211 的 20 个源账号重复（按 Riot PUUID）。
  - 每个账号能在 OP.GG 和 Riot 都查到；查不到的写进账本并请用户替换。

### 采集要求

- 新建数据目录 `docs/history/reports/r216/opgg-holdout/`，不得复用 R211 目录。
- 只取 KR 单双（420）、10 人完整、OP.GG 有评分（排除全员 0 分）。
- **剔除**：与 R211 260 局重复的对局；包含 R211 任一源账号的对局。
- **目标 300 局**，每个账号最多 20 局，避免被少数账号主导。
- Key 用 `riot_key.local.txt`（个人 Key），遵守 R208 限流；可中断续跑。

**采集日志加强**（用户要求多加日志），每次运行写一份 `collection-log.jsonl`，每条一行：
- 每个账号：解析结果（PUUID / OP.GG 是否找到）、可用对局数、被剔除对局数及原因（重复、非 420、OP.GG 无评分、人数不全、请求失败）。
- 每个请求：URL 类别（OP.GG 页面 / Flight / Riot match / Riot timeline）、HTTP 状态、耗时、重试次数。不记 Key。
- 汇总 `collection-summary.json`：
  - 总局数、按账号的局数。
  - 按段位分布（用 OP.GG 的 `tier_info`）。
  - 职业 / 普通两组各自的局数。

### 冻结

采集完成后，计算 `opgg-holdout/` 全部文件清单的 SHA-256 并写进账本。**GPT 不运行评估**，评估由 Claude 在 P4 独立运行。

## P4　一次性评估（Claude 运行）和上线判据

### GPT 准备

1. 新脚本 `scripts/r216-evaluate-holdout.py`：
   - 读取冻结的候选和留出集，**用 Go 实现算分**：通过 `go test -run TestR216ScoreDump` 或一个小命令把每局 10 人分数输出成 JSON，脚本只做比对，保证评估的就是上线代码。
   - v2 与 v2.1 各算一遍。
   - 报告：MVP 一致、SVP 一致、名次 ρ 中位数，全部 / 职业组 / 普通组三套。
   - 再加 MVP、SVP 各自的配对比较：两者都对 / 只有 v2 对 / 只有 v2.1 对 / 都错，四格计数。
2. 结果文件已存在时拒绝再次运行。
3. 账本写清楚运行命令。到这一步停下，等 Claude 评估。

### 上线判据（在评估前固定，评估后不得修改）

v2.1 通过，需要**同时**满足：
- MVP 一致率不低于 v2。
- SVP 一致率比 v2 高 ≥ 2 个百分点。
- 名次 ρ 中位数下降不超过 0.01。
- 普通组（钻石～铂金）单独看，MVP 不低于 v2 超过 2 个百分点。

**通过**：GPT 把 `scoreParams` 换成 v2.1，参数版本记为 `v2.1`。
- 赛季扫描里如果存了逐场分数，缓存版本 +1。
- R216 测试里的 golden 同步更新，并在测试名里标明 v2.1。

**不通过**：保持 v2，账本记录结果，不再继续在这批样本上调参。下一次调优必须再采一批新样本。
