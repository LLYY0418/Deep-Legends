## P1　标签换成项目自己的样式（去掉 LeagueAkari 的外观，不用图标）

### 现状（截图 + 源码）

- `gameplay.css` 的 `.match-data-tag` 是实心深色块 + 白字，每种标签一个独立色相（深红、紫、蓝、绿、褐、金、橄榄……十几种），全场第一前面加「★」。整行像一排彩色按钮，和页面其余部分（半透明描边的「势不可挡」「零阵亡」、斜切六边形的多杀、金色 MVP 胶囊）不是一个语言。
- 配色和「★」分层方式都来自 LeagueAkari，辨识度太高。

### 设计要求（用项目已有的语言重做，不要照搬任何外部产品的外观）

项目里已经有一套成熟的标签语言：`.match-keyword-tag` / `.match-zero-deaths`——半透明着色底、1px 同色描边、5px 圆角、10px 字号，颜色来自 `--tag-*` 变量。**数据标签直接并入这一套**，不再另起一套。

1. **形状与尺寸**：高 20px、圆角 5px、内边距 `2px 7px`、10px 字号、不换行；与「势不可挡」「零阵亡」同一家族，同一行里看起来是一伙的。
2. **没有图标**：不使用 ★、箭头、emoji、SVG 小图标、角标。用文字和**填充强度**区分层级：
   - **全场第一**：着色底更实（约 26% 混入 `--surface`）、描边更亮（约 75%）、文字字重 700；
   - **队内第一**：沿用关键词标签的轻量配方（约 14% 底、55% 描边、字重 600）。
   - 不用渐变、不用阴影、不用实心白字深色块。
3. **只用 5 个色系**，全部取自现有 `--tag-*` 变量，不新增十几个独立色相：

| 色系 | 标签 | 取色变量 |
|---|---|---|
| 输出 | 输出、伤转率、击杀 | `--tag-unstoppable` |
| 控制 | 控制 | `--tag-resilience` |
| 承受与支援 | 承伤、治疗、护盾 | `--tag-dedication` |
| 经营（仅召唤师峡谷） | 补兵、经济、拆塔、参团 | `--tag-leader` |
| 技巧 | 单杀、越塔、塔之子、压刀、好钩 | `--tag-innocent` |

4. **文案**（2–4 个字，不带符号）：全场第一写作「输出第一」「击杀第一」等；队内第一写作「队内输出」「队内击杀」等。维度用词：输出（原「伤害」）、伤转率、控制、治疗、护盾、承伤、击杀、参团、拆塔、经济（原「金币」）、补兵。单杀、越塔、塔之子、压刀、好钩保留「名称×次数」。悬停文字沿用现有说明句（「全场最高伤害：…」「单杀：N 次」）。
5. **深浅主题**：浅色主题照 `.match-zero-deaths` 的做法给固定深色文字和浅色底；实测文字对比度 ≥ 4.5（沿用 R235 的 Chromium 量法，深浅各记录最小值）。
6. **不动**：评分胶囊（MVP/SVP/名次）、斜切六边形多杀标签、关键词标签（势不可挡等）、零阵亡的现有外观，只调整它们和数据标签放在一起时的间距与高度对齐。
7. **不要写任何方法论、免责声明或「说明」文字**到界面；解释只放在悬停提示里（已有）。

## P3　标签永远单行、放在装备栏右侧；放不下就隐藏，悬停看剩余的

### 现状（截图 + 源码）

- 标签在**装备栏下面**另起一行，不在右侧。原因在 CSS：`.match-build{flex-wrap:wrap}` 加 `.match-tags-collection{width:100%}`，加上 `.match-build .match-badges{min-width:max-content}`，三处叠加把标签挤到下一行；同一个选择器 `.match-build .match-badges` 在 2176 行和 2230 行有两条互相矛盾的规则。
- 截图里装备栏右侧到名单之间有大片空位（斗魂卡片约 740px），完全够放。
- 悬停「+N」目前是一段纯文字提示，列出的是**全部**标签，不是被隐藏的那些。

### 修改

1. **布局**：`.match-build` 在桌面宽度下 `flex-wrap:nowrap`；装备栏固定宽度，`.match-badges` 为 `flex:1 1 0; min-width:0; overflow:hidden`，标签集合 `display:flex; flex-wrap:nowrap; white-space:nowrap`。标签与装备栏**垂直居中对齐在同一行**，不再单独占一行。合并 2176/2230 两处冲突规则，只留一份。
2. **窄屏**：780px 及以下若装备栏右侧已没有位置，仍然不换行，直接只显示「+N」；不要回到换行布局。
3. **隐藏规则**：沿用 `fitMatchTags` 的按宽度计算，保留优先级顺序（评分胶囊 > 多杀 > 关键词 > 数据标签 > 零阵亡），**评分胶囊（MVP/SVP/名次）永远不被隐藏**；放不下的从优先级最低的开始隐藏，末尾显示「+N」。「+N」的样式与标签同一家族（中性色，不用实心深色块）。
4. **「+N」悬浮窗（用户给的参考图：LeagueAkari 的「+4」，悬停后在上方弹出一个窗，里面是剩下的标签）**——**交互照这个做，外观用我们自己的**：
   - 触发：鼠标悬停或键盘聚焦「+N」（它是 `button`），出现悬浮窗；移开、失焦、按 Esc、滚动时关闭；触屏点击切换。出现延迟 ≤ 80ms，不要用浏览器原生 `title`。
   - 位置：默认在「+N」**正上方**居中，带一个指向「+N」的小三角；上方空间不够（贴近窗口顶部）时翻到下方；水平方向夹在窗口内，不被卡片或滚动容器的 `overflow:hidden` 裁掉——所以悬浮窗要挂在 `document.body`（`position:fixed`）上，不能放在标签容器里面。
   - 内容：里面放**被隐藏的那些标签本身**（同样的标签样式，不是纯文字列表），按隐藏顺序排列，一行放不下就换行，最大宽度约 320px；不放已经显示在行内的标签。没有被隐藏的标签时不显示「+N」。
   - 外观：用项目现有的悬浮提示面板（`var(--surface-strong)` 底、`var(--line)` 描边、与现有 `data-tooltip` 同样的圆角和阴影），不要照搬 LeagueAkari 的深色气泡和实心胶囊；「+N」本身是中性色的同家族标签（`color-mix` 的灰底灰描边），不是实心深色块。
   - 悬浮窗里的每个标签仍保留自己的悬停说明（「全场最高输出：…」）；说明提示的层级要高于悬浮窗。
   - 同一时间只开一个悬浮窗；快速划过多张卡片不残留。
5. 保留 R235 已有的性能处理（ResizeObserver 只在宽度变化时重算、跳过离屏卡片），不要因此回到每次切回强制布局。

### 测试

- Node：悬浮窗里的标签集合 = 被隐藏的集合（不含已显示的）；评分胶囊永远可见；打开第二个悬浮窗时第一个已关闭；Esc、失焦、滚动都会关闭。
- Chromium（深浅两套，1280 / 900 / 780 宽）：
  - 标签行顶部与装备栏顶部偏差 ≤ 2px，且标签行高度 ≤ 装备栏高度（证明没有换行）；
  - 斗魂卡片（用户截图那种）、峡谷卡片、大乱斗卡片各一张截图；
  - 窄宽度下只剩「+N」时仍不换行；
  - 悬浮窗：出现在「+N」上方并带三角，不被卡片裁剪；贴近窗口顶部时翻到下方；截图深浅各一张（悬浮窗打开状态，里面是标签本身）。
- 变异：恢复 `flex-wrap:wrap` → 单行断言必须 FAIL。

### 预期效果（用截图那几场对照）

- 斗魂第 1 名（原：MVP ★伤害 ★伤转率 单杀×3 ★击杀 参团 金币 ★补兵 双杀）→ MVP、输出第一、击杀第一、双杀。

## P4　日志发现：总览每次打开都重新拉约 11.6MB 的赛季头部（5 分钟内连刷 3 次）

### 证据（`season_stats_head_refresh`，本人账号，当前构建）

| 北京时间 | scanned | sgp_bytes | sgp_requests | fresh |
|---|---|---|---|---|
| 00:59:46 | 528 | 11,632,735 | 2 | false |
| 01:02:05 | 528 | 11,632,735 | 2 | false |
| 01:07:13 | 528 | 11,632,735 | 2 | false |
| 01:08:29 | 528 | 11,632,735 | 2 | false |
| 01:08:43 | 528 | 11,632,735 | 2 | false |
| 01:31:28 | 528 | 11,632,735 | 2 | false |

- 每次 `scanned` 都是 528，没有新对局，仍然重新请求（01:07、01:08、01:08 三次在 90 秒内）。
- 每次头部扫描两条流（海斗 `q_2300,q_2400,q_3270`、排位 `q_420,q_440`）各 50 场，加上总览本身 20 场 + 单队列 20 场，一次进入总览合计约 15MB。国内晚高峰或移动网络下这是实打实的慢和流量。
- 对比 21:14 那份日志：同样每次进入都是 11.6MB，说明这不是 R235 新引入，但 R235 的头部流程没有解决。

### 修改

1. 头部扫描前先做一次**很小的新鲜度检查**：只请求最新 1 场（不带标签，`count=1`），比较最新 GameID 和本地记录的头部标记；**没有新对局就直接跳过两条流的头部扫描**，`season_stats_head_refresh` 记 `skipped=true`、`sgp_bytes` 为小请求的字节数。
2. 有新对局才扫描，且只扫到遇到本地已有 GameID 为止（已有的游标逻辑），不要固定拉 50 场。
3. 同一账号 60 秒内再次进入总览，不做任何头部请求（合并/复用上一次结果）。
4. 诊断补充：`season_stats_head_refresh` 增加 `skipped`、`skip_reason`（`no_new_game` / `recent`）、`new_games`。

### 测试（Go）

- 假 SGP：两次进入、无新对局 → 第二次只有 1 个小请求；有新对局 → 只拉新增并停在已有 ID。
- 60 秒内连续进入 → 0 次头部请求。
- 并发：新鲜度检查与已有后台回补不竞态（`-race`）。
- 变异：去掉新鲜度检查 → 无新对局用例必须 FAIL。

## P5　日志发现：收藏页「待重试」每次启动都 3 次重试后放弃（blank_entries=1）

`collection_data_retry_exhausted`：北京 23:56、00:13、01:00、01:03、01:32 共 5 次，每次 `attempts: 3, blank_entries: 1`，前面是 3 次 `collection_refresh_lifecycle source=pending_retry`（间隔约 18 秒、34 秒）。同一个空条目每次启动都重试到放弃。

### 根因

日志没有记录是**哪一个**条目为空，只记了数量，所以现在判断不了是数据问题（某个皮肤/表情/奖池元数据缺失）还是网络问题。不要猜。

2. 对同一个目录版本下**已经重试放弃的同一个条目**做 1 小时的负缓存，不再每次启动重试 3 次。
3. 把补充后的诊断样本写进账本，**不要在没有证据的情况下改收藏页逻辑**。

### 测试（Go）

- 夹具：一个永远为空的条目 → 第 1 次重试 3 次后放弃并记样本；1 小时内再次触发 → 0 次重试。

## P6　战绩条中间部分加宽：KDA、伤害/承伤、装备栏与右侧名单之间的空隙太大

### 现状（截图 + `gameplay.css`）

`.match-summary` 是四列：`108px | minmax(0,1fr) | 名单(150–190px) | 40px`；中间那一列里的 `.match-main` 又是四列：`champion(auto) | KDA(96px) | 数据块(宽 188px) | minmax(0,1fr)`（斗魂是三列）。**最后那个 `1fr` 是空的**，数据块固定 188px，所以 KDA 和伤害/承伤挤在左半边，右边到名单之间空出约 400px（截图里斗魂卡片从「承伤 29843」到名单之间一整片空白）。装备栏和标签行（`.match-build`，`grid-column:1/-1`）也被限制在窄的左半边，这正是标签放不下的原因之一。

### 修改

1. 把空的尾列用起来，让 KDA 和数据块吃掉富余宽度，而不是留白：
   - KDA 列从固定 96px 改成 `minmax(96px,1fr)` 级别的弹性宽度，KDA 数字和「x.xx:1 KDA」居中于该列；
   - 数据块（伤害/承伤，或击杀参与率/CS/平均段位）从固定 188px 改成 `minmax(188px,1.4fr)` 之类，标签靠左、数值靠右，数值列加宽，不再贴在一起；
   - 去掉空的尾列（斗魂、峡谷、大乱斗三种 `.match-main` 变体都要处理）；
   - 具体比例由你按截图调，目标：中间块与名单之间的空隙缩到约 60–100px（1x 缩放、1280 / 1600 / 1920 宽），不要把名单挤小，名单宽度保持 `clamp(150px,18cqi,190px)`。
2. 装备栏与标签行随之变宽：`.match-build` 现在能占满中间列的全部宽度，标签才有地方放（P3 的单行在这个宽度上才成立）。装备格本身尺寸不变。
3. 响应式：1100px 以下断点（现有 `@media` 里 783、797、804、812、815 行）的布局保持不变，窄屏仍然是装备栏在主区域下方、标签单行的做法，只补上「不换行 + +N」。
4. 对局列表在深浅主题、斗魂/大乱斗/峡谷三种卡片、有评分和无评分的卡片上，行高不变（`min-height:118px`），不引入新的换行或跳动；R235 的 `content-visibility` 与行高估算不要被打破（切回「全部」仍然是 R235 测到的 ~17ms 水平）。
