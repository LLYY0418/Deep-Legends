## P5　韩服战绩又慢又会失败（「之前不是都好的吗」）

### 证据

**探测**

| 时间（北京） | `riot_relay_probe` |
|---|---|
| 20:45:47 | ok，**首字节 4.47 秒** |
| 20:46:47 | failed：`/health` 返回 **404**（首字节 2.79 秒），回退到状态路径后，同一个 8 秒预算用完 → 退避 30 秒 |
| 20:48:08 | failed，8 秒超时 → 退避 60 秒 |
| 20:49:12 / 20:49:18 | ok，1.28 秒 / **5.67 秒** |
| 20:50:12 / 20:51:16 | 又是 `/health` 404 加超时 → failed |

**总览**

- 20:45:56 韩服玩家总览 12.9 秒（账号 5.7 秒，排位/熟练度/对局列表各约 7 秒）。
- 20:46:32、20:46:47、20:49:30 三次 503（不可用）。

**10 分钟汇总**（20:55:47）：49 个请求里有 **16 个网络失败**、3 个 403、9 个 404，没有 429。

**Riot 限速头**：`app: 1 秒 20 次、120 秒 100 次`。这是 personal key 的额度，所有用户共用每 2 分钟 100 次。

### 根因

1. **`/health` 没有部署**。新的探测先请求 `/health` 得到 404，再回退到状态路径，两次请求共用 8 秒预算。晚高峰首字节 3–5 秒，两次加起来就超时，探测失败后退避 30/60 秒，期间所有韩服请求直接返回不可用。这是 R231 留下的风险，日志已经证实。
2. **晚高峰国内访问 Cloudflare 很慢**。20 点以后国际出口拥塞：首字节 3–6 秒，10 分钟内 1/3 的请求在网络层失败。白天测的时候正常，所以「之前是好的」。
3. **韩服总览串行两轮往返**（先查账号，再并发查其余），每轮 3–6 秒，加起来就是 12 秒。
4. Key 是 personal 级别，用户一多就会撞到每 2 分钟 100 次的上限（这次还没撞到）。

### 修改

1. **部署 Worker `/health`**（代码 R231 已写好，用户已确认部署）。在 `relay/riot-worker/` 执行 `wrangler deploy`（需要用户机器上已登录的 Cloudflare 账号；未登录就让用户先跑 `wrangler login`，不要要密钥）。部署后实测并写进账本：
   - `curl -i https://riot.yinxiaobia.net/health` → 204，带 `Cache-Control: no-store`；
   - 白名单外路径（如 `/r/xx/foo`）→ 404；
   - `/r/kr/lol/status/v4/platform-data` 仍然 200；
   - 再看一次软件日志里的 `riot_relay_probe`：不再有「`/health` 404 → 回退」那一串。
2. **探测不再阻塞业务请求**：
   - 10 分钟内有过成功请求，就不再单独探测，直接发业务请求；
   - 需要探测时，探测和第一个业务请求并发，任何一个 2xx 都算可达；
   - `/health` 和回退路径各用独立的 8 秒预算。
3. **业务请求**：
   - 单次超时改为 15 秒；
   - 网络层错误（连接重置、首字节超时）自动重试 1 次，隔 500ms；
   - 连续 3 次网络错误才进入退避，退避从 15 秒开始。
4. **韩服总览少一轮往返**：
   - 按 Riot ID 缓存账号（PUUID）到本地磁盘，有效期 24 小时，命中后直接并发查其余接口；
   - 本次请求一回来就后台刷新缓存。
5. **诊断**：`riot_relay_request_summary` 的 `failures.auth` 和 `failures.network` 按路径类别分开记（account/summoner/league/mastery/match），用来定位 3 个 403 来自哪里。
6. **第二个中转节点：不是必须，本单先不做，做完上面 1–5 条后用数据再决定**（用户问「必须做吗、提升多大」，结论如下，写进账本）：
   - **不是必须。** 今晚日志里的失败主因是 `/health` 没部署导致探测误判（探测失败 → 退避 30/60 秒 → 期间所有韩服请求直接报不可用），这一部分靠第 1–3 条就能消掉，不需要新机器。
   - **节点能解决的只有「国内到 Cloudflare 的晚高峰链路」**：日志里首字节 3–6 秒、10 分钟内 16/49 个请求网络失败，是链路问题，业务代码改不掉。国内线路好的香港/首尔机器通常比这条链路稳，但提升多少要实测，**不要预先承诺数字**。
   - **节点解决不了 Riot 限速**：personal key 的 `1 秒 20 次、120 秒 100 次` 是按 key 算的，所有用户共用，换节点不会多出额度；这个只能靠 production key。今晚 10 分钟内没有 429，限速目前不是瓶颈。

## P6　海斗隐藏分还是显示不出来

### 证据（`mayhem_rating_lookup`，ARAMKit）

| 时间（北京） | 结果 | 耗时 |
|---|---|---|
| 20:36:54 | 本人，**timeout** | 9.0 秒 |
| 20:38:07 | 本人，成功 | 7.0 秒 |
| 20:39:34 | 成功 | 2.9 秒 |
| 20:47:56 | 成功 | 4.2 秒 |
| 20:48:09、20:48:25 | **response-read**（响应头 200，响应体 9 秒内没读完） | 9.0 秒 |

### 根因

- ARAMKit 实时计算，响应体最大约 2MB（带近期每局 10 人明细），晚高峰 3–9 秒以上。
- 我们给的总时限是 9 秒（含读完响应体），前端还有 12 秒总超时。超时后显示「暂不可用」，60 秒内不会重试，弹层里也没有重试按钮，看起来就是「一直出不来」。

### 修改

1. 后端改为两段时限：响应头 10 秒，读响应体 25 秒；前端请求超时改为 40 秒。
2. 失败（timeout / response-read / network）不进入失败缓存，下次打开弹层就立即重试；只有「未收录」缓存 5 分钟。
3. 打开总览就在后台发起查询（现有逻辑）；用户打开弹层时如果还在查询中，显示「查询中」，不要让请求被重复取消。
4. 弹层在失败状态显示一个「重试」按钮，复用现有按钮样式，不加说明文字。
5. 诊断：`mayhem_rating_lookup` 增加 `ttfb_ms`、`bytes`，区分是服务端算得慢还是传输慢。

### 测试

- Go：假 ARAMKit 首字节 8 秒、响应体 15 秒读完 → 成功；超时失败后下一次请求不命中失败缓存。
- Node：失败状态下弹层有「重试」，点击后进入「查询中」，成功后显示分数。

   - 同时请求 LCU 历史，回来后原地替换；
   - LCU 历史超过 3 秒没回来，就先把快照和排位、熟练度渲染出来，不让整个总览一起等。
3. 连接成功后到事件流连接成功之间的 3 秒：确认是否在串行做某件事，能并发就并发，写进账本。
4. 目标：日服本人从「连接成功」到「总览出现」≤ 2 秒（有快照时）。

### 测试

- Go：拳头服本人总览不调用中转（假中转记录调用次数 = 0）；LCU 历史 6 秒才返回时，总览在 3 秒内返回（带快照），历史回来后通过 SSE 补齐。

## P8　客户端启动时，加载遮罩提前消失，此时玩家标签页还没出现；分组也没切过去

### 证据

| 时间（北京） | 事件 |
|---|---|
| 20:51:00.9 | 遮罩显示（`blocking_state_client show`） |
| 20:51:15.9 | **遮罩按 15 秒超时隐藏**（`hide_reason=timeout`），这时客户端还没连上，界面退回到「启动方式」页 |
| 20:51:24.6 | 连接成功 |
| 20:51:37.6 | 本人标签页才出现 |

### 根因

1. 遮罩只有固定 15 秒超时，不看连接状态。客户端启动阶段（`probe-failed` / `credentials-unreadable`）本身就要 20 秒以上。
2. 分组切换（`gameplay.js` 约 552–562 行）只在「本人页签当时正是该分组的激活页签」时才切。用户正在看其他分组或其他玩家时，客户端启动后不会切到对应服务器的分组。

### 回答用户的问题

现在不是总会切过去。只有本人页签原本就是那个分组里正在显示的页签时，才会切。

### 修改

1. **遮罩只在以下情况隐藏**：
   - 本人页签已经渲染，并且首个卡片 ready（`overview_card_ready`）；
   - 连接明确失败：进程消失（`process-not-found`）持续 5 秒；
   - 兜底总超时 120 秒。

   客户端处在启动中（`probe-failed` / `credentials-unreadable` / 已连接但总览未返回）时，遮罩保持显示，文案沿用遮罩现有的阶段文案，不新增文字。
2. **分组跟随**：客户端从未连接变为已连接、并且身份就绪时，如果用户在最近 10 秒内没有手动切换过页签，就自动切到本人页签所在的分组（国服 → 国服分组，日服/韩服 → 拳头分组），并激活本人页签。
3. 诊断：`blocking_state_client hide` 记录 `hide_reason`（`self-tab-ready` / `connect-failed` / `hard-timeout`）。

### 测试（Node）

- 启动中持续 30 秒 `probe-failed` → 遮罩不隐藏；连接成功并收到首个卡片 → 隐藏，原因 `self-tab-ready`。
- 用户停在另一个分组，客户端连上 → 自动切到本人分组；用户 10 秒内刚切过 → 不切。

## P10　筛选切到某个模式再切回「全部」，要卡约 2 秒

### 证据

- 切回「全部」时没有网络请求（用的是 60 秒内的缓存视图）。
- 同一分钟里 `renderer_perf` 记录到 9–20 个长任务，合计 0.75–1.6 秒。当时页面 5000 多个节点、500 多张图片。
- 卡顿来自把「全部」的整份列表（常常已翻页到上百局）一次性重新生成 HTML 并重新挂图片。缓存超过 60 秒时还会重新请求网络。

### 修改

1. 每个筛选保留一份已渲染的 DOM：切走时把列表节点移进 `DocumentFragment` 存下（参考 R231 P3 的详情页暂存），切回时原样放回。图片、展开状态、滚动位置都保留。
2. 缓存视图的有效期改为 5 分钟。切回时如果超过 30 秒，就在后台只请求头部 1 页：有新对局就插到顶部，没有就不动。
3. 最多保留 4 个筛选的暂存，超出时按最久未用回收。
4. 目标：切回「全部」≤ 100ms，过程中没有超过 50ms 的长任务。

### 测试

- Node：切换「全部 → 灵活 → 全部」，第二次进入「全部」时列表节点和原来是同一批（`===`），不重新生成；滚动位置恢复。
- 缓存 31 秒后切回 → 后台头部请求 1 次，新对局插到顶部。

## P11　斗魂 3x6 战绩被算成「5 连胜」（用户截图：甜甜酱QvQ#34839）

### 现象

截图里最近 6 场全是斗魂竞技场 3x6，名次依次是 **1、2、4、3、4、5**。战绩卡片自己的判定是：前三名蓝色（胜）、第 4 名和第 5 名红色（负）。但头像旁边的徽章显示「5 连胜」。

### 证据

- 日志 `sgp_match_history_succeeded`（`filter: arena`，12:37 UTC）：`participant_counts: {"18": 20}`，即这 20 场斗魂每场 18 个人，3 人一队，**一共 6 队**。队名次最大是 6。
- 日志 `match_mode_classified`：`queue_id: 1750`，`queue_label: 斗魂竞技场 3x6`。

### 根因

`backend/web/gameplay.js` 的 `computeOverviewStreak`（约 8830 行）里，斗魂对局写死了「名次 ≤ 4 算胜」：

```js
const next = arena ? (Number(subject?.placement) > 0 ? (Number(subject.placement) <= 4 ? "win" : "loss") : "") : …
```

这个阈值只适合「2 人一队、8 队」的经典斗魂。3x6 只有 6 队，前一半是前 3 名。所以截图里的 1、2、4、3、4 全被算成胜，第 5 名才断开，正好是「5 连胜」。按卡片的口径（前 3 名为胜），最近三场是 胜、胜、负，连胜根本不到 3 场，徽章不应该出现。

同一个写死的 4 还有两处同类问题：
- `gameplay.js` 约 3971 行：斗魂对局详情里的队伍分组，`group.placement <= 4` 标成 `is-top`，3x6 的第 4 名会被标成上半区；
- `backend/web/demo-data.js` 约 254 行：演示数据 `placement <= 4`。

### 修改

1. **只保留一个斗魂胜负口径**：前一半队伍为胜 = 名次 ≤ ⌈队伍数 ÷ 2⌉。队伍数取这一局参赛者里不同的 `subteamId` 个数（8 队 → 前 4 名，6 队 → 前 3 名）；取不到队伍数时，按队列 ID 回退（1750 → 6 队，其余斗魂队列 → 8 队）；再取不到就不下判断。
2. **先查战绩卡片的蓝/红是怎么来的**（`match.result`，后端 `backend/gameplay.go` 约 3880–3903 行按名次赋值）。如果后端口径已经正确，前端连胜直接用 `match.result`，不要在前端再算一遍；如果后端也写了固定阈值，两边一起改。目标是卡片颜色、连胜徽章、对局详情的上半区标记三处**来自同一个函数/同一个字段**，不能再各写各的。
3. `computeOverviewStreak`：斗魂分支改用上面的统一口径。其余规则（跳过重开、自定义、未知结果；至少 3 场才显示；`plus` 表示后面还有更多场）保持不变，是否跨模式连续计数也保持现状。
4. 3971 行的 `is-top` 和演示数据同步改用统一口径。
5. 排查：全局搜一遍还有没有别的地方写死斗魂「4」或「8 队」（`rg "placement\s*<=?\s*4|<= 4|<=4"`），逐个说明是不是同类问题，写进账本。

### 测试（Node）

- 3x6（18 人 6 队）名次由新到旧 1、2、4、3、4、5：连胜为 `null`（前两场胜，第三场负）。
- 3x6 名次 1、2、3、3、1：连胜 5，且 `strong`（≥5）。
- 经典 8 队名次 1、2、4、3、4：连胜 5（前 4 名为胜，不能被误伤）。
- 6 队名次 3 → 胜，4 → 负；8 队名次 4 → 胜，5 → 负（边界）。
- 缺 `subteamId` 时按队列 ID 回退；队列 ID 也未知 → 该场不下判断，连胜在此断开。
- 卡片颜色、连胜、详情页 `is-top` 对同一场数据结论一致（同一组夹具三处断言）。
- 变异：把阈值改回写死的 4 → 第一条必须 FAIL。
