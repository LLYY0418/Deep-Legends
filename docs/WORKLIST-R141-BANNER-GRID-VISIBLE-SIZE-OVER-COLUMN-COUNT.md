## 0. 背景：为什么要重新开工单而不是回去改 R140

`docs/r140-execution-ledger.md` 里的真机测量数据（1200px 可用宽度 882.22px，960px 可用宽度 657.56px）是准确的，`floor((882.22+16)/(152+16))=5`、`floor((657.56+16)/(152+16))≈4` 的算法也没错——问题是"4-5 列"这个约束本身，在这个容器宽度下，从数学上就只留了几乎没有放大空间（150→152px）。截图对比（`docs/r140-validation/before-grid-1200.png` vs `after-grid-1200.png`）确认卡片视觉上几乎没变化，改善全部来自间距从 `12px 10px` 加到 `20px 16px`。

R140 本身没做错，是约束条件需要放宽，所以另开号，不回去改 R140。

## 1. 新目标：格子宽度目标约 200px，允许列数降到 3-4 列

1. 不要凭猜测锁死 200px 这个数字——用 `desktop/r140-banner-layout.cjs`（或扩展它）在真机 Chromium 里重新测：
   - 复用已经测出的可用宽度基准（1200px→882.22px，960px→657.56px），如果这两个数值在当前代码状态下有变化，以重新测量为准。
   - 在这个可用宽度下，选一个列宽，目标是**比 R140 的 152px 明显更大**（不小于 190px），同时保证：
     - 1200px 宽度下列数落在 **3-4 列**（不要求刚好是 4，只要求不多于 4、不少于 3）。
     - 960px 宽度下列数落在 **3-4 列**。
   - 按 200px 目标折算：1200px 下约为 4 列，960px 下约为 3 列（`floor((882.22+16)/(200+16))=4`，`floor((657.56+16)/(200+16))=3`）——这是预期结果，但最终数值必须以真机渲染结果为准，不是照抄这个算式。
   - 列宽定下来后，同步更新 `.facade-grid.is-banners` 的 `contain-intrinsic-size`（跟着 `aspect-ratio: var(--facade-banner-ratio)` 重新算实际高度）。
2. 间距维持 R140 定的 `gap: 20px 16px` 不用再改。
3. 头像视图（`.facade-grid.is-icons`）本单不动。

### 验收

- 扩展或新建真机布局脚本，在 1200px 和 960px 两个宽度下量出旗帜网格实际渲染列数，断言都落在 3-4 之间（含 3 和 4）；同时断言列宽数值 ≥190px。截图存到 `docs/r141-validation/`，并与 R140 的 `before/after-grid-1200.png` 做一次三方对比（R138 之前 / R140 之后 / R141 之后），确认这次卡片视觉上肉眼可辨地变大，不再是"看起来一样、只是间距变了"。
- CSS 断言：`.facade-grid.is-banners` 的 `grid-template-columns` 数值比 R140 的 `152px` 明显更大（≥190px）。
- 变异：把列宽改回 `152px`，列数断言必须变化（列数应该变回 4-5）或 FAIL。
- 用真实旗帜图片过一遍，确认没有裁剪、变形；未拥有旗帜的置灰+锁图标在新尺寸下比例正常。
- 检查并更新所有断言旧列宽/列数的既有测试（例如 `desktop/r140-banner-layout.cjs` 如果里面锁了"4-5 列"或"152px"的断言，需要同步改成新目标），不能留着和新行为矛盾的旧断言。
