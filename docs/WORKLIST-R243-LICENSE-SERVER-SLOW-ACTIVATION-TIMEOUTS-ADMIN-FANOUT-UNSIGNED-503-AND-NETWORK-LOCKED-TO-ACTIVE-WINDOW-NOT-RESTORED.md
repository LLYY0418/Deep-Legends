## 日志证据

- 05:55:59 第五次成功，耗时 1128 ms。
- 客户端单次请求超时是 `backend/license.go:25` 的 `licenseTimeout = 8s`，所以前三次是**服务端 8 秒内没有响应**。

**A（诊断 1402）**：
- 同一时段续租明显变慢且频繁失败：
  - 05:42:08 失败（`body`），05:43:34、05:43:58、05:44:21 失败（`network`），05:54:32 失败（`body`）。

**A 窗口问题**：
- 05:42:00 启动，第一次续租失败，窗口从 PENDING 切到 **NETWORK_LOCKED**（860×580），显示"无法连接激活服务"（截图一）。
- 05:42:25 续租成功，状态变为 ACTIVE，页面显示主界面。
- 但 05:42:29 记录了 **`client_diagnostic_rejected raw_event=license_window_state reason=invalid-window-state`**：这次 NETWORK_LOCKED→ACTIVE 的窗口切换记录被后端校验拒绝。`backend/license_window_diagnostic.go:36` 只在请求尺寸或实际尺寸的宽或高 ≤0、或缺失时拒绝。说明这次切换算出的目标尺寸无效，窗口因此停在 860×580（截图二）。
- 而运行中 REVOKED→ACTIVE（05:44:55、05:46:48、05:50:18）和重启后 PENDING→ACTIVE（05:44:13）都正常恢复到 2111×1314 左右。所以问题只在**启动时先进入 NETWORK_LOCKED、之后自动恢复为 ACTIVE** 这条路径上。
- 另外，切换从 05:42:25 到记录被拒用了约 3.5 秒，远超正常的 20–200 ms，也要一起查清。

## 服务端根因（已读代码）

1. **管理页每次刷新都逐个查询每个注册码的 Durable Object（DO）**：
   - `src/admin-query.ts:34–38`：列表的每一行都对对应的 LicenseDO 发 `snapshot`，8 个一组并发。
   - `src/admin-query.ts:50`：汇总卡片对**所有行**并发调用。
   - R242 的管理页每 30 秒自动刷新列表和汇总，切回页面时也刷新。
   - LicenseDO 内部用一个队列串行处理所有命令（`license-do.ts` 的 `tail`），而 `snapshot` 还会先执行 `recover()` 和 D1 查询。所以管理页开着时，**真实用户的激活/续租要排在管理页的查询后面**。
   - 现在 staging 只有少量码，已经出现 5–8 秒延迟；生产有 100 个码以上时，每 30 秒会有约 200 次 DO 调用，情况更糟。
2. **服务端内部错误返回未签名的 503**：
   - `src/public.ts:16、21、43、49` 在内部失败时返回裸 JSON `{"error":"SERVICE_UNAVAILABLE"}`，没有签名。
   - 客户端无法验签，只能记为 `body` 失败，用户看到的仍是"无法连接激活服务"，日志里也分不清是服务端出错还是网络问题。
3. **服务端没有日志**：`wrangler.jsonc:14` 是 `"observability": { "enabled": false }`，所以出了问题看不到服务端的耗时和错误。

## P1　管理页不再逐个查询 DO（会话 B）

1. 列表和汇总**只从 D1 读取**，不再对每一行调用 LicenseDO：
   - "在线"的判断改为 `last_seen_at + 租约时长 > 现在`（`last_seen_at` 由 R242 P7 每 5 分钟回写一次）。
   - 列表上的"在线/租约剩余"因此是估计值，最多晚约 5 分钟。不需要在界面上加说明文字。
2. **只有打开详情抽屉时**才查询这一个码的 DO，显示精确的当前设备、租约剩余和设备列表。抽屉里每 30 秒刷新一次，抽屉关闭后停止。
3. 设备号搜索（R242 的管理员码设备前缀搜索）如果依赖 DO，改为用 D1 已有的 `current_device_short` 匹配。管理员码的多设备前缀搜索只在详情抽屉中提供。账本里写明取舍。
4. `snapshot` 必须是只读的：不执行 `recover()` 中的写操作；不在 `pending` 存在时阻塞读取（可以返回 `pending: true` 的旧数据）。确保管理页查询不会让真实用户的激活/续租排队。
5. 写测试：
   - 列表、汇总请求不调用任何 DO（可以用计数桩证明）。
   - 详情抽屉只调用一个 DO。
   - **压力测试**：本地模拟 100 个码，管理页同时每 30 秒刷新列表和汇总，并且有 10 个客户端持续续租、1 个客户端反复激活。记录激活/续租的中位数（p50）和第 95 百分位（p95）耗时，改动前后对比写进账本。要求改动后**本地 p95 < 1 秒**，并且没有续租排在管理查询后面。

## P2　服务端错误必须签名，并开启服务端日志（会话 B）

1. 激活/续租接口在能签名的情况下（签名密钥可用），所有内部失败都返回**签名的** `SERVICE_UNAVAILABLE` 协议响应，不再返回裸 JSON。包括 DO 调用失败、D1 失败、超时、异常。只有签名密钥本身不可用时，才允许返回未签名 503，此时日志里注明 `signing_unavailable`。
2. 客户端对签名的 `SERVICE_UNAVAILABLE` 已有处理（按网络类错误重试），不需要改协议。共享向量里已有该错误的向量，不要新增或修改向量。
3. 开启 Workers 日志：`wrangler.jsonc` 中 staging 环境设置 `"observability": { "enabled": true }`（生产环境也开启，采样率 100%）。
4. 每次激活/续租写**一条**结构化日志（`safeLog`），字段：
   - `kind`（activate/renew）、`result`（ACTIVE 或错误码）、`http_status`。
   - 各阶段耗时（毫秒）：读取与验签、D1 查找、DO 排队等待、DO 处理、D1 回写、签名、总耗时。
   - 注册码标识前 8 位（`short(license_id)`）、`cf-ray`。

   **不得记录**注册码、完整设备摘要、IP、请求体、Access 令牌。
5. 测试：
   - 用故障注入让 DO 抛异常、D1 超时，确认返回签名的 `SERVICE_UNAVAILABLE`，并且日志字段齐全、不含敏感信息。
   - 变异测试：把一处改回裸 JSON 503，测试必须失败。

## P4　客户端记录失败的具体原因（会话 A）

现在客户端只记 `network` 或 `body`，分不清超时、连不上、服务端出错还是验签失败。

1. `license_renew`（以及激活）失败事件增加以下字段，**不记录注册码和完整设备摘要**：
   - `kind`：activate 或 renew。
   - `failure`：取值为 `timeout`、`dns`、`connect`、`tls`、`http_status`、`unsigned_error`、`bad_signature`、`parse`。
   - `http_status`：有就记。
   - `server_error`：未签名 JSON 里的 `error` 值，只允许协议错误码列表中的值，其他记为 `other`。
   - `elapsed_ms`、`cf_ray`（响应头中有就记）。
2. 这些字段在诊断导出中可见；本地前端收到的错误消息不变。

## P5　激活更耐慢，修复 NETWORK_LOCKED→ACTIVE 窗口不恢复（会话 A）

1. **激活自动重试一次**：
   - 用户点"激活"后，如果遇到超时、连接失败、5xx、未签名错误或签名的 `SERVICE_UNAVAILABLE`，自动用**新的签名请求**重试一次。两次请求总时长上限 20 秒。
   - 期间按钮保持"正在激活…"，不中途显示错误。
   - 明确的业务错误（`INVALID_CODE`、`REVOKED`、`EXPIRED`、`RATE_LIMITED` 等）不重试。
   - 续租的退避规则（15/30/60 秒）不变。
2. **启动时先 NETWORK_LOCKED 再恢复 ACTIVE，窗口必须恢复到保存的大小**：
   - 用真实 Electron 复现：有过期的本地租约缓存，第一次续租失败，第二次成功。要求窗口从 860×580 恢复为 `window-bounds.json` 中保存的大小/位置/最大化状态；没有保存记录时用 `initialWindowBounds()`。
   - 查清 05:42 这次切换为什么算出了无效的目标尺寸（宽或高 ≤0 或缺失），以及为什么用了约 3.5 秒。修复根因，不要只放宽诊断校验。
   - 增加保护：切到 ACTIVE 后，如果实际内容区小于 780×600（正常模式的最小尺寸），就按保存的大小重设一次，再不行用 `initialWindowBounds()`，并在诊断里记录 `fallback_used`。
   - 诊断记录被校验拒绝时，不要整条丢掉：改为记录一条 `license_window_state_invalid`，写出哪个字段无效（字段名和原始数值类型，不写其他内容），方便下次定位。
3. **覆盖安装测试**：模拟用 R242 包覆盖安装到已有 R240 包的数据目录（保留 `window-bounds.json` 和授权缓存），启动后按上述两种情况各测一次：续租立即成功，以及第一次失败、第二次成功。
4. 测试与变异：
   - 纯模块测试和真实 Electron 测试覆盖上面三条。
   - 变异 a：去掉 ACTIVE 后的最小尺寸保护，复现用例必须失败。
   - 变异 b：去掉激活自动重试，"第一次超时、第二次成功"用例必须失败。
   - 两项都必须是断言失败，不能是编译错误。
