# WORKLIST-R86-ADDENDUM 验收追加工单

本工单来自对 `docs/r86-execution-ledger.md`（R86 执行账本）的独立验收。验收方式：六路并行核实全部 34 条 P0/P1/P2 声明，
每路要求做真实的独立变异（改代码/参数、跑测试确认变红、再还原），不只读代码、不采信账本文字。

**结论**：34 条里 30 条完全属实，2 条是原始工单自己判断错误、被这轮执行合理修正（不需要动，见文末"无需处理"一节）。
本工单只收录**验收中发现的 4 条真实缺口**，都不是回归性的功能损坏，但都值得在下一轮补齐。

## 执行须知

1. 每条都要留护栏，且护栏必须能扛住独立变异——本轮验收专门抓出过"测试写了断言但对文件系统时序敏感、10 次里 3 次漏判"
   这种情况（就是下面 R86-ADD-2），修的时候请自己反复跑几次变异确认稳定性，不要只跑一次就认为过了。
2. 磁盘空间是这个项目沙箱环境反复出现的瓶颈（`.gocache` 会滚雪球涨到 9GB+）。如果验收时遇到
   `no space left on device`，先 `go clean -cache` 或检查 `df -h`，不要当成产品 bug 排查。
3. 本工单条目彼此独立，可以任选顺序做，也可以只做一部分。

## R86-ADD-1（原 P0-7 遗留）展开战绩后切换详情子页签，仍会触发整页重建

**背景**：R86 工单 P0-7 要求"展开/收起战绩详情"不再触发总览页 `innerHTML` 全量重建，这部分**真的修好了**
（commit `f06979c`，`entry.replaceWith(replacement)` 局部替换）。但 P0-7 原文本身有一句警告没被跟进：
`matchViewRevision` 这个字段还被三处别的交互共用，需要"逐个分流"，这部分本轮没有做。

**证据**（验收时独立写探针测试复现）：`web/gameplay.js` 里以下三处仍然是
```js
tab.matchViewRevision++; rerender();
```
的旧模式（自己 grep `matchViewRevision++` 定位这三处，行号请以当前代码为准，不要照抄旧行号）：
1. 已展开的战绩卡内部，切换详情子页签（如"概览"→"出装"）—— `bindMatchDetailControls` 相关处理器。
2. 伤害排序切换（damage-sort）。
3. 团队分析指标切换（team-analysis-metric）。

`bindMatchDetailControls(replacement, tab, rerender)` 在 P0-7 修复里传入的 `rerender` 是**通用的整页 `rerenderTab(tab)`**，
不是局部替换。验收时构造的探针：boot 200 场战绩的 demo app，展开一场，点击它的 `[data-match-detail="build"]`
（出装）子页签 → `.match-list` 的 DOM 身份变了，即整个列表被重建了——这正是 P0-7 本来要杀死的那个回归，
只是通过一个不同的入口触发。

**影响**：用户展开一场战绩看装备/时间线/团队分析，这是非常常见的真实交互路径，目前每次点子页签都要付
P0-7 报告里描述的那次代价（200 场规模下约 19,000 次 `createElement`、2.8 万节点重建）。

**改法**：把上述三处的 `rerender` 换成作用域收窄到"当前展开的这一张战绩卡"的局部渲染函数（P0-7 修复里应该已经有
一个可复用的"只重渲染某个 `.match-entry`"的函数，找到它并复用，不要重新发明一套）。`matchViewRevision` 的语义
应该收窄为"整列表可视形态变了"（筛选/排序/口径），不该被"某一张卡片内部的子标签切换"触发。

**验收判据**：boot 200 场战绩，展开一场后依次点击它的详情子页签、伤害排序、团队分析指标切换，每次操作后断言：
(a) 除目标战绩卡外，其余 `.match-entry` 的 DOM 节点身份不变（`===`）；(b) 单次操作期间 `document.createElement`
调用数 < 500。用 R86 验收时那个探针测试的思路固化成正式测试，加进 `desktop/overview-render.test.cjs`。

**风险**：低（作用域是明确的，P0-7 已经提供了参照实现）。

## R86-ADD-2（原 P1-2 遗留）championDataCache 的 hexdata 保护回归测试对文件系统时序敏感，约 30% 概率漏判

**背景**：R86 工单 P1-2 要求 `champion_cache.go` 的 `pruneDisk` 不再对每个文件 `os.ReadFile` 判断是不是 hexdata 条目，
改成从文件名就能判断，且要保留"hexdata 条目不能被当普通 LRU 淘汰"这条保护。**核心改动真的做了**（用文件名前缀判断，
不再整目录 ReadFile），性能收益是实打实的。问题出在验证这条保护的测试本身不可靠。

**证据**：验收时对现有测试（大致是 `r86_disk_test.go` 里 `TestR86ChampionDiskMigrationPruneAndThrottle` 一类，
自己在仓库里搜索确认具体名字）做独立变异——把 hexdata 判断条件改成恒为 `false`（模拟"保护逻辑被误删"这个真实回归）：
- 连续跑 10 次，**7 次正确失败**（抓到了 hexdata 文件被误删）；
- **3 次误判为 PASS**（保护逻辑明明失效了，测试却说过）。

根因是测试依赖迁移/落盘的文件相对 mtime 排序是否早于后续 200 个 fixture 文件，这个排序在并发/系统调度抖动下不稳定。

**影响**：这不是产品缺陷（生产代码的保护逻辑目前是对的），是**测试护栏本身不可靠**——如果将来有人真的不小心把
hexdata 保护判断改坏了，有 30% 概率这条测试不会报警，CI 会放行一个会导致"hexdata 授权数据被当成普通缓存条目
误删"的回归（这类数据是用户可见的恢复数据，误删的后果在项目历史记忆里已经出现过一次）。

**改法**：把测试从"依赖 mtime 排序"改成确定性断言，两种做法任选：
(a) 测试里显式设置文件的 mtime（`os.Chtimes`）而不是依赖创建顺序自然形成的 mtime；
(b) 更彻底：直接断言 `pruneDisk` 执行前后，hexdata 条目所在的路径集合完全没有被"触碰"（没有被读取、没有被删除），
   不依赖"是不是被淘汰"这种间接判据。

**验收判据**：改完后连续跑同一个变异（保护条件恒为 `false`）**20 次**，要求 20 次全部失败，不能再出现漏判。
写进测试注释里说明"这条断言不依赖文件系统 mtime 排序，是确定性的"，避免以后又退化成时序依赖。

**风险**：低（只改测试，不改生产代码）。

## R86-ADD-3（原 P1-19 遗留）韩服战绩详情信号量取消代码，现有测试证明不了它必要

**背景**：R86 工单 P1-19 要求 `riot_api.go` 里获取详情并发信号量的地方改成
`select { case semaphore<-struct{}{}: case <-ctx.Done(): return }`，这样取消请求时不会傻等信号量释放。
**这段代码本身写对了**，限速窗口的记账也正确地在"发请求前"而不是"记账后回滚"。

**证据**：验收时把这处 `select{}` 还原成旧的阻塞式写法（`semaphore <- struct{}{}`，去掉 `ctx.Done()` 分支），
重跑 `TestR86RiotOverviewCancellationStopsQueuedDetails`（以及相关的取消测试）**全部仍然通过**。
根因是取消检测实际发生在更底层的 `p.wait()`（在 `getLimited`/`p.get` 内部）里，已经提前拦截了，
外层信号量的 `select{}` 在现有测试的（即时响应 mock）场景下从未真正被"卡在信号量满、同时取消"这个组合状态触发过。

**影响**：不是功能 bug——代码目前的行为是正确的。但这意味着如果将来有人不小心把这段 `select{}`
"简化"回阻塞写法（比如重构时手滑、或者代码审查时觉得这行看着多余），**没有任何测试会报警**。
这段代码防的场景是"信号量已满、且正在等待的是一个响应很慢的真实 HTTP 请求时用户取消"，现有 mock
请求都是立即返回的，永远制造不出这种竞争。

**改法**：补一个能真正制造"信号量已满+慢响应+取消"这个组合状态的测试：用一个可控延迟（比如几十到上百毫秒
不返回）的假上游把并发信号量占满，在有请求排队等待信号量时触发 ctx 取消，断言排队中的请求确实提前退出
（而不是傻等信号量释放），且没有对已经拿到信号量正在跑的请求造成影响。

**验收判据**：新测试要满足两个条件才算数：(a) 把 `select{}` 还原成阻塞写法时，新测试必须变红；
(b) 当前正确实现下，新测试必须为绿。这是"变异测试的意义"——写完请自己至少验证一次 (a)，不要只验证 (b)。

**风险**：低（只是补测试，不改生产代码逻辑）。

## R86-ADD-4（原 P2-3 遗留）一处已确认的死 CSS 类没有被实际删除

**背景**：R86 工单 P2-3 要求清理死 CSS，执行时生成了一份自己的交叉核对结果 `docs/r86/css-crosscheck.json`，
用来判断哪些类名是真死代码、哪些是被动态拼接引用而静态 grep 找不到的假阳性。绝大部分清理都做对了
（`.resource-section`、`.augment-podium`、`.pro-table-hint` 等一批确认死亡的类都真的被删了）。

**证据**：`web/champions.css` 里 `.arena-synergy-panel`（在一条复合选择器里，和
`.champion-list-card, .augment-directory, .arena-synergy-panel, .recommendation-section` 写在一起）
仍然存在。而这个类名**本身就在 GPT 自己生成的 `docs/r86/css-crosscheck.json` 的 `missingLiteral`
（无字面量引用候选）数组里**——也就是说执行方自己的审计工具已经标出了它，只是最后清理时漏掉了。
全仓 `grep -rn "arena-synergy-panel" web/*.js index.html` 零命中确认它确实是死的（真正在用的是名字很接近但不同的
`arena-synergy-section`，`web/champions.js` 里 `renderArenaItemSection` 系列函数动态拼出来的）。

**影响**：纯 cosmetic，零功能影响，只是仓库里多留了一行没用的 CSS 选择器。

**改法**：把 `.arena-synergy-panel` 从那条复合选择器里删掉（如果删完这条选择器只剩它一个类名单独存在，
就整条规则删除；如果和其他仍在用的类名共享同一条规则体，只删掉这一个类名，保留规则和其余类名）。

**验收判据**：删除后 `node --test web/champions.test.cjs` 全绿（现有 233 个用例不依赖这个类名，用来确认没有
误伤）；`grep -rn "arena-synergy-panel" web/ index.html` 全仓零命中。

**风险**：低（单个选择器删除，且已经过独立核实确认零引用）。

## 无需处理（供参考，不是待办）

以下两处是本轮验收顺带确认"原始工单判断有误、这轮执行方做了正确修正"的案例，**不需要任何改动**，
记录在这里只是防止以后有人照着旧工单文字把它们"纠正"回错误状态：

- **原 P2-4**（build-windows.ps1）：原工单认为这个脚本没人引用可以删，实际 `desktop/source-fingerprint.cjs`
  和 `desktop/release-quality-gates.test.cjs` 都依赖它存在（前者做内容哈希、后者是回归测试）。
  当前处理方式（改成明确报错的 stub 而非删除）是对的，不要改回"删除"。
- **原 P1-13(a)**（`.cs-dialog` 的 zoom 处理）：原工单认为 `.cs-dialog` 应该像 `.skin-dialog` 那样补
  `zoom: var(--ui-zoom, 1)`。实际 `.cs-dialog` 是挂载在 `#app-frame` 内部的普通后代元素（不是 body 级
  `showModal` 弹窗），本身已经继承 `.app-frame` 的 zoom，再补一个 zoom 属性会导致双重缩放。
  这轮验收用真实 Chromium 复现过：套用原工单方案会让对话框在 1000px 高的视口里渲染到 1872px 高、
  顶部溢出到 -436px。当前的 `zoom: 1`（显式钉死）+ 尺寸除法处理是正确的，**千万不要"纠正"回工单原方案**。
  **唯一遗憾**：这个正确修复目前没有任何自动化回归测试保护，如果你顺手能补一个（真 Chromium 或至少
  jsdom 层面断言 `.cs-dialog` 的 computed zoom 值恒为 1、不随 `--ui-zoom` 变化），会更安全，但不强制要求。
