# R116-探测：LCU 海克斯选择端点穷举 + 海斗局内数据形状实测

**目标：**
1. 一次性回答「LCU 客户端是否存在任何暴露海克斯三选一候选项的端点」，为 P1-1（海克斯三选一实时排序）的去留提供真实依据。
2. 一次性回答「海斗（KIWI/ARAM_MAYHEM）模式下 `/liveclientdata/playerlist` 是否带装备字段、选人阶段能否看到对方阵容」，为 P1-4（下一步出装建议）与 P1-2/P1-3（ChampSelect 阶段的协同/克制）提供前置判据。

**背景：** `docs/r116-proposal-feasibility-review.md` 第 3 节证伪了方案对局内实时上下文的三条核心假设（已选海克斯/当前阶段/三选一候选局中均拿不到）。用户裁决：不直接删除 P1-1，先花一次很小的成本探测，再决定去留（2026-09-20）。本工单只做只读探测和诊断埋点微调，**不实现任何新产品功能**，不产出用户可见改动。

**版本：** 基线 0.12.7。本工单不改变版本号（无产品功能交付），探测结果写入 `docs/r116-probe-findings.md`。

## P0：LCU 端点穷举（不需要在对局中执行，任意登录客户端即可）

### 现状证据

- `backend/objective_diagnostics.go:373` 已经实现了拉取 `/swagger/v3/openapi.json`（16 MiB 上限，`:377-380`）并用 `objectiveContracts`（`:279-332`）提取 operations 的完整能力。
- 但 `objectiveContracts` 的路径过滤走的是 `objectiveDiagnosticPath`（`:70-90`），该函数**硬编码只认 `/lol-missions/v1/`、`/lol-notifications/v1/`、`/lol-event-hub/v1/` 三个前缀**（`:75`），用于「任务/通知徽章」这个不相关的既有功能。
- 全仓 `grep -n "cherry\|mayhem\|augment" backend/*.go` 与 LCU 路径字面量清单核实过：`/lol-cherry*`、`/lol-mayhem*`、`/lol-augment*` 命名空间从未出现在代码里（因为我们也从未请求过，仓库里没有就不代表客户端没有——这正是本节要探测的事）。

### 实现要求

1. **不要修改 `objectiveDiagnosticPath`**（它是任务徽章功能的既有护栏，扩大它的匹配范围会让任务徽章诊断意外收进海克斯相关字段，属于超范围改动）。
2. 新增一个独立的、一次性的探测函数（建议命名 `augmentContractProbe`，放在新文件 `backend/augment_contract_probe.go`），复用 `objectiveContractSchema`（`objective_diagnostics.go` 内既有）与 LCU client 的 `getBytes`，但用新的路径过滤谓词：
   ```go
   var augmentProbePath = regexp.MustCompile(`(?i)cherry|augment|mayhem`)
   ```
   对 `/swagger/v3/openapi.json`（16 MiB 上限）的 `paths` 做全量扫描（不再限定 `/lol-missions/` 等前缀），把匹配到的 path + method + parameters 汇总成一份诊断事件 `augment_contract_probe`（字段与 `objective_badge_contracts` 同构：`path`/`method`/`parameters`/`body`）。
3. 通过一个仅本机可触发的临时入口调用它（可参考 `collectObjectiveDiagnostics` 的触发方式，即诊断导出面板里加一个临时按钮，或复用现有"导出诊断日志"入口时附带调用一次）。**该入口与新文件在探测完成、结论落盘后必须整体删除**，不进入正式版本——这是一次性侦察代码，不是产品功能。
4. 打开 League 客户端（登录状态，不需要在对局中，不需要在海斗模式），触发探测，导出诊断日志。

### 验证判据

1. `augment_contract_probe` 事件里的 `count` 字段：
   - `count == 0` → **确证**客户端 openapi 契约里没有任何海克斯/斗魂相关端点。这是比"猜六轮"更权威的否定证据（openapi.json 是客户端自陈的完整契约，不依赖某次网络包被恰好捕获）。
   - `count > 0` → 逐条检查 `path`：是否存在类似 `/lol-cherry/*` 或包含 "augment"/"pick" 的 GET 端点。如果有，记录到 `docs/r116-probe-findings.md` 并**新开工单**评估其可用性（不在本工单范围内实现）。
2. 探测代码编译通过、有单测覆盖 `augmentProbePath` 的匹配/不匹配用例，且**不影响** `objective_diagnostics.go` 既有测试（跑一遍 `go test ./backend -run Objective`）。

### 对抗变异

- 故意在测试 fixture 的 openapi.json 里加入一个 `/lol-cherry-augments/v1/select` 路径，确认探测函数能命中并进入 `count`；再故意把它删掉，确认 `count` 归零——证明探测本身不是死代码。

## P1：海斗局内数据形状实测（需要真机 + 一局海斗对局）

### 现状证据

- `live_client_playerlist_shape`（既有诊断，`gameplay.go:6081` `finalizeLiveClientPlayerListShape`）**无条件对所有模式记录**，不需要改代码。R90 在**斗魂（CHERRY）**下实测出的 19 个 `element_keys` 恒定包含 `items`，但**海斗（KIWI）下这个事件从未被观测过**。
- `lcu_champ_select_session_shape`（`gameplay.go:4975-4984` `recordLCUChampSelectSessionShape`）**无条件对所有模式记录**，不需要改代码。仓库里现存的 `their_team_length` 观测全部来自测试 fixture（恒为 `[]`），**没有一条真实海斗/大乱斗对局的观测**。
- `live_client_allgamedata_shape`（`arena_truth_diagnostics.go:256-306` `liveClientAllGameDataShape` + `sampleArenaAllGameData`）**函数本身与模式无关**（只用 `gameID` 做去重键，`arenaShapeKey` 白名单不含任何模式限定），但触发点 `gameplay.go:6087` 的条件是 `arenaMode && (phase == "GameStart" || "InProgress" || "Reconnect")`（`arenaMode := isArenaChampSelectMode(response.GameMode)`，`:5943`），**海斗（`aramMode`）不满足这个条件，从未被调用过**。

### 实现要求

1. **唯一需要的代码改动**：在 `gameplay.go:6087` 旁新增一个海斗专用触发分支，不修改现有 arena 分支：
   ```go
   if arenaMode && (phase == "GameStart" || phase == "InProgress" || phase == "Reconnect") {
       // ...既有斗魂逻辑，不动...
       go a.sampleArenaAllGameData(ctx, response.GameID)
   }
   if aramMode && !arenaMode && (phase == "GameStart" || phase == "InProgress" || phase == "Reconnect") {
       go a.sampleArenaAllGameData(ctx, response.GameID)
   }
   ```
   `aramMode := isARAMFamilyGameMode(response.GameMode)` 已在 `:5944` 声明，直接复用。`sampleArenaAllGameData` 函数本身按 `gameID` 去重（`arena_truth_diagnostics.go:308`），海斗与斗魂各自的 `gameID` 不会互相冲突。
2. 打一局海斗（KIWI/ARAM_MAYHEM 任一子模式），完整走完 ChampSelect → InProgress，正常结束。
3. 导出诊断日志，读取以下三个事件：
   - `live_client_playerlist_shape.element_keys`（海斗场次）
   - `lcu_champ_select_session_shape.their_team_length` / `their_team_nonzero_counts`（海斗 ChampSelect 场次）
   - `live_client_allgamedata_shape.top_level_keys`（海斗场次，本工单新增触发后才会出现）
4. **探测完成、结论落盘后，评估是否保留 `aramMode` 分支**：若 P1-4/P1-2/P1-3 判定要做，这一行可以保留作为正式埋点的一部分（不算超范围，因为它只是把现有诊断能力扩大到海斗模式，没有新增用户可见功能）；若判定不做，删除即可，回退成本为一行代码。

### 验证判据

1. **`live_client_playerlist_shape.element_keys`**：
   - 若含 `items` 且元素结构与斗魂一致（`itemID`/`slot`/`count` 等） → P1-4「下一步出装」判定为**可行**，转入 R116-D 正式实现。
   - 若不含 `items` 或结构不同 → P1-4 判定为**不可行**，从 R116-D 移除，记录到 `docs/r116-probe-findings.md`。
   - 若出现 `<unknown-key>`（`arenaShapeKey` 的兜底分支，`arena_truth_diagnostics.go:249-254`）→ 说明海斗有斗魂没有的字段，需要人工判读该字段是否与本方案相关。
2. **`lcu_champ_select_session_shape.their_team_length`**：
   - `> 0` → P1-2/P1-3 可以扩展到 ChampSelect 阶段。
   - `== 0` → P1-2/P1-3 只在 InProgress 阶段出现（与本次评审的保守判定一致，不算回退）。
3. **`live_client_allgamedata_shape.top_level_keys`**：主要用于交叉核实，不阻塞任何功能判定；若发现明显与海克斯相关的字段（如 `augment`/`cherry` 字样），记录并升级为独立调研项。

### 对抗变异

- 故意把 `aramMode` 判断写反（`!aramMode`），确认海斗对局不会触发 `sampleArenaAllGameData`，证明新分支确实是新增触发点而非巧合命中既有逻辑。
