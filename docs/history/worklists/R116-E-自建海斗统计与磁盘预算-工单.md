# R116-E：自建海斗个人统计（含新建磁盘预算 + 海克斯→出装静态联动）

**目标：**
1. 放开 `season_stats.go` 的队列过滤，允许海斗（2300/2400/3270）计入个人赛季统计（仍只统计当前登录账号本人）。
2. **新建**一套 season-stats 磁盘预算——不是"复核 `binary_disk_budget.go`"，那套治理的是图片缓存的 `strictDisk`，与本目录无关，season-stats 目录当前完全没有任何大小上限。
3. P2-6：海克斯→阶段→出装联动，做成英雄详情页的**静态查询**（"选了 X 之后通常出什么"），不是局内实时联动（局内实时形态已被证伪，见 R116-探测/R116-D）。

**背景：** `docs/r116-proposal-feasibility-review.md` 第 5 节：放开队列过滤本身代价很小（`GameIDs` 早已全队列记录，只是 `Stats`/`RankedMatches` 没算海斗），真正的成本在"新增 augment 维度字段"要求的额外存储，且这个文件每次前台扫描都要整文件重写。用户裁决：纳入本轮规划（沿用方案原决策 3，2026-09-20 会话确认不变）。

**版本：** 完成后升到 0.12.11。

## P0：放开队列过滤（低风险）

### 现状证据
- `seasonStatsAccumulate`（`season_stats.go:167`）：`if info == nil || (info.QueueID != 420 && info.QueueID != 440) { return }`。
- `seasonRecordRankedMatch`（`season_stats.go:211`）：同样的双队列硬过滤。
- `GameIDs` 的 append（`season_stats.go:654`）**在过滤之前**，海斗场次的 `gameId` 早就被记进去了，只是不出现在 `Stats`/`QueueStats`/`RankedMatches` 里。
- `queue_groups.go:120-124`：海斗对应 2300/2400/3270。

### 实现要求
1. `seasonStatsAccumulate` 与 `seasonRecordRankedMatch` 的过滤条件从"只认 420/440"改为"420/440/2300/2400/3270"，改动前先确认这两处的判据**保持同步**（现有注释已经写明"判据必须一致，否则近 20 场排位和赛季英雄统计会对不上账"——这条约束对新增的三个队列同样适用）。
2. `seasonStatsCacheSchemaVersion` 从 7 升到 8（协议已注释"不同来源的对局结构和统计口径不能共用缓存"，新增队列属于口径变化，必须升版本号强制旧缓存失效重新扫描）。
3. 隐私声明文案同步：检查产品文档/设置页里关于"统计范围"的描述，确认新增队列后文案与实际行为一致（这是项目红线：声明要和实际写操作一致）。

### 验证判据
- 用一条海斗对局的 fixture 跑 `seasonStatsAccumulate`，验证 `Stats`/`QueueStats` 正确记入；用一条 420 对局验证行为不变（回归）。
- 升版本号后，旧 schema=7 的缓存文件读取时应触发重新扫描而不是直接复用（用测试断言 `seasonStatsCacheSchemaVersion` 不匹配时的既有失效逻辑正确触发）。

## P1：新建 season-stats 磁盘预算

### 现状证据
- `season_stats.go:22-28` 的页数上限注释写"每页 20 场"，但实际 `matchHistoryOn` 走的是 `sgpPageSize = 50`（`sgp_api.go:77`），同时存在向 `sgpFallbackPageSize = 20`（`:78`）降级的路径（`matchHistoryFilteredOn`，`sgp_api.go:841-947` 里 `pageSize` 会在缓存命中 20 场时收窄到 20）。**真实单页大小在 20~50 之间波动，不是固定 20**，前台 2 页覆盖 40~100 场、后台 12 页覆盖 240~600 场，取决于走的是首次请求还是缓存回退路径。工单执行时按这个区间估算容量，不要用错误的"20 场/页"死算。
- `saveSeasonStats`（`season_stats.go:155-164`）→ `writeLocalStoreFile`（`storage.go:161-170`）→ `atomicWriteFile`（`:172` 起）：**全流程没有任何大小/条目上限检查**，`season-stats` 目录本身也没有被任何 prune 逻辑扫描过。
- 对照：`binary_disk_budget.go` 治理的是图片缓存 `championDataCache.strictDisk`（只被 `champion_images.go:19-21` 的 `newPublicBinaryCache` 打开），与 season-stats 完全是两套不同的存储（一个是二进制图片缓存，一个是 JSON 统计快照），**不能"复核"一套不管辖这里的预算，必须新建**。

### 实现要求
1. 新增一个轻量级预算检查，**不需要照搬 `binary_disk_budget.go` 的复杂度**（那套是为图片这种高频写入设计的严格记账，season-stats 是低频的整文件重写，量级小很多），只需要：
   - 单文件大小上限（建议 4 MiB，留出充足余量：不放开海斗时约 60-70 KB，放开后估算见 P2 小节）。
   - 超限时的处置：截断 `RankedMatches`（保留最新的 `seasonRankedMatchLimit` 条即可，本来就有这个上限）优先，而不是整体拒绝写入或丢弃 `Stats`。
   - 一次性的目录级健康检查（应用启动或首次扫描时跑一次，记录 `season-stats/` 目录总大小到诊断事件，不需要做成实时监控）。
2. 该预算独立于 `binary_disk_budget.go`，可以放在 `season_stats.go` 内部或新文件 `season_stats_budget.go`。

### 验证判据
- 构造一个人为超过 4 MiB 的 `seasonStatsCache`，验证写入前会先截断 `RankedMatches` 到上限，而不是写入失败或 panic。
- 目录健康检查诊断事件能正确报出总大小（用临时目录构造几个文件验证）。

## P2：放开队列过滤后的容量估算（供实现时对照，不是需要额外实现的功能）

放开后单文件构成变化（以一季 2000 场海斗的高频玩家估算）：

| 组成 | 变化 | 算式 |
|---|---|---|
| `GameIDs` | 不变 | 已经全队列记录 |
| `Stats` | 不变 | 按 championID 聚合，上限 173 条 |
| `QueueStats` | +3 条 | +0.3 KB |
| `RankedMatches` | +3 队列 × 40 条 × ~450 B | +54 KB（前提：P0 已经把 `seasonRecordRankedMatch` 的过滤一起放开） |
| **小计** | | 约 60 KB → 120 KB，翻一倍 |

**这一层代价很小**，真正要小心的是决策 3 附带的"新增 augment 维度字段"（见 P3），那才是需要磁盘预算保护的部分。

这条链路走 SGP（`sgp_api.go:621-739` 用 LCU 的 entitlements token 打腾讯 SGP），**不调用 `enterRiotLimitQueue`，不吃 Riot 的 90/2min 配额**，不需要在这里重复设计限流。

## P3：新增 augment/装备维度字段（供 P2-6 使用）

### 现状证据
- `gameplay.go:599-604`（LCU 赛后战绩）与 `riot_api.go:633-638`（SGP/Riot match-v5 participant）都已经有 `PlayerAugment1..6`/`Item0..6`/`GoldEarned`/`TotalDamageDealtToChampions`/`TotalDamageTaken`/`GameDuration` 字段，赛季扫描本来就要解出这些 JSON，加几个字段是零额外网络请求（与 `seasonRankedMatch.Ability` 字段"顺手记"的既有模式一致）。
- 按 22 项 postmatch 全量存：约 1 KB/场 × 2000 场 = 2.0 MB；只存 augment+item 精简字段：约 300 B/场 × 2000 场 = 0.6 MB。

### 实现要求
1. 新增 `seasonAugmentSample` 结构（参考 `seasonRankedMatch.Ability` 的"顺手记"模式），只存**必要字段**：`GameID`/`ChampionID`/`AugmentIDs[6]`/`ItemIDs[7]`/`Win`（**不存 22 项 postmatch 全量**，那是英雄级统计，个人样本不需要；本条走「精简 0.6 MB」路线，不是「全量 2.0 MB」路线）。
2. 只在海斗队列（2300/2400/3270）记录，经典排位（420/440）不需要这个字段。
3. 这份数据只用于 P2-6 的"选了 X 之后通常出什么"静态查询（对本人历史海斗对局按 augment 分组统计出装频率），**不做成局内实时联动**——局内联动的三个输入（已选海克斯/当前阶段/系统候选）已在 R116-探测/R116-D 判定为不可行或需要额外前置条件。

### 验证判据
- 放开后单文件大小实测控制在 P1 的 4 MiB 上限之内（用 2000 场海斗的合成 fixture 验证）。
- P2-6 的静态查询：给定一个 augment ID，能从本人历史样本里聚合出「选了它之后最常出的装备组合 + 场次 + 胜率」，样本不足（< 一个可配置阈值，建议复用 `hexdataMinimumSample` 类似的量级但按个人样本调低，比如 10 场）时整块不显示。

## 明确不做（Anti-scope）

1. **不做局内实时的海克斯→出装联动**（P2-6 是静态查询，不是局内推荐；局内形态已被 R116-探测/审查证伪）。
2. **不恢复 ARAMKit `/rating` 里被主动丢弃的 `participants[]`**（`aramkit_rating.go:353-359`）——那是第三方估算的他人身份数据，丢弃是刻意设计，与本工单无关，不得借机复活。
3. **不把 season-stats 的预算逻辑塞进 `binary_disk_budget.go`**——两套存储性质不同，混在一起会增加不必要的耦合。
4. **不存 22 项 postmatch 全量到个人样本**——个人样本只需要 augment/item/胜负，指标级数据走英雄级的 `/api/hexdata/postmatch`（R116-A），不要在个人对局记录里重复存一份。
