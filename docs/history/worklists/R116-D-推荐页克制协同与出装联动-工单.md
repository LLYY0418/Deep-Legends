**目标：**
1. P1-2/P1-3：阵容协同分 / 克制风险提示，改成「命中才出现」的低调形态，**只拉本人英雄的 `hero-json` 一次**，不对 10 个英雄各拉一次。
2. P1-4：局内已出装备 → 下一步出装建议，**前置条件是 R116-探测确认海斗 `playerlist.items` 形状可用**，本工单先做诊断解析（不影响用户可见功能），再按探测结果决定是否放开渲染。
3. P1-5：队伍画像缺口提示（我方 5 人的 `postmatch` 指标聚合），纯静态数据拼装，不依赖任何局内实时上下文。

**背景：** `docs/r116-proposal-feasibility-review.md` 第 3.1/4.3 节：`weakAgainst`/`strongAgainst`/`teammateSynergies` 实测每个英雄各只有 **7 条**（显著性筛选后的结果，不是被截断），按 172 英雄算，克制提示单局命中率 34.6%，协同分 18.8%。**且这三个数组全部来自"本人英雄"这一次 `hero-json` 请求**——`weakAgainst`/`strongAgainst` 本来就是"该英雄 vs 全体对手"的完整表，不需要对 10 个英雄分别拉。用户裁决：这一轮做，但改成低调的「命中才出现」形态，不做固定卡片、不算总分（2026-09-20）。

**依赖：** R116-A（`hero-json`/`postmatch` 数据源）；P1-4 部分依赖 R116-探测的结论。

**版本：** 完成后升到 0.12.10。

## P1-2 + P1-3：克制风险提示 / 阵容协同分（低调形态）

### 现状证据
- 实测 `weakAgainst`（谁克我）、`strongAgainst`（我克谁）、`teammateSynergies`（我与队友的协同）各 **7 条/英雄**，全部 `evidence: "supported"`、`qValue: 0`（通过多重比较校正的显著项）。
- 覆盖率测算：`weakAgainst+strongAgainst` 合计 14 条，对 5 个敌方目标至少命中 1 条的概率 34.6%；`teammateSynergies` 7 条对 4 个队友至少命中 1 条的概率 18.8%。
- 数据全部来自**本人英雄**的单次 `hero-json` 请求（R116-A 已经在推荐路径上拉过一次，不需要新增请求）。对面/队友是否在这 7 条名单里，只需要拿到 10 人的 `championId` 做集合比对，`gameplay.go:5833-5847`（InProgress/Reconnect）与 `gameplay.go:6660-6724`（ChampSelect 我方）已经能拿到。

### 实现要求
1. `gameplayRecommendationBundle` 新增 `MatchupNotices []gameplayMatchupNotice` 与 `SynergyNotices []gameplaySynergyNotice`（各自最多 5 条，按 `|counterDelta|`/`synergyDelta` 绝对值排序）：
   ```go
   type gameplayMatchupNotice struct {
       Direction    string  `json:"direction"` // "weak" | "strong"
       OpponentID   int     `json:"opponentChampionId"`
       CounterDelta float64 `json:"counterDelta"`
       Evidence     string  `json:"evidence"`
       ConfidenceLow, ConfidenceHigh float64 `json:"confidenceLow,confidenceHigh"`
   }
   type gameplaySynergyNotice struct {
       TeammateID   int     `json:"teammateChampionId"`
       SynergyDelta float64 `json:"synergyDelta"`
       Evidence     string  `json:"evidence"`
       ConfidenceLow, ConfidenceHigh float64 `json:"confidenceLow,confidenceHigh"`
   }
   ```
2. 计算逻辑：拿本人 `hero-json` 的 `weakAgainst`/`strongAgainst`/`teammateSynergies`，与 InProgress/Reconnect 阶段的 10 人 `championId`（或 ChampSelect 阶段的我方 5 人 `championId`，取决于阶段）做交集，命中才生成对应 notice。
3. **必须透传 `evidence`/`confidenceLow`/`confidenceHigh`**（第 6.5 条硬性要求：证据不足要明确降级；本数据全部 `evidence:"supported"`，但字段要留着，万一上游未来放宽阈值出现非显著项，前端也能正确处理）。
4. 前端渲染：**没有命中就不渲染任何 DOM 节点**（不显示"暂无数据"的占位卡片），符合"拿不到就整块隐藏"的既有约定。有命中时以行内小条形式插在详情 tab 里（不做成固定卡片、不做成"阵容协同 +X%"总分——覆盖率撑不起总分这个语义）。
5. **ChampSelect 阶段的克制/协同展示需要先看 R116-探测的 `their_team_length` 结论**：若探测证实海斗 ChampSelect 拿不到对方阵容，则 P1-3（克制）在 ChampSelect 阶段只展示"我方 vs 已知信息"，不展示"对面 5 人"部分；P1-2（协同）本身只需要我方，不受影响。

### 验证判据
1. 构造一个「本人英雄的 weakAgainst 里有一条 opponentChampionId 命中当前对局某个敌方英雄」的 fixture，验证生成且仅生成 1 条 `MatchupNotice`。
2. 构造一个「7 条 weakAgainst 均未命中当前 10 人」的 fixture，验证 `MatchupNotices` 为空**且前端不渲染任何相关 DOM**。
3. 请求计数：整个对局页一次刷新，hexdata 相关请求数不因为加了这两项而增加（复用本人英雄已经在拉的 `hero-json`，不新增 per-entity 请求）——用集成测试断言请求数不变。

### 对抗变异
- 故意把交集判断写反（比较 `teammateID` 而不是 `championId`），构造出全零匹配的场景，确认测试能检测到"永远不命中"这种隐蔽退化。

## P1-4：局内已出装备 → 下一步出装建议（前置条件：R116-探测确认可行）

### 现状证据
- `parseLiveClientPlayerList`（`gameplay.go:4557-4666`）目前只读 `position`、身份键、含 `subteam` 字样的键，**从未读取 `items`**，尽管该字段在 R90 的实测里恒定存在于 `/liveclientdata/playerlist` 响应（斗魂模式下）。海斗模式下这个字段是否存在、结构是否一致，**未经实测，需要 R116-探测先给出结论**。
- `terminalItemTrios`（R116-A 接入，裁剪到 top-50/英雄）自带 `itemIds[3]`/`winRate`/`deltaWinRate`/`games`，可以按"已出 2 件"匹配前缀推第 3 件。

### 实现要求（分两阶段，第一阶段不依赖探测结果，第二阶段依赖）

**阶段一（可以立即做，只是诊断，不影响用户）：**
1. 在 `parseLiveClientPlayerList` 里新增解析：读取每个 entry 的 `items` 字段（结构预期为 `[{itemID, slot, count, canUse, consumable}]`），存入 `liveClientSnapshot.ItemsByIdentity map[string][]liveClientItem`，用与 `PositionByIdentity` 相同的身份匹配方式（`liveClientEntryIdentityKeys`）。
2. 新增一条诊断事件 `live_client_items_parsed`，记录本人（self）识别到的 `items` 长度与 `itemID` 集合，**不在生产 UI 上展示任何内容**——这一步只是把解析能力打开，用真实对局验证解析是否正确。

**阶段二（依赖 R116-探测的 `live_client_playerlist_shape` 结论为"可用"）：**
3. 用本人当前 `items`（`itemID` 集合，滤掉消耗品/未成型的空槏）与本人英雄的 `terminalItemTrios` 做前缀匹配（已出 2 件且这 2 件恰好是某个 trio 的前两件时），推荐第 3 件，带 `winRate`/`games`。
4. 渲染在 `renderBuildRecommendation`（`gameplay.js:5650-5710`）里，作为"下一件推荐"的补充行，不替换现有的静态核心装路线。
5. **降级规则**：`items` 解析失败、海斗字段结构与预期不符、或没有任何 trio 前缀匹配时，这一行**整体不渲染**。

### 验证判据
1. 阶段一：用真机导出的海斗诊断日志核对 `live_client_items_parsed` 事件出现且 `itemID` 集合非空（如果 R116-探测已经做过这一步，直接引用其结论，不用重复打真机）。
2. 阶段二（仅在探测结论为"可行"时要求）：构造"本人已出 A+B 两件，trio 表里有一条 A:B:C"的 fixture，验证推荐出现 C 且带正确的 winRate/games。
3. 20 秒的局内轮询周期足够覆盖这个计算（纯本地数据比对，不发新请求，不存在超时风险）。

### 对抗变异
- 若阶段二判定为不可行（探测结果否定），本工单只交付阶段一的诊断解析，**不强行实现阶段二**——验收时以 R116-探测的结论文档为准，不接受"猜测字段结构强行实现"的交付。
