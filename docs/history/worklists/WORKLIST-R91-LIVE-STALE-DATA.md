# WORKLIST-R91 — 新局开始后页面残留上一局数据

诊断日期：2026-09-14
来源：用户反馈「对局响应慢的问题彻底解决了吗，新对局开始后没有反应页面还是空的，要不就是还遗留着上个对局的推荐，刷新也没用，重新获取才行」。逐条核查代码后确认这是三个不同状态混在一起，本工单只处理**已明确坐实、之前几轮从未测过**的那一条。

---

## 现状澄清（供理解背景，不是本工单要改的东西）

- **诊断请求风暴已经砍掉**（`web/runtime.js:128` 对 `live_refresh_client` 做了1秒节流，`local_request_client` 10秒节流），**但"连接槽位被挤占导致8秒超时"这个根因本身从没在真机上证实过**，只是机制推测。这轮复核也没找到任何真正扩容连接数或缩短 LCU 请求延迟的改动。这不是本工单要解决的问题——沙箱做不了真机验证，需要用户实际体感反馈。
- **刷新按钮与"重新获取"没有代码差异**（全部走 `force=true`，都会穿透缓存），不存在"一个假一个真"的问题。用户感觉两者不等价，本质是下面这条 bug 的另一种表现。

---

## 唯一要修的真实问题：新局开始后，页面会残留渲染上一局的数据

### 已证实（file:line，本轮独立复核过）

`web/gameplay.js:3747-3768 loadLive(force, source)`：
```js
async function loadLive(force = false, source = "direct") {
  ...
  state.liveLoading = true;
  state.liveError = "";
  renderLive();
  try {
    const previousLive = state.live;
    const nextLive = await api(force ? "/api/gameplay/live?refresh=1" : "/api/gameplay/live", ...);
    ...
    state.live = nextLive;   // ← 只有请求成功返回后才覆盖
```
**请求发起时（3747-3757行）不清空 `state.live`**，只置 `state.liveLoading = true`。

`web/gameplay.js:4298 renderLive()`：
```js
if (state.liveLoading && !state.live) {
  nodes.liveContent.innerHTML = '<div class="gameplay-skeleton">...</div>';
  return;
}
const data = state.live;   // 4308行，否则直接用旧对象渲染
```
骨架屏**只在 `state.live` 完全为空时**才显示（比如应用刚启动、还没加载过任何对局）。

### 后果

只要上一局曾经有过数据，`state.live` 就不是空对象。新一局的 gameflow phase 进入 ChampSelect/InProgress 后触发 `loadLive`，在新数据从后端返回之前的这段空窗期里（可能是几百毫秒，也可能因为连接慢拖到几秒甚至更久——见上面"响应慢"那条未证实的推测），页面会**原样把 `state.live` 当作"当前数据"继续渲染**，也就是**完整展示上一局的所有推荐内容**（英雄推荐、符文、出装等），不会有任何"正在加载"的提示。

- 如果用户在这段空窗期内看到的就是这坨旧数据 → 用户描述的「还遗留着上个对局的推荐」。
- 如果这段空窗期恰好卡在某次请求失败/取消导致 `state.live` 后续被清空的边缘状态（本轮未深入核实这条分支是否存在，需要执行方一并核查）→ 可能是用户描述的「页面还是空的」。

**后端侧没有问题**：`gameplay_refresh.go` 的预热缓存在被消费前每次都会重新核对当前 gameId 与缓存里的 gameId 是否一致，不会把旧局数据发给新局。问题完全在前端这段状态管理上。

### 要做的改动

1. **在 `loadLive` 发起新请求时，判断这是否是"新的一局"，如果是就应该先失效/清空旧的 `state.live`（或至少标记为 stale），再触发渲染。** 判断"是否新的一局"可以用 gameId 变化、或 phase 从非 ChampSelect/InProgress 转为 ChampSelect/InProgress 这个跳变点。
   - 注意不要过度清空：如果只是同一局内的例行刷新（比如玩家买了装备后的推荐更新），不应该清空重建，否则会引入新的闪烁/骨架屏抖动问题。**清空的触发条件必须精确限定在"新的一局开始"，不能是任何一次 `loadLive` 调用。**
2. **渲染层加一个"数据陈旧"的视觉区分**，哪怕暂时没有新数据可显示，也不应该让用户以为自己看到的是"当前对局的推荐"。可选方案：
   - (a) phase 跳变触发后，在新数据到达前显示骨架屏/"正在识别新对局…"的过渡态；
   - (b) 或者在旧数据上叠加一层"数据可能已过期"的提示条，直到新数据确认到达。
   两种方案各有取舍（(a) 更干净但如果新数据迟迟不来会导致长时间空白，(b) 更保守但需要额外的视觉设计），具体选哪个请执行方评估后决定，工单不强制指定。
3. **顺带核查**：`state.liveError` 分支（4300-4304行左右）和请求失败/取消（`state.liveRequestToken` 不匹配那几处 `return`）之后，`state.live` 会不会一直卡在某个既不是"当前局的新数据"也不是"明确的错误态"的中间状态——这可能是用户描述的「页面还是空的」这一半症状的成因，需要一并核实并修复。
4. **点刷新时如果已有请求在飞行中，要给用户可见反馈**。`web/gameplay.js:3751` 现状：`if (state.liveLoading) { if (force) state.liveForceRefreshQueued = true; return; }`——直接静默排队、不做任何 UI 提示，点了跟没点一样。改成：按钮短暂显示"正在刷新…"或类似状态，或者禁用按钮直到本次请求结束，让用户能感知到"点击已生效，只是还在等"，而不是误以为这个按钮没用、去找别的入口。
5. **★这条是「刷新没用，重新获取才行」的真正根因，务必修——普通刷新遇到卡住的请求时只会排队等待，不会打断它。** 对比两条路径：
   - 普通"刷新"（`loadLive(true)` 撞上 `state.liveLoading===true`）：只把 `liveForceRefreshQueued=true` 后 `return`（3751行），**不 abort 当前正在进行的请求**，必须等那个请求自己完成（成功或失败）才会在 3786 行被消费、重新发起一次。如果卡住的正是这个进行中的请求本身，普通刷新就只能死等。
   - 全局"重新获取"（`handleHardRefresh` → `softResetGameplayState`，3842-3858行）：会把 `state.controllers` 里所有进行中的请求 `controller.abort()`，并把 `state.liveLoading` 强制置回 `false`，然后立刻发起新请求。这是它"总能救回来"的真正原因——不是因为它绕过了什么缓存，而是因为它敢打断卡住的请求。
   
   修法：普通刷新按钮在检测到有请求正在飞行且用户主动要求强制刷新（`force=true`）时，也应该像硬刷新一样先 abort 当前请求再重新发起，而不是排队等待。需要确认 `loadLive` 内部发起请求时用的 `fetch`/`api()` 调用是否有对应的 `AbortController` 可以拿到并中断（参考 `state.controllers` 的用法），把这个能力下沉到 `loadLive(force=true)` 自身，不必依赖用户去点另一个"硬刷新"入口才能生效。

   **★职责边界，不要做过头**：`loadLive` 内部的 `api()` 调用（`web/gameplay.js:182`）本身就会把请求的 `AbortController` 存进 `state.controllers.set("live", controller)`，而且已经有三处现成用法（`gameplay.js:414/3817/3835`）在用 `state.controllers.get("live")?.abort()` 做**只中断对局这一个请求**的局部操作。这次要照抄的是这个局部模式，**不要**去调用 `softResetGameplayState()` 或复制它里面"中断所有 controller、重置所有标签页分页状态、清空推荐子页选中"那套全局逻辑——那是硬刷新（"重新获取"）专属的职责，一旦普通刷新也做这些，两个按钮就变得功能重复，"刷新战绩"就失去了作为一个轻量、局部操作存在的意义。改动应该只做一件事：`loadLive(true)` 撞上正在飞行的请求时，`state.controllers.get("live")?.abort()` 一下，再正常走原来的请求发起流程，仅此而已。

### 验收判据

- 构造测试：`state.live` 已有上一局的完整数据 → 触发一次"新局开始"的 phase 跳变 → 在新数据到达前的这段时间里，UI 不应该渲染出上一局的推荐内容（骨架屏/过渡态/陈旧提示三选一，但不能是"看起来和上一局一模一样、毫无提示"）。
- 构造测试：同一局内的例行刷新（phase 不变）不应该触发骨架屏重建，保持现有的"原地更新"体验，不能因为这次改动引入新的闪烁。
- 构造测试：请求进行中再点一次刷新，按钮/页面必须出现可感知的"处理中"状态，不能是静默无反馈。
- 构造测试：请求进行中再点一次刷新，应立刻中断旧请求并重新发起，不能死等旧请求自然结束。
- **构造测试：普通刷新触发时，除了"live"这一个请求的 controller 被 abort，其余 `state.controllers`（总览标签页、收藏等）不应被触碰，各标签页的分页/加载状态也不应被重置。** 这条专门用来防止改动范围失控、变成和硬刷新功能重复。
- 手工/真机验证：连续打几局，切局瞬间观察页面表现，确认不再有"卡在上一局画面很久"的现象；请求进行中重复点刷新时能看到反馈且很快响应；刷新战绩与"重新获取"两个按钮在行为上依然能感觉出明显差别（前者只影响对局页，后者是全局重置）。
