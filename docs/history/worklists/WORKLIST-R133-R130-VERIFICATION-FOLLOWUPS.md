## P1　看门狗注释还停在旧数值（`backend/web/app.js`）

`loadImageSources` 里设置看门狗定时器那一段的注释仍然写着：

```
// R130 P1-A 兜底看门狗：第二层彻底放弃时靠 removeAttribute("src") 收尾，
// 而移除 src 不触发任何 load/error，onerror 上的候选回退与名额释放就永远
// 不会执行。这里保证 25s 内必定推进一次。
```

而 `CARD_IMAGE_STALL_MS` 已经在同一轮里从 25000 改成了 `45_000`（对抗评审发现 25s 早于第二层最坏放弃时间 30s，会截胡本来能显示的候选地址）。常量改对了，注释没跟着改，后面谁看代码会被这句"25s"误导。

改成"这里保证 `CARD_IMAGE_STALL_MS` 内必定推进一次"或者直接写"45s"，不要在注释里再放一个和常量脱节的具体数字。顺手检查一下同一段代码里还有没有别处提到旧的 25s（比如同函数上方紧邻的另一条注释也提到过"25s 内推进一次"，两处都要改）。

验收：`grep -n "25s" backend/web/app.js` 在这一段不再有命中；`CARD_IMAGE_STALL_MS` 的实际值和注释里写的数字一致。这条不需要新增测试，改完读一遍确认即可。

## P2　R130 工单验收总表要求的真机手动验证，两轮都还没做

R130 的验收总表原文：

> 手动验证：在皮肤列表来回快速拖动滚动条、悬停十几张动态原画卡、在奖池页和皮肤页之间切换，持续 5 分钟后，屏幕上的卡片仍能在 2 秒内出图。

`docs/history/ledgers/r130-execution-ledger.md` 第 8 节"未验证 / 边界"第 1 条已经如实写了没做这一步（"需要连着国服客户端、在 Windows 真机上跑真实皮肤目录与真实动态原画视频"）。我这轮独立复测只能在虚拟 DOM 和 jsdom 级别验证机制本身，同样做不了这一步，所以这条到现在还是空的。

请找一台能连英雄联盟客户端的机器，按下面的步骤跑一遍：

1. 打开收藏页「全部皮肤」视图，快速来回拖动滚动条（尤其是跳到列表很靠下的位置再跳回顶部）。
2. 连续悬停 10 张以上带动态原画的皮肤卡片，每张停留 1-2 秒再移到下一张。
3. 在收藏页的「三合一奖池」子页和「全部皮肤」子页之间来回切换几次。
4. 上面三个动作穿插进行，持续 5 分钟。
5. 5 分钟结束时，检查屏幕上当前可见的卡片是否都能在 2 秒内出图（不是长时间停在"加载中"）。
6. 导出诊断日志，搜索 `card_image_stalled`：
   - 如果完全没有，说明这轮修复在真实负载下也成立，直接在执行记录里补一句"P2 已跑，无 stall"就可以结项。
   - 如果出现了，对照同一时间窗有没有大量 `local_request_client / failed(endpoint=image)`：有的话是第二层积压（第二层名额不够用，该调的是远程/本机道的名额），没有的话说明第二层放弃时又没能通知到第一层（说明合成 error 的某个闸门还有漏洞），这两种要分开处理，不要混在一起改。

验收：把这次真机跑的操作时长、`card_image_stalled` 出现次数（以及出现时对应的 `local_request_client failed` 数量）补进 `docs/history/ledgers/r130-execution-ledger.md` 第 8 节，或者单独起一条记录，不需要为这个再开新工单——除非真的抓到了 stall 且是通知失败那一种，那就是新缺陷，按项目惯例另开工单。
