# WORKLIST-R203：进入收藏被"正在读取召唤师信息"遮罩卡住；全项目阻塞状态排查；内存每局上涨

诊断人：Claude（看截图 + 读日志 + 只读核对源码）。执行人：GPT。日期：2026-10-03。基线：0.12.63（`c21482dba3c7`），可与 R201/R202 合并发布。

## 现象

用户截图：收藏 → 三合一奖池 → 奖池皮肤，整个窗口被遮罩盖住，中间卡片写"正在读取召唤师信息 · 正在读取身份与总览数据 · 立即重试"。**遮罩后面皮肤网格其实已经显示出来了**（传说品质一排排卡片可见）。

## 证据（日志 `lol-loot-diagnostics-1003-2144.jsonl`）

| 时间 (UTC) | 事件 |

| 13:41:5x | 用户进入收藏 |
| 13:42:01 | `collection_refresh_request coalesced=false` → 13:42:03 `refresh_succeeded` 1.9 秒 |
| 13:42:08 | 又一次 → 13:42:10 成功 1.8 秒 |
| 13:42:14 | 又一次 → 13:42:16 成功 1.8 秒 |

| 13:42:28 之后 | 后端、桌面端、前端都没有记录，直到 13:44:01 新进程启动（`desktop_startup` + 新 `run_id`），说明用户关掉软件重开了 |

结论：

1. **后端没有卡死**。27 秒内 4 次完整的收藏刷新全部成功，每次约 2 秒；每个本地请求都正常返回。
2. **数据也已经到了前端**（截图里遮罩后面有网格，`dom_nodes` 从 7561 涨到 12778）。卡住的是那个**全屏遮罩没有撤掉**，用户只能关掉软件。
3. 27 秒内连续 4 次完整刷新是不正常的。日志里没有记录每次刷新是谁发起的（用户点「立即重试」，还是前端自动补刷），无法区分。

## 根因（源码已核对的部分）

1. **用错了遮罩。** `backend/web/app.js` `updateReadingOverlay`（约 523–553 行）：`preparing` 的第三个条件是"已连接、快照已就绪、当前在收藏页、正在加载列表"，满足时显示的是**启动用的全屏遮罩**，文案写死"正在读取召唤师信息 / 正在读取身份与总览数据"，并给整个应用加 `inert`。收藏列表重载根本不是读召唤师信息，却把整个软件锁住。
2. **每次状态变化都会把遮罩重新弹出来。** `refreshStatus` 里只要 `lastSync`、`lastAttempt`、`collectionDirty` 等任一字段变化，就调用 `updateReadingOverlay(true)`（`willLoadItems=true`），在收藏页就进入 `preparing` → 显示遮罩，然后 `loadSkins(true)` 重新拉列表。每次收藏刷新都会改 `lastSync`，所以每刷新一次遮罩就重新出现一次。
3. **疑似补刷循环。** 后端 `connection_manager.go markCollectionDirty`：客户端推来跟收藏相关的事件就标记"收藏已变"；`main.go clearCollectionDirtyThroughLocked` 只清除刷新**开始前**的标记。刷新期间如果客户端又推了相关事件（读皮肤、战利品时客户端自己也会推事件），刷新完仍是 dirty；前端 `triggerCollectionRescanIfDirty` 在下一次状态轮询（约 10 秒）又发起一次完整刷新……这与日志里"每 6～11 秒一次"的节奏一致。**需要执行时用诊断证实**（见 P1-5）。
4. **「立即重试」很重。** 遮罩上的「立即重试」直接调用顶部「重新读取」（`el.refresh.click()`）：中断所有请求、重置页面状态、`POST /api/refresh` 全量刷新、再派发 hard-refresh。用户连点几次，就是几次全量刷新，又会再触发第 2、3 条。
5. 遮罩有 25 秒兜底（`startupFallbackTimer`），但每次重新显示 / 点重试都会重新计时，兜底形同虚设。

## P1　收藏页不再用全屏遮罩；补刷不再循环

1. **全屏遮罩只用于两种情况**：未连接客户端（"正在连接英雄联盟客户端"）、已连接但身份还没读到（"正在读取召唤师信息"）。删掉 `preparing` 里"收藏页正在加载"那一条。
2. **收藏页的加载只在页面内显示**：
   - 已经有列表时，后台刷新保持现有卡片可见（现有 `keepVisible` 逻辑扩展到所有刷新），不遮挡、不 `inert`；
   - 第一次进入、还没有任何数据时，用网格区域内现有的加载占位（骨架或"正在读取收藏"一行），**不锁整个窗口**。
3. **全屏遮罩的硬上限**：任何原因显示的全屏遮罩，从第一次显示起最多 15 秒，到时强制撤掉，不因再次显示或点重试而重新计时（计时只在遮罩真正隐藏后才重置）。撤掉后如果身份仍未读到，在页面顶部用现有的状态提示条显示"召唤师信息读取失败"和「重试」，不再锁界面。
4. **遮罩上的「立即重试」只重试身份读取**，不再调用全量「重新读取」。同一次遮罩里连续点击，1 秒内只算一次。
5. **补刷限流**：
   - 前端由 `collectionDirty` 自动发起的补刷，同一个页面会话里**最多 60 秒一次**；页面不在前台、或当前不在收藏页时不发；
   - 后端在收藏刷新结束后 5 秒内收到的"收藏已变"事件，只记录、不重新标 dirty（这段时间的事件大多是刷新本身触发的）；
   - 诊断 `collection_dirty_marked`：`uri_kind`（只记事件路径的类别，如 `inventory` / `loot` / `champions`），`during_refresh`（布尔），`suppressed`（布尔）。
6. **刷新来源记录**：`collection_refresh_request` 增加 `source`：`user_refresh`（顶部重新读取）、`overlay_retry`、`dirty_rescan`、`ensure`、`event`。

### 测试（Node + Go）

1. 收藏页已有 1183 张卡片，状态 `lastSync` 每 8 秒变一次 → 全屏遮罩**从不出现**，`appFrame` 从不 `inert`，卡片一直可见。
2. 第一次进入收藏、列表为空 → 只在网格区域显示加载，不出现全屏遮罩。
3. 身份始终读不到 → 全屏遮罩 15 秒后撤掉，即使中途又触发了 3 次显示、点了 2 次重试；撤掉后出现状态提示条。
4. 遮罩上点「立即重试」→ 只发身份读取请求，不发 `/api/refresh`，不派发 hard-refresh。
5. 状态每次都返回 `collectionDirty=true` → 60 秒内最多一次 `dirty_rescan`。
6. Go：刷新结束 3 秒后收到收藏事件 → 不标 dirty，`suppressed=true`；结束 6 秒后收到 → 正常标 dirty。

变异：恢复收藏页的全屏遮罩条件 → 测试 1 FAIL；遮罩计时随重新显示重置 → 测试 3 FAIL；去掉补刷限流 → 测试 5 FAIL。

## P2　全项目排查同类"原则性问题"（用户要求）

这次的问题属于同一类错误：**一个局部的加载状态，用了会锁住整个软件、又没有可靠退出条件的界面；同时状态变化会自动触发重请求，形成循环**。请按下面四类逐项排查整个前端（`backend/web/*.js`）和后端，把结果做成表格写进账本（文件:行号、场景、风险、处理方式、对应测试），能改的在本工单一起改：

1. **阻塞界面**：所有全屏遮罩、`inert`、禁用整页、模态弹窗。每一个都要有：明确的触发原因、最长显示时间（≤15 秒，确实需要更久的写明理由）、用户可以离开的方式、显示和撤掉的诊断。
2. **自动触发的重请求**：所有"状态 / 事件变化 → 自动发起刷新或重读"的地方（收藏补刷、总览 dirty 刷新、对局页刷新、LP 记录、征召、组队推断等）。每一个都要：同时只有一个在进行（single-flight），有频率上限，记录发起来源；不能由自己的结果再次触发自己。
3. **可能永远不结束的加载状态**：所有 `loading = true` 的地方，确认请求被取消、超时、出错、页面切换时都能复位（`finally` 按 generation 复位），不会一直转圈。
4. **后端等待**：HTTP handler 和后台任务里等锁、等 channel、等外部请求的地方，必须带 `context` 超时；不能持有锁时做网络请求或写诊断。

排查结果里认为"不需要改"的，也要写明理由。

## P3　后端内存每局上涨约 15 MB，不回落

同一份日志 `backend_runtime_metrics`，在大厅空闲时的堆内存：

| 时段 (UTC) | 空闲时 heap_alloc |
|---|---|
| 11:29–11:56 | 约 48–60 MB |
| 12:20–12:43 | 约 68–71 MB |
| 12:56–13:11 | 约 82–89 MB |
| 13:21–13:39 | 约 97–105 MB |

每打完一局，空闲时的基线就上涨约 15 MB，之后不再回落（goroutine 数一直回到 14，所以不是 goroutine 泄漏，是数据被留住了）。进入收藏时峰值到 257 MB。

1. 加诊断：每局结束后 60 秒（复用 `lobby_after_60s` 时机），记一次 `heap_profile_top`：按占用内存取前 15 个分配位置（只记函数名和 MB，不记数据），每局最多一次。
2. 排查每局都会新增、但没有上限或过期的缓存：对局快照、对局页战绩缓存（R202 P5 刚加了按队列区分的键，注意上限）、对局详情、图片代理缓存、诊断去重表、组队推断、LP 记录等。每个缓存都要有条目上限或过期时间，写进账本。
3. 目标：连续打 5 局后，大厅空闲时的堆内存与第 1 局后相差不超过 15 MB。用模拟对局循环跑一个 Go 测试，断言多轮后缓存条目数稳定。
