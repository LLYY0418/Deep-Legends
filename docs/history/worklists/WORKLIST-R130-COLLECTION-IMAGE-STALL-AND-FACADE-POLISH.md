## P1　皮肤列表一开始正常，过一会整屏「加载中」且不再恢复

### 0. 结论

后端没有问题：最后一次启动里皮肤目录 4 次刷新都成功（每次 1.4–1.5 秒，`skinCount 2121`，指纹不变），没有任何接口报错。**卡住的是前端两层图片队列之间的配合**：

- 第一层 `app.js` 卡片队列：全局 8 个名额（`pumpCardImageQueue`，`state.activeCardImages < 8`），名额只在图片的 `onload`，或 `onerror` 把全部候选地址试完时才释放。
- 第二层 `image-queue.js`：真正给 `<img>` 设置 `src`。

下面四个问题都会让第一层的名额被一直占着。8 个名额占满以后，新出现的卡片永远排不到，就是截图一的样子。

### 1. 根因（按影响从大到小）

**A. 第二层超时放弃时不通知第一层，名额永久泄漏（已复现）**

`image-queue.js` 的超时处理是 `img.removeAttribute("src"); finish(true)`；重试一次还超时，就只执行 `prefetch.delete(img)`，然后什么都不做。可是**移除 `src` 不会触发任何 `error`/`load` 事件**（Chromium 实测：请求一直挂起时移除 `src`，1.5 秒内收到事件 `[]`）。于是：
- `app.js` 的 `image.onerror` 永远不会被调用，这张卡的名额永远不释放；
- 这张皮肤后面的候选地址（`tilePath`、`loadScreenPath`、`/api/skin-art`）也永远不会去试，本来能显示的图一直停在「加载中」。

复现（真实的 `image-queue.js` + 从 `app.js` 原样抽出的 7 个队列函数，放在无头 Chromium 里跑）：

| 时刻 | 卡片名额占用 | 排队 | 已显示 | 「加载中」 |
|---|---|---|---|---|
| 8 张挂起的图入队后 1s | 8 | 0 | 0 | 8 |
| 34s（第二层已经两次超时、彻底放弃） | **8** | 0 | 0 | 8 |
| 再加 6 张正常的图，过 5s | **8** | **6** | **0** | 14 |
| 同一时刻直接 `fetch` 一张正常的图 | — | — | HTTP 200 | — |

也就是说后端和网络都正常，但页面再也不会加载任何卡片图。

`favorites-facade.js` 的头像/旗帜卡片也靠 `image.onerror` 显示「无图」，同样会一直停在「加载中」。

**B. 两层用的可见区域判断不一致，名额被屏幕外的卡片占住（已复现）**

- 第一层：`IntersectionObserver` 的 root 是 `el.appScroll`，`rootMargin: "620px 0px"`，卡片离可见区还有 620px 就分配名额；
- 第二层：卡片模板是 `loading="lazy"`，`image-queue.js` 用自己的观察器（root 是视口，`rootMargin: "160px"`，但会被 `appScroll` 这个滚动容器裁掉，实际上要真正可见）判断，不可见就不放行，名额继续占着。

复现：40 张全部正常的图、容器高 300px。停在顶部时就已经有 5 个名额被屏幕下方的卡片占住；**直接跳到底部，4 秒后屏幕上的卡片一张都没加载**（名额 8/8，排队 5），要滚回原来的位置才会动。拖滚动条、恢复滚动位置、刷新后重建列表，都会遇到这种情况。

**C. 悬停播放的视频不释放连接，挤占图片连接（机制已复现，大小相关）**

`prepareSkinVideo` 在 `pointerenter` 时开始播放循环视频（`/api/media`，不经过图片队列），但**全文件没有 `pointerleave` 处理**：鼠标移开后视频继续循环，要等列表重建才会停。Chromium 每个主机最多 6 条连接。实测：5 个大视频（40MB）即使本机不限速传输，Chromium 也会暂停缓冲但**一直保持连接**，这时再请求一张 1×1 的小图，12 秒后仍在等待；换成 6MB 的视频就能下完并释放连接。炫彩原画、终极皮肤这类动态原画视频体积大，用户在列表上随便划过几张卡，就能把连接占满，导致图片超时，然后触发 A。0.12.15 的图片队列上限是 6，再加上 SSE 就是 7，本来就超过 6 条，情况更容易出现（0.12.17 已改成 5）。

**D. 离开奖池页时不取消奖池列表的卡片任务**

`activateFavoritesPage` 和切换一级页签时只调用了 `cancelDeferredImages(el.grid)`，没有取消 `el.poolSkinGrid`。奖池面板隐藏后，里面的图片永远不可见，第二层不会放行，已经拿到名额的任务会一直占着全局 8 个名额，直到下次打开奖池页。

### 2. 修复方向

1. **（A）第二层彻底放弃时必须通知**：`image-queue.js` 不再重试（`count >= maxRetries`）时，在 `finish` 移除自身监听以后执行 `img.dispatchEvent(new Event("error"))`，让调用方的 `onerror` 正常运行（`app.js` 接着试下一个地址，`favorites-facade.js` 显示「无图」）。卡片被取消（`cancelled`）时不要发这个事件。
2. **（A 兜底）第一层加看门狗**：卡片任务拿到名额以后，25 秒内没有 `onload`/`onerror`，就按失败处理：释放名额、试下一个地址、全部试完显示「暂无预览」。不管第二层以后怎么改，名额都不能再被永久占用。
3. **（B）只在一层判断可见区域**：`app.js` 分配名额的时候，把 `image.loading` 设成 `"eager"`，第二层不再重复按懒加载判断；已经排队但还没拿到名额的任务，如果卡片离开了 620px 范围，就撤回来重新观察，保证先加载当前屏幕上的卡片。
4. **（C）悬停视频**：`pointerleave`/`blur` 时调用已有的 `resetVideo(video)`，并重新显示图片；全局同时最多播放 1 个悬停视频，开始下一个之前先停掉上一个。
5. **（D）** 切换收藏子页、切换一级页签时，同时调用 `cancelDeferredImages(el.poolSkinGrid)`。另外检查一遍 `deferCardImageSources` 的所有调用点，确认它们所在的容器被替换或隐藏时都会取消任务。
6. **诊断**：卡片任务被看门狗判定超时时，上报 `card_image_stalled`（字段：`activeCardImages`、`queued`、`reason: "watchdog"`、`sourceIndex`、`imageSource` 类别，不带路径），每 10 秒最多一条，并加进 `features.go` 白名单。下一份日志就能直接看到有没有再卡住。

### 3. 测试（均需对抗变异）

- 复现 A：假的 `img`（移除 `src` 不触发事件）+ `image-queue.js` + 抽出的 `app.js` 队列函数；8 张永不返回的图 → 第二层放弃后名额必须归零；之后加入的正常图必须全部加载。**变异**：去掉 `dispatchEvent`，并关掉看门狗 → 必须 FAIL。只关掉其中一个仍然要 PASS（两道防线各自有效）。
- 复现 B：40 张图、容器 300px、跳到底部 → 屏幕上的卡片必须在 2 秒内开始加载。**变异**：去掉 eager 设置 → 必须 FAIL。
- C：`pointerleave` 以后视频的 `src` 被移除；连续悬停 3 张卡，同时只有 1 个视频在播放。
- D：打开奖池页 → 切回皮肤页 → `activeCardImages` 只统计皮肤列表的任务。

## P2　旗帜卡片太小，尤其高度不够

现在 `.facade-grid.is-banners` 是 `--card-min: 168px` + `.skin-art { aspect-ratio: 1/1 }`，旗帜是细长竖图，只占正方形中间一窄条，文字还压在上面。

- 格子改成固定宽度的竖长卡：`grid-template-columns: repeat(auto-fill, 150px)`；`.skin-art` 的宽高比取旗帜图片真实的 `naturalWidth / naturalHeight`：第一张旗帜图加载后写进网格的 `--facade-banner-ratio`，加载前默认按 `0.3`。`object-fit: contain`，不裁剪。
- 名称等文字移到图片下方（和 R125 头像格子的处理方式一样），不要再压在旗帜上。
- 验收：旗帜图片的高度占满图片区域（上下留白 ≤ 5%），不被裁剪，宽窗口下格子尺寸不变。

头像、旗帜、炫彩（`makeChromaCard` 的「已拥有 / 未获取」）卡片都去掉右上角的状态标签。未拥有的卡片靠置灰 + 锁图标表示，已拥有的卡片正常显示。

- 皮肤卡在「全部皮肤」视图里的「三合一剩余」标签表示的是奖池状态，不是拥有状态，**保留**。
- 详情弹窗里的「拥有状态」一行保留。

删除 `index.html` 里的 `.facade-metrics`，同时删除 `favorites-facade.js` 中 `el.total/owned/visible/metricsBar` 的相关逻辑和 CSS，只保留下面一行摘要，和其它收藏页保持一致。断连时的收起逻辑（`renderDisconnected`）同步调整，不要因为引用了不存在的元素而报错。

## P5　摘要行：去掉「已显示」、数字用主题色；头像默认不显示未拥有

1. `facadeCollectionMetaText` 改为 `共 5,099 款头像 · 已拥有 478`，去掉「· 已显示 N」。
2. 摘要行里的数字用主题色：`<b class="list-meta-number">`，`color: var(--primary); font-weight: 650; font-variant-numeric: tabular-nums;`。应用范围：头像/旗帜摘要、皮肤摘要（`app.js` 约 1061 行「已拥有 649 款 · N 位英雄」）、炫彩摘要（约 3157 行）。只改摘要行，不改英雄分组的小标题。改用 DOM 拼接或者先转义再用 `innerHTML`，**不能**把未转义的文本放进 `innerHTML`。
3. 头像默认关闭「显示未拥有」：`filters.icons.showUnowned` 默认 `false`，`index.html` 里的 checkbox 去掉 `checked`，由 `syncControls` 控制。旗帜保持默认打开。
4. 与 R124 的配合：`syncControls` 现在在拥有状态不可用时执行 `filters.showUnowned = true`，**会永久改掉用户的设置**，拥有状态恢复后开关仍然是开着的。改成不修改保存的值，只在筛选时用 `unavailable || filters.showUnowned` 作为实际生效的值。R124 的测试（状态不可用时网格不能为空）必须继续通过；另外补一条：状态从「不可用」恢复为「可用」后，头像开关回到用户原来的设置（默认关闭）。

## P6　头像详情弹窗：按图标本身的尺寸显示，完整、正方形

`.facade-detail-dialog` 现在宽 560px，图片区域是 560×560，128px 的头像被放大 4 倍多（截图五模糊就是这个原因）。

- 头像：图片区域是正方形，大小等于图片的 `naturalWidth × naturalHeight`（按 CSS 像素 1:1 显示，不放大），最大 256px；`object-fit: contain`，完整显示。弹窗宽度跟着缩小，改成紧凑布局（图标在上，信息在下，或者图标在左、信息在右，二选一，以不出现大片空白为准）。
- 旗帜：同一个弹窗按旗帜自身比例显示（`contain`，不裁剪），高度不超过弹窗的最大高度。
- 图片加载前先按 128×128 占位，避免弹窗尺寸跳动。
- 皮肤/炫彩详情弹窗不动。
