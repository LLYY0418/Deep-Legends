# R116-F：海克斯概率预测器 + 负向推荐 + 平衡参数可行性探测

**目标：** 三个互相独立、可并行的小工单合并成一张：
1. P2-4：海克斯稀有度概率预测器升级为「英雄专属」口径（现有 `/augment-rarity` 是全服口径）。
2. P2-5：负向推荐（"选的人多但收益为负"的慎选提示）。
3. 平衡参数（伤害加成/承伤修正）抓取的独立可行性探测——这三项里**只有这一项需要新探测**，前两项数据已经在 R116-A 的 `hero-json` 里，是纯本地计算。

**背景：** 这三项在原方案里风险评级最低，独立核查未发现需要纠正的实质性错误，本工单沿用原方案 P2-4/P2-5/平衡参数探测部分的设计，仅补充依赖关系。

**依赖：** P2-4/P2-5 依赖 R116-A（需要 `hero-json` 的 `augments[].stages[]`）；平衡参数探测无依赖，可随时单独执行。

**版本：** 完成后升到 0.12.12。

---

## P1：海克斯稀有度概率预测器（英雄专属口径）

### 现状证据
- 现有 `/augment-rarity` 全服口径阶段分布已接入（`hexdataRarityStage`，`hexdata.go:235-239`），渲染在 `renderMayhemRarityPanel`（`champions.js:1123-1131`）。
- R116-A 接入的 `hero-json` 里 `augments[].stages[]` 每条带 `rarity` 与 `pickRate`，按阶段把同英雄所有海克斯的 `pickRate` 按 `rarity` 求和，就能算出"这个英雄在第 N 阶段刷出棱彩/黄金/白银的概率"——**纯本地聚合，不需要新请求**。

### 实现要求
1. 新增本地聚合函数 `computeHeroStageRarityDistribution(augments []hexdataAugmentRowV2) map[int]map[string]float64`（阶段 → 稀有度 → 概率），输入就是 R116-A 已经解析好的 `hero-json.Augments`。
2. 渲染时保留现有全服口径面板，新增一个"该英雄专属"的对比视图（不要替换全服口径，两者信息量不同：全服口径回答"整体分布"，英雄口径回答"这个英雄"）。
3. 概率转移矩阵/四阶段组合枚举（原方案里的进阶功能）本工单**不做**——这是纯计算的加分项，价值明显低于其他工单，留到有余力时再补，避免在这张工单上无限扩展。

### 验证判据
- 用一个英雄的 `hero-json` fixture 验证聚合结果：某阶段所有海克斯的 `rarity` 分组求和后，三个概率之和应为 1.0（±0.01 浮点误差）。

## P2：负向推荐（慎选/陷阱提示）

### 现状证据
虎牙站的 `trapAugments` 思路（专属联动/陷阱联动），但**必须有统计依据才给，不能编辑拍脑袋**。可靠信号：`items.withoutItemWinRate` 反例（出了反而更差）+ `augments` 里"选取率高但 `deltaWinRate` 为负"的组合。

### 实现要求
1. 判据：`pickRate` 超过该英雄同稀有度海克斯的中位数、且 `deltaWinRate < 0`、且 `sampleTier != "low"`（P0-2 已有的样本分档，避免小样本噪音被当成慎选信号）。
2. 文案统一为"数据显示：选取率较高但胜率低于基准 X%"这类客观陈述，**不使用"陷阱"这类主观评判词**（沿用项目一贯的"陈述关联，不做因果断言"风格，参考 Hexdata C 位榜的"描述赛后关联，不证明主动让经济会带来胜利"措辞）。
3. 渲染落点：海克斯推荐卡的次要信息位（详情页"概览"tab），不单独开新 section。

### 验证判据
- 构造一个"选取率 30%、`deltaWinRate: -0.05`、样本 5000"的 fixture，验证生成负向提示；构造一个"选取率高但样本低"的 fixture，验证**不**生成（低样本不作为慎选判据）。

## P3：平衡参数（伤害加成/承伤修正）独立可行性探测

### 现状证据
- ARAMKit 与 RESG（`bb` 字段）都显示存在这类数据，但实测 CommunityDragon 常规 JSON 端点没有：`champions/157.json`（200，无 aram/balance 键）、`champion-summary.json`（200，无）、`game/data/characters/yasuo/yasuo.bin.json`（200，无）、`champions-summary.json`/`aram-champion-balances.json`（404）。

### 实现要求
1. 这是一次**独立的、允许失败的**探测，不承诺产出功能。候选路径（按成本排序）：
   - LCU 客户端本地是否有海斗平衡参数缓存文件（游玩后本地磁盘/内存里可能有游戏内配置，需要真机排查，而不是网络请求）。
   - 版本公告页面解析（Riot 官方 patch notes 里偶尔会列出具体数值，但格式不稳定，人工核对成本高）。
   - **不抓取** RESG/ARAMKit 的页面（已在原方案里否决：无明确引用许可条款/无公开 API）。
2. 探测产出一份 `docs/r116f-balance-param-findings.md`，结论只有两种："找到可用来源，值得开新工单" 或 "探测不通过，明确放弃，写清楚已排除的路径，避免以后重复调研"。

### 验证判据
- 探测文档产出且给出明确结论（不允许"待进一步调研"这种没有终点的表述）。
