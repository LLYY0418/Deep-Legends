## 背景

用户在真机上找不到"检查更新"按钮，排查后发现这是**预期行为**：
`web/app.js:3299` 的 `renderUpdateStatus()` 只有当 `current.state` 已经是
`available`/`downloading`/`verifying`/`ready`/`applying`/`failed` 之一
**且** `current.latest` 有值时，`#update-button` 才会显示——也就是说这颗按钮
天生就是"被动通知"，不是"主动触发"。

但顺带发现一个真实缺口：后端早就有 `POST /api/update/check`
（`update_http.go:15-16`，调用 `updates.Check(true)` 强制立即检查，绕过
`update.go:319` 的 6 小时缓存），**前端却从未调用过这个接口**——软件里没有任何
地方能让用户主动点一下"现在就检查"，只能等启动时的一次自动检查、或者最多等
6 小时的下一次自动检查。

用户确认要加这个按钮。

## 要做什么

在设置页新增一个手动检查更新的入口，放在版本信息旁边最自然：

1. **位置**：`web/index.html:287` 那行
   `<p id="settings-build-identity" class="settings-build-identity">版本信息读取中…</p>`
   紧挨着加一个按钮（复用现有 `setting-card` 里按钮的样式类，比如
   `class="text-button"`，参考 `web/index.html:297` 侧边栏收起按钮那个写法），
   文案用"检查更新"。

2. **点击行为**：
   - 调用 `POST /api/update/check`（未鉴权 token 走现有 `authorized` 包装，
     复用页面里已有的 `api()` helper，不要另起一套请求逻辑）。
   - 检查期间按钮显示忙碌态（disabled + 文案变成"正在检查…"之类），
     参考现有 `el.updateButton` busy 状态的做法（`web/app.js:3307`）。
   - 检查完成后：
     - 如果发现了新版本（`state` 变成 `available` 及以后）：**直接复用现有的
       `renderUpdateDialog()` / `#update-dialog`**（`web/index.html:356`），
       和自动检查发现更新时弹出的是同一个对话框，不要新做一套 UI。
     - 如果没有新版本（`state` 仍是 `idle`）：在按钮旁边给一个短暂的文字反馈，
       比如"已是最新版本"，几秒后消失。参考页面里其它"保存成功"之类的短提示
       模式（例如 `setting-proxy-save` 按钮周边如果有类似反馈，抄那个模式；
       没有的话就用最简单的 `textContent` 设置 + `setTimeout` 清空，不需要
       引入新的通用 toast 组件）。
     - 如果请求本身失败（网络问题、`当前构建不支持更新` 等 400 响应）：
       同样给出简短的错误反馈，不要静默失败。
   - **不支持更新的构建**（`current.supported === false`，即
     `updateUI.status.supported`，对应后端 `version === "dev"` 或没有
     `store` 的情况）：这个按钮应该隐藏或禁用，不要点了之后才提示"当前构建不支持更新"。

3. **不要重复请求**：如果上一次手动检查还没返回、或者更新本身正处于
   `downloading`/`verifying`/`applying` 等忙碌状态（`updateManager.busyLocked()`，
   `update.go:309`），按钮要禁用，不能让用户连点触发并发的 `Check`——
   虽然 `Check()` 自己有 single-flight 保护不会崩，但连点应该在前端就给出
   明确的"进行中"反馈，而不是让用户以为点了没反应。

## 验收判据

1. 真机或 Chromium 截图验证：设置页版本信息旁边能看到"检查更新"按钮。
2. 点击后确实发出了 `POST /api/update/check` 请求（不是复用 6 小时缓存的旧结果）。
3. 模拟"发现新版本"场景：点击后正确弹出 `#update-dialog`，内容与自动检查触发时
   的弹窗一致（同一套渲染逻辑，不是另一份重复代码）。
4. 模拟"没有新版本"场景：点击后有明确的"已是最新"反馈，不是毫无动静。
5. 模拟请求失败场景：有明确的错误反馈。
6. `current.supported === false` 时按钮隐藏或禁用，不产生误导性的点击结果。
7. 检查进行中或更新本身处于忙碌状态时，重复点击不会造成界面上出现两份反馈、
   或者按钮状态错乱。

## 变异判据

| 变异 | 测试必须能发现 |
|---|---|
| 按钮点击没有真的调用 `/api/update/check`（比如误用了缓存的 status） | ✅ |
| "发现新版本"时按钮点击弹出的是另一份新写的对话框，而不是复用 `renderUpdateDialog()` | ✅（两处弹窗内容/字段渲染逻辑分叉，以后维护更新说明文案容易漏改一处） |
| `supported === false` 时按钮仍可点击 | ✅ |
| 忙碌状态下按钮仍可重复点击并发请求 | ✅ |

## 不要做的事

- 不要改动 `updateManager.Check()`、6 小时自动检查间隔、`busyLocked()` 这些
  后端已有且验收过的逻辑，本单只加前端的手动触发入口。
- 不要把这个按钮做成常驻在主界面顶部（那是 `#update-button` 通知按钮的职责，
  两者定位不同：一个是"有更新时主动提醒"，一个是"用户主动问一下有没有"）。
- 不要顺带发布或验证 v0.13.0 GitHub Release，那是 `WORKLIST-R85-FIRST-RELEASE.md`
  的范围，本单只加这一个按钮。
