## P1　斗魂征召「勇敢举动」：预选阶段的失败被记成「这个英雄选不了」，真正轮到自己锁定时请求根本没发

### 日志时间线（北京时间，0.12.73）

第一个征召（action 34）：

| 时间 | 事件 |
|---|---|
| 20:14:32.45 | 进入英雄选择，`timer_phase=PLANNING`，候选 `champion_id=-3`（勇敢举动），安排 `write_step=intent` |
| 20:14:32.97 | 第 1 次 PATCH（intent）→ `http-success` |
| 20:14:35.27 | `postflight not-applied-after-2s`：`observed_champion_id=0`，客户端没采纳 |
| 20:14:35.80 | 第 2 次 PATCH（intent）→ `http-success`，2 秒后同样没生效 |
| 20:14:38.43 | `confirmation attempt-limit`（第 2/2 次） |
| 20:14:42 | 禁用暗夜猎手（67）：hover → lock，两步都 `applied`。禁用正常 |
| **20:15:07.70** | **轮到自己选**：`timer_phase=BAN_PICK`，`completed=true`（锁定步骤）→ **`schedule attempt-limit`，一个请求都没发** |
| 20:15:18 | `manual-takeover`，用户手动选了勇敢举动（之后 `current_champion_id=-3`） |
| 20:15:25 | 有人秒退，回到排队 |

第二个征召（action 30）完全一样：20:15:32 / 20:15:35 两次 intent 没生效 → 20:16:05 轮到自己锁定时 `schedule attempt-limit` → 20:16:16 用户手动选。**同一问题复现两次。**

### 根因（源码已核对）

1. **预选失败和锁定共用一个失败标记。** `backend/champselect_execution.go` 约 151～163 行：pick 请求没生效时，`pickFailures[actionID][championID]++`，达到 `champSelectMaxWriteAttempts`（2）就设 `pickFailed[actionID][championID]=true`。这里**没有区分 `write_step`（intent 预选 / lock 锁定）**。
2. `backend/champselect.go` `scheduleChampSelectRequest`（约 1222 行）对每个 pick 请求都检查 `champSelectPickBudgetLocked(actionID, championID)`（`champselect_recovery.go` 第 6 行），只要 `pickFailed` 为 true 就返回 `attempt-limit`。所以预选失败两次之后，锁定这一步直接被拦下。
3. `pickFailed` 是 R200（提交 `91df3a9a`，0.12.63，ARAM 卡牌选择）加的（`git log -S pickFailed` 已确认），按「动作 + 英雄」记，没有考虑同一动作先预选、后锁定两步。从 0.12.63 起斗魂征召的勇敢举动很可能就一直选不上（这份日志只有 0.12.73 的两次样本，无法确认更早版本）。
4. **为什么预选总是失败：** 英雄选择的规划阶段（PLANNING），客户端接受了 championId=-3 的 PATCH（返回成功），但不会把「勇敢举动」显示成预选，`championId` 一直是 0。普通英雄能预选，勇敢举动不能。禁用没有规划阶段预选这一步，所以禁用不受影响。
5. **界面没有告诉用户已经停了：** `champselect_execution.go` 约 187 行的 `advancing` 判断是「这个动作试过的英雄少于 3 个」，就认为会换下一个候选，于是把「已停止尝试，请手动操作」这句隐藏了。但选用序列里只有 1 个英雄，根本没有下一个。锁定被 `attempt-limit` 拦下时（`champselect.go` 约 1225 行）只写诊断，本局记录里没有任何一条，卡片还显示「可选」、顶部还写「当前为自己的操作回合」。

### 修复要求

1. **预选和锁定分开计数。** intent 失败只停止这个动作、这个英雄的后续预选；不能把它记成锁定失败。锁定步骤有自己独立的 2 次机会。普通英雄也一样适用（以前一个普通英雄预选失败两次，后面也会锁不上）。
2. **勇敢举动（-3）在规划阶段不发预选请求。** 轮到自己时按策略处理：
   - 「立即锁定」：直接发锁定。
   - 「亮出后锁定」「仅亮出」：轮到自己时亮出 -3，按现有流程等待和锁定。
   具体用哪个请求能让客户端接受勇敢举动（`PATCH .../actions/{id}` 带 `championId:-3, completed:true`，还是先 PATCH 再 `POST .../actions/{id}/complete`），**必须在 Windows 真机的斗魂征召里实测确定**，把成功的那条请求和对应日志写进账本。
3. **锁定后的确认：** 勇敢举动锁定后客户端可能显示 -3，也可能直接变成随机到的英雄。确认逻辑要把这两种都当成功，不能因为观察到的英雄 ≠ -3 而重试或报失败。
4. **`advancing` 要看真实情况：** 只有选用序列里还有没失败、可用的下一个候选时，才隐藏「已停止尝试」。否则照常显示。
5. **被拦下时要告诉用户：** 锁定步骤因为次数用完或其他原因没有发出时，本局记录写一条（同一动作只写一次），比如「勇敢举动 自动选用已停止，请手动选择」；卡片状态不再显示「可选」。这属于失败提示，符合界面文案红线。
6. 秒退后进入新的英雄选择（新 `session_trace`），所有计数清零（现在是这样，加测试锁住）。
7. R200/R202 的 ARAM 卡牌选择、替补席交换逻辑不能被影响，原有测试全部通过。

### 测试

- Go：构造斗魂征召会话：PLANNING 阶段 -3 不发 intent；进入 BAN_PICK 且本人 pick 动作 `isInProgress=true` 时发出锁定请求。
- Go：普通英雄 intent 两次未生效 → 到自己回合时锁定照常发出。
- Go：锁定两次都没生效 → 本局记录出现「已停止」的提示，只出现一次。
- Go：只有 1 个候选时，第 2/2 次失败的提示里带「已停止尝试，请手动操作」。
- Go：锁定后观察到随机英雄 ID（不是 -3），确认为成功。

## P2　斗魂对局出现两个自己：上一局 5v5 的红方 5 人残留在客户端数据里，被当成本局玩家

### 日志证据

| 时间（北京） | 版本 | 事件 |
|---|---|---|
| 19:16 | 0.12.71 | 海克斯大乱斗 `9016492149` 结束（5v5） |
| 19:20:14 | 0.12.71 | 斗魂 `9016529305` 开始：`lcu_gameflow_session_shape` → `game_mode=CHERRY`，**`team_one_length=17`、`team_two_length=5`** |
| 19:20:32 | 0.12.71 | `live_roster_shape`：`players=22`、`raw_count=22`、`team_counts {"100":17,"200":5}`、**`duplicate_player_refs=1`** |
| 19:20:25～38 | 0.12.71 | `live_roster_rendered`：`players_received=22`、`rendered_100=17`、`rendered_200=5` |
| 20:16:54 | 0.12.73 | 斗魂接斗魂：`team_one_length=18`、`team_two_length=0`，名单 18 人，没有重复 |

斗魂一共 18 人，全在 teamOne。19:20 那局 teamTwo 里的 5 人就是上一局大乱斗的一方，**里面包括自己，英雄还是上一局的**，所以出现了第二个「自己」。
`team_one_length=17` 说明那一刻 teamOne 还少一名真实玩家，名单实际上是「17 个真玩家 + 5 个上一局的人」。

### 根因（源码已核对）

- `backend/gameplay.go` 约 7745～7756 行：非英雄选择阶段，把 `session.GameData.TeamOne` 当 100 队、`TeamTwo` 当 200 队，**不看模式、不查重复**。客户端在斗魂里只写 teamOne，不清空 teamTwo，上一局的数据就留下来了。
- 英雄选择阶段已经有类似保护（约 7722 行 `DroppedStaleGameData`，不读 gameData），但对局进行中没有。
- 前端斗魂模式把所有玩家放进同一个「全部玩家」列表（`gameplay.js` 约 6866 行 `team(null, ...)`），所以 200 队的 5 人也混进来了。两行「自己」的 `data-live-player-row` 都是 `card:<同一个 puuid>`，行的 key 重复。
- 0.12.73 没有改这段代码。**只要斗魂的上一局是 5v5（召唤师峡谷、大乱斗等），这个问题就会再出现。**

### 修复要求

1. 斗魂模式（`isArenaQueue` / `CHERRY`）下**不读 teamTwo**。如果 teamTwo 不为空，丢弃，记诊断 `stale_team_two_dropped`，只记 `count`、`queue_id`、`game_id`，不记身份。
2. 所有模式都加最后一道去重：组装完名单后按 `playerRef`（puuid）去重，同一个人只留一条，优先保留 teamOne / 英雄和本局客户端数据一致的那条。去掉的数量记在 `live_roster_shape` 新字段 `duplicates_dropped` 里。非斗魂模式下，如果 teamTwo 的人和 teamOne 重复，也按残留处理。
3. `gameplay.go` 约 5697 行的 `livePositionShapeDiagnostic` 也读了 `TeamTwo`（只用于位置诊断），斗魂下同样跳过残留，避免诊断数据被污染。
4. 前端兜底：渲染前如果同一个 `data-live-player-row` key 出现两次，只渲染第一条，并上报一次诊断。
5. 斗魂 teamOne 少人（像 19:20 的 17 人）时，不能因为丢了 teamTwo 就少显示人：用现有的 playerlist 补人逻辑把缺的人补上（`session_missing_from_playerlist`），核对这一路是否生效，写进账本。
6. 「我的小队」标记（`markRememberedArenaSquad`）在去重之后执行，保证只有 3 个人带「我的小队」。

### 测试

- Go：斗魂会话 teamOne 18 人（含自己）+ teamTwo 5 人残留（含自己，英雄不同）→ 返回 18 人，自己只有一条，英雄是斗魂这一局的。
- Go：斗魂会话 teamOne 17 人 + teamTwo 5 人残留，playerlist 18 人 → 返回 18 人。
- Go：召唤师峡谷正常 5v5 不受影响；teamTwo 里有人和 teamOne 重复时被去掉。
- 前端：同一个 key 的两行只渲染一行。

| 20:17:23（对局开始后第一分钟） | 7 | **banner 1、tab-row 1、other 1** | 9 | 40 |
| 20:18:23 | 1（只有状态栏） | — | 0 | 0 |
| 20:18:23～20:20:42（导出日志） | 没有记录（0 次） | — | — | — |

- 0.12.73 这一局在加载完成后基本稳定，比 0.12.71 好很多（R213/R215 应该起了作用）。但加载完成的前 5 秒内仍有 3 次整块重建：20:17:18 第一次渲染时显示「小队数据尚未完整，正在自动重试」，20:17:23 playerlist 读到后提示消失，提示条变化触发整块重建（banner）；页签行也变了一次（tab-row）；还有一次原因是 `other`（说明外壳变了，但现有 4 种检查都没认出来是哪里变了）。

- 诊断里的 `sources` 不可靠：`state.liveRenderSource` 记的是最近一次加载的来源，之后不管是什么触发的重绘都记成 `interval`，所以看不出 0.12.71 每秒一次的重绘到底是谁触发的。

### 修复要求

1. **提示条、状态文字不要触发整块重建。** 「小队数据尚未完整，正在自动重试」这类提示条改成单独的节点原地更新（或放到 `data-live-body` 外面），出现或消失时不重建名单和推荐面板。
2. **页签行变化原地更新。** 只是页签文字、数量、选中状态变化时，原地改页签，不重建面板。
3. **查清 `other`：** 整块重建原因是 `other` 时，记下第一个不一样的外壳节点（标签名 + class，不记文本内容），找到原因后修掉，并在账本里写明是什么。
4. **名单按 key 增量更新：** `patchLiveRosterPanel` 改成按 `data-live-player-row` key 对应，行的顺序变了就移动已有节点，新增和减少的行单独插入/删除，不再因为顺序或行数不同就整个面板替换。
5. **诊断记录真实的触发来源：** 每次重绘记下这次是谁触发的（加载完成、SSE、进度、图片、页签切换、定时器等），不要沿用上一次加载的来源。如果还存在不带数据变化的定期重绘，找到触发点去掉。
6. 和 P2 一起做：名单 key 不重复以后，再验证一次。

### 验收标准（每个模式都要达到）

- 对局进行中、数据没有变化的每一分钟：`full=0`、`images_recreated=0`、`rows_replaced=0`；`build`/`insight` 只有在数据真的变了时才出现。
- 从进入对局到名单加载完成：整块重建最多 1 次；提示条出现、消失不产生整块重建。
- 需要实测的模式：召唤师峡谷（排位或匹配）、海克斯大乱斗（2400）、极地大乱斗（450）、斗魂竞技场（1700/1750，包括「斗魂接在 5v5 后面」这种情况）、练习工具，以及当天能排到的其他轮换模式。每个模式在账本里贴一段对局中 3 分钟以上的 `live_render_rebuild` 和 `renderer_perf` 原始记录。
- 每个模式录一段对局页 1 分钟左右的屏幕录像，确认没有闪烁（GPT 执行），放到 `docs/history/reports/r224/`。

## P4　名字后面的标签间距不一致（所有模式都有）
