## 〇、评审修订摘要（相对 Codex 初稿）

整体方向正确：服务端掌握授权、Go 后端执行门禁、客户端只带验签公钥、注册码不内置明文。初稿对风险边界的判断也基本准确。问题在于它按「零重叠的商业 DRM」设计，对 100 个码的小规模私有分发来说，**实现与运维成本过高，并且 60 秒租约会让国内网络稍有波动的合法用户频繁被锁**。本次修订的主要改动如下：

| # | 初稿做法 | 问题 | 修订后 |
|---|---|---|---|
| 1 | 严格交接：新机要等旧机发出 `ack-stop`，或等旧租约到期（最坏约 65 秒）后才解锁 | 用户需求只是「新机能用、旧机被遮罩」，并没有要求新机等待。为了零重叠，初稿不得不引入 60 秒租约、停止确认协议和 TRANSFERRING 状态，复杂度和误锁风险都很高 | **最后激活者立即生效**：B 输入码后马上可用；A 在线时下一次心跳（≤60 秒）锁定并提示「注册码已被其他地方使用」；A 离线时最迟在租约到期时锁定。重叠时间有明确上限，等于租约时长 |
| 2 | 租约 60 秒，心跳 20 秒，没有任何离线宽限 | 网络中断超过 1 分钟就锁定；授权服务一旦抖动，所有人同时被锁；心跳量约 43 万次/天 | **租约 15 分钟，心跳 60 秒**，失败后退避重试；最坏情况约 14.4 万次/天，常见在线时长下约 3–4 万次/天 |
| 3 | 每次启动都必须联网，不认可本地已有授权 | 应用内更新、崩溃重启时，一旦网络不好就被锁 | 本机保存的租约**若未过期、签名有效、绑定本机设备公钥**，可直接放行，同时立即在线续租；首次激活仍必须联网 |
| 4 | 每个请求先取一次性挑战 nonce，再签名 | 每次心跳要多一次往返 | 设备签名覆盖「方法 + 路径 + 请求体摘要 + 时间戳 + 设备单调计数器」；服务端检查时间窗（±300 秒）和计数器递增来防重放，不再需要取挑战这一步 |
| 5 | 优先使用 TPM 不可导出密钥，DPAPI 作为降级方案 | 后端以 `CGO_ENABLED=0` 构建，接入 TPM/CNG 要手写 syscall，成本高，对「防止共享注册码」的收益有限 | **第一期使用 Ed25519 软件密钥 + DPAPI（CurrentUser）**；TPM 列为可选后续增强 |
| 6 | 注册码存 HMAC 摘要，另外单独保管 HMAC 密钥并制定轮换方案 | 码本身已是高熵随机数，HMAC 密钥只会增加密钥管理负担 | 码有 100 bit 熵，服务端存 **SHA-256 摘要**即可；去掉 HMAC 密钥及其轮换方案 |
| 7 | 授权服务的平台和存储未定 | 现有 relay 和授权服务若放在同一个 Cloudflare 免费账号下，会**共用每天 10 万次 Workers 免费额度**。relay 用尽额度时会返回 1027，授权服务也会跟着失败，导致**全员被锁** | 明确方案：独立 Worker + **每个码一个 Durable Object**（天然按码串行，满足原子占用）+ 自有子域名；**生产环境必须开通 Workers Paid 或使用独立账号**，与 relay 的额度隔离 |
| 8 | 防篡改把 Authenticode 签名列为必需 | 代码签名证书需要付费和受控签名环境，会阻塞上线；而且初稿也承认签名本身不构成强制 | 拆成两档。**必做**：Electron fuses、ASAR 完整性，并把后端 SHA-256 作为构建期常量写进 ASAR 内的 `main.cjs`，启动前校验，形成不依赖证书的信任链。**可选**：Authenticode，不阻塞上线 |
| 9 | relay 是否加入授权检查留待「兼容发布方案」决定 | relay 是唯一真正握在服务端的资源（外服查询用的是开发者本人的 Riot Key） | 列为 **P4b 第二阶段**：relay 校验授权服务签发的短期访问令牌；旧版本客户端设兼容期 |
| 10 | 备份恢复使用 `issuer_epoch` 代际 | 对 Durable Object 存储来说过重 | 简化为：恢复旧备份时轮换签名 `kid`，旧 `kid` 签发的租约在 15 分钟内自然失效 |

**结论：可行。**按修订方案实施，客户端改动集中在 Go 授权管理器、路由门禁和授权遮罩；服务端是一个约几百行的 Worker；防篡改「必做档」不需要购买证书。

## 一、用户需求与可行性结论

用户要求：新用户安装后首先看到注册码输入界面，遮罩挡住软件，验证成功后才能使用；不能通过修改安装包文件关闭验证；注册码内置在代码里；普通码只能在一台电脑上使用，新电脑使用后旧电脑重新遮罩并提示「注册码已被其他地方使用」；先放 100 个注册码，其中一个是管理员码，可在任意电脑上使用任意次数。软件未来可能闭源。

**功能可以实现，但「纯客户端内置注册码」「绝对无法修改绕过」「断网也能立即知道异地使用」这三点不能同时成立。推荐由远程授权服务掌握授权状态，Go 后端执行功能门禁，界面只展示授权状态，再给官方安装包加上完整性校验。**

| 需求 | 结论 | 本单处理 |
|---|---|---|
| 首次打开强制注册码遮罩 | 可以 | 启动时默认锁定，验证前不启动业务取数和自动化；没有跳过入口，也不会超时自动关闭 |
| 普通码只允许一台电脑使用 | 可以 | 服务端按码串行维护「当前设备」；最后一次明确激活者生效 |
| 新电脑使用后旧电脑遮罩、提示异地使用 | 联网时 ≤60 秒；离线时最迟 15 分钟 | 心跳发现被替换后立即锁定并给出准确提示；离线的旧机在租约到期时锁定，联网后再补准确原因 |
| 100 个码，其中一个管理员码 | 可以 | 暂按 **总数 100 = 普通 99 + 管理员 1**，不擅自生成 101 个；本轮不生成生产码 |
| 管理员码在任意电脑无限次使用 | 可以 | 不限设备数、并发数、激活次数，设备之间不互踢，没有到期日；默认仍需联网续租，可撤销、可轮换 |
| 所有注册码随客户端代码内置且保密 | 不能作为安全方案 | 客户端连同其解密逻辑都可以被提取；加密、混淆或改成 Go 常量都消除不了这个问题 |
| 修改安装包绝对不能绕过 | 无法承诺 | 能挡住修改 JS/CSS/配置、替换后端、换 ASAR 等常见绕过；挡不住直接给主程序或后端二进制打补丁 |
| 将来闭源后自然安全 | 不成立 | 闭源只是少了直接读源码的便利，代替不了服务端授权 |

### 必须明确的需求调整与边界

1. **注册码存放位置**：「内置」改为「授权服务预置固定码池」。服务端只存摘要；客户端只带授权服务地址和验签公钥。生产码、签名私钥都不进 Git、安装包或日志。
2. **换机时的重叠窗口**：采用「最后激活者立即生效」。旧机在线时 ≤60 秒内锁定；旧机离线时最多还能用到当前租约到期（≤15 分钟）。如果要求零重叠，新机就必须等待，对 100 码的私有分发来说得不偿失。附录 A 保留了严格交接方案，留作将来的备选。
3. **防止来回抢占**：A 被踢后保持 `REPLACED` 状态，重启、重连都不会自动抢回，只有用户手动重新输入注册码才行。这样两个人共用一个码时，每次切换都得手动输码，体验足够差。服务端统计每个码每天的接管次数，超过阈值（建议 10 次/天）只记录、在管理工具中标出，**不做硬性拒绝**，不影响正常换机。
4. **管理员码「无视规则」**：只豁免单机、互踢、次数和有效期限制；仍然要验证真实性和签名，仍需联网续租，泄漏后可撤销、可轮换。它不代表永久离线通行，也不具备管理后台权限。
5. **设备识别**：以设备密钥证明身份，能阻止直接复制授权文件；但无法识别系统整盘克隆、虚拟机克隆或故意转发密钥的情况。
6. **旧版本边界**：已经发布、不带授权逻辑的旧版本仍能运行本地功能，本单不承诺「所有历史版本一并强制激活」。

## P0　冻结实施规则

### 推荐规则

| 项目 | 建议值 / 行为 |
|---|---|
| 普通码 | 99 个；任一时刻只有一个「当前设备」；允许用户主动换机，不设换机次数上限 |
| 管理员码 | 1 个；多设备、无限激活、互不影响；不具备任何管理接口权限 |
| 注册码格式 | Crockford Base32，20 位（100 bit 熵），显示为 `DL-XXXXX-XXXXX-XXXXX-XXXXX`；输入时忽略大小写、空格、连字符，并把 `O→0`、`I/L→1` 归一 |
| 首次激活 | 必须联网 |
| 进程启动 | 本机租约有效（签名正确、绑定本机公钥、未过期、本机时间不早于上次记录的服务器时间）时直接放行，并立即续租；否则显示授权层并在线核验 |
| 心跳 | 每 60 秒一次，请求超时 8 秒；失败后按 15 秒→30 秒→60 秒退避；续租不能把截止时间往回延长到已签发租约之前，也不能借重试延长 |
| 租约 | 15 分钟 |
| 换机 | 最后激活者立即生效；旧机下次心跳收到 `REPLACED` 后锁定 |
| 异地提示 | 只有服务端明确返回 `REPLACED` 才显示「注册码已被其他地方使用」；单纯断网到期显示「无法连接激活服务，请联网后重试」 |
| 休眠 / 恢复 | 恢复后先按单调时间和墙钟时间重新判断租约，立即续租一次；超出租约就先锁定 |

**容量估算**：100 台机器 × 每分钟 1 次 × 24 小时 = 14.4 万次/天（理论上限）；按人均每天在线 6 小时估算约 3.6 万次/天。每次心跳对应 1 次 Worker 请求 + 1 次 Durable Object 请求。**免费账号的每日 10 万次额度由 relay 和授权服务共用，不能用于生产。**开通 Workers Paid（每月 5 美元起，含 1,000 万次请求）后，本服务的用量远低于包含额度；实施时按 Cloudflare 当前价格页核对。

### 已确认的决策（用户 2026-10-06 确认，按本单推荐方案执行）

- [x] **码数量**：首批 100 = 普通 99 + 管理员 1，不生成 101 个；之后通过管理页按需增加，不设上限。
- [x] **换机规则**：最后激活者立即生效；旧机在线时 ≤60 秒锁定，离线时最迟租约到期（≤15 分钟）锁定。附录 A 的严格交接不实施。
- [x] **服务部署**：授权服务使用 Cloudflare Workers Paid，或与 relay 分开的独立账号，不与 relay 共用免费额度。
- [x] **老用户升级顺序**：先向现有用户发码，再发布带门禁的客户端版本；不用「存在旧配置目录」识别免费用户。

- [x] **域名**：`license.yinxiaobia.net`（与 relay 同一个主域名，绑定到新建的独立 Worker `deep-legends-license`）。
- [x] **不需要服务器，需要管理页（用户 2026-10-06 追加）**：授权服务和管理页都跑在 Cloudflare Workers + Durable Objects + D1 上，用户只需要已有的域名。**`deep-legends-manage` 作为独立新项目承载服务端与管理页，不放在本仓库**，分工见 P1 第 0 条；管理页放在 `manage.yinxiaobia.net`，见 P1 第 3、9 条。
- [x] **签名私钥保管（用户本人保管，GPT 不接触）**：
  1. Ed25519 密钥对在用户自己的电脑上用脚本生成一次，私钥由用户本人通过 `wrangler secret put` 写入生产 Worker 的 Secret；GPT 开发和测试只使用测试密钥对，**不得看到、记录或提交生产私钥**。
  2. Cloudflare Secret 写入后无法再读出，所以生成后立即把私钥存进用户的密码管理器，并另存一份离线备份（如加密 U 盘）；不进 Git、聊天记录、工单、安装包或日志。
  3. Cloudflare 账号开启两步验证；管理接口令牌同样由用户本人保管。
  4. 公钥写进客户端，客户端同时认两个 `kid`。私钥泄漏或丢失时：生成新密钥、发布新客户端（同时信任新旧 `kid`）、再停用旧 `kid`。
  5. 注册码原文交付文件同样由用户本人保管，发给用户时按码逐个发，不群发整份。

## P1　授权服务（Cloudflare Worker + Durable Object）

0. **工程归属（用户 2026-10-06 确认：`deep-legends-manage` 做成独立项目）**：
   - **本仓库（deep-legends）只做客户端**：Go 授权管理器、路由门禁、授权遮罩、设备密钥、完整性校验（P2–P6 客户端部分），以及一份协议合同文档 `docs/license-protocol.md`（接口、字段、签名规则、错误码）——**该文档由 `deep-legends-manage` 先产出并定稿，本仓库只在客户端阶段同步一份，不在本仓库先行起草**。**实施顺序：先只做 `deep-legends-manage`（服务端与管理页），期间不改动本仓库；服务端测试环境就绪后再开始本仓库的客户端部分。****本仓库不放授权服务代码、码表、管理页、私钥或任何真实注册码。**客户端从头到尾只看到用户自己输入的那一个码，列表和使用状态不在本仓库访问范围内。
   - **独立仓库 `deep-legends-manage` 负责服务端与管理页**：授权 Worker（`/v1/*`）、Durable Object、D1 表结构、管理页与管理接口（`/admin/*`）、密钥生成与部署脚本、服务端测试与执行账本。注册码的增删改查、使用状态、事件记录都在这个项目里。
   - **两个项目靠协议合同衔接**：合同以 `deep-legends-manage` 为准，本仓库文档同步一份；改协议时两边同时改并升级协议版本号。客户端内置的只有授权服务地址和验签公钥列表。
   - **域名分开**：客户端接口用 `license.yinxiaobia.net`；管理页用单独的主机名 `manage.yinxiaobia.net`，只由 Cloudflare Access 放行用户本人，公开的客户端接口与管理入口互不暴露。两个主机名由同一个 Worker 项目部署，共用同一个 D1 和 Durable Object。
   - **联调**：`deep-legends-manage` 提供一个测试环境（独立的测试 Worker、测试 D1、测试密钥对），在管理页生成测试码给 GPT 做 T03–T12 双机联调；生产码、生产私钥只在生产环境，GPT 不接触。
   - **服务端实施已转入 R233**：`deep-legends-manage` 的授权服务、管理页、一致性测试与运维要求见 `WORKLIST-R233-...`（P3–P7），本节 P1 仅保留设计依据。
   - **执行拆分**：本工单的 P1（服务端）与管理页部分，实施时在 `deep-legends-manage` 项目新建对应工单与账本；本仓库工单执行 P2–P8 的客户端部分，并以服务端测试环境联调通过作为 T03–T19 的前置条件。
1. 新建独立 Worker `deep-legends-license`，代码放在 `deep-legends-manage` 项目（**不放在本仓库的 `relay/` 下**），绑定自有子域名，设置 `workers_dev=false`（国内经常无法访问 `*.workers.dev`）。不要和 `riot-worker` 合并成一个 Worker。
2. **每个 license 一个 Durable Object**（SQLite 存储），对象名为 `license_id`。同一个码的激活、续租、撤销都在同一个对象里串行执行，天然满足「原子占用」，不需要额外加锁。禁止用 KV、Cache 或进程内 Map 来裁决设备占用（它们是最终一致的）。
3. **码表放 D1 数据库，不再是固定的 100 个**：新建 D1（SQLite）作为注册码总表，字段包括 `license_id`、`code_digest`（规范化码的 SHA-256）、`kind`（standard/admin）、`status`（active/revoked）、`note`（备注，例如发给谁）、`batch`、创建/撤销时间，以及由 DO 回写的使用摘要（当前设备短 ID、最后在线时间、接管次数）。激活时用 `code_digest` 查 D1 得到 `license_id`，再进入该码的 Durable Object 做原子占用。**设备占用仍只由 DO 裁决，D1 只负责码表、列表查询和事件日志。**首批 100 个码（99 普通 + 1 管理员）通过管理页「批量生成」创建，之后可随时增加，不设上限。原码只在生成当下显示一次并可导出 CSV，服务端只存摘要，不进入仓库、构建产物、日志或工单；丢失时在管理页「重置」，换成一个新码并让旧码失效。
4. 管理员码的类别只由服务端映射决定。客户端提交的 `isAdmin`、码前缀或本地配置一律无效。
5. 签名：Ed25519 私钥作为 Worker Secret，并带上 `kid`；客户端内置公钥列表 `{kid → pubkey}`，支持新旧两个 `kid` 交替轮换。
6. 接口（建议合同）：
   - `POST /v1/activate`：`{code, device_pub, ts, counter, sig}` → 普通码：把 `current_device` 设为该设备，`revision+1`，签发租约；管理员码：把该设备加入设备集合，签发租约。
   - `POST /v1/renew`：`{license_id, device_pub, revision, ts, counter, sig}` → 设备仍是当前设备（管理员码：仍在集合内且未撤销）时签发新租约；否则返回 `REPLACED` / `REVOKED`。
   - 只用 POST，参数不放 URL；响应带 `Cache-Control: no-store`。
7. 防重放：每个设备在 DO 中记录 `last_counter`，请求的 `counter` 必须严格递增，`ts` 与服务器时间相差不超过 300 秒。同一设备重复激活视为幂等，不会把自己踢掉。
8. 限流：按 IP 和按码摘要限制激活频率（建议每个 IP 每分钟 10 次激活）；无效码统一返回「无效」，详细原因只记在服务端。限流不等于给管理员码设置使用次数上限。
9. **管理页（取代命令行，已确认需要）**：在 `deep-legends-manage` 项目内提供（部署在 `manage.yinxiaobia.net`），不新建服务器。
   - **访问保护**：用 Cloudflare Access（Zero Trust 免费版，50 个用户内免费）保护 `manage.yinxiaobia.net` 全部路径（页面与管理接口）；`license.yinxiaobia.net` 上不提供任何 `/admin` 路径，登录方式用邮箱一次性验证码，只放行用户本人的邮箱。**Worker 自己还必须校验 `Cf-Access-Jwt-Assertion`（签名、受众、过期）**，Access 配置出错时也不能裸奔；管理页不使用普通客户端接口的任何凭据。
   - **查**：注册码列表（只显示掩码）、类型、状态、备注、批次；使用状态：当前绑定的设备短 ID、最后在线时间、租约剩余、被替换次数；按状态/类型/备注/批次搜索筛选；单个码的激活与接管事件时间线（脱敏）；接管次数异常（建议 >10 次/天）的标记。
   - **增**：批量生成（输入数量、类型、批次名、备注），结果页只显示一次明文码并提供 CSV 下载；生成**管理员类型**需要二次确认并再次验证。
   - **改**：编辑备注/批次；撤销（客户端 ≤60 秒内锁定，离线 ≤15 分钟）；恢复；解除绑定（让该码下次可被任意设备激活）；重置（换新码，旧码失效）。
   - **删**：只允许删除「从未被激活」的码；已激活过的码只能撤销，保留事件记录，避免追不到来源。
   - 所有写操作记录操作人（Access 邮箱）和时间；页面不展示完整码、私钥或租约内容；管理页的 HTML/JS 随 Worker 一起部署，不引用第三方 CDN；CSRF 通过 Access 的同源会话加自定义请求头校验。
   - 命令行脚本仅保留生成密钥对、初始化 D1、部署和备份导出这类一次性运维，不再承担日常增删改查。
10. 故障处理：存储写入失败、未知码型、签名配置缺失时，一律拒绝新的放行，不回退到「本地校验通过」。

## P2　客户端租约与换机

### 租约载荷

`{license_id, kind, device_pub_hash, revision, kid, issued_at, expires_at}`，用 Ed25519 签名。客户端校验：签名正确、`kid` 在白名单内、`device_pub_hash` 等于本机公钥摘要、未过期。字段缺失或算法未知一律拒绝。

### 状态机

```text
LOCKED ──输入有效码──▶ ACTIVE
ACTIVE ──续租成功──▶ ACTIVE（截止时间更新）
ACTIVE ──续租失败──▶ ACTIVE（租约内继续，退避重试）──租约到期──▶ NETWORK_LOCKED
ACTIVE / NETWORK_LOCKED ──服务端返回 REPLACED──▶ REPLACED（不自动重试激活）
任意状态 ──服务端返回 REVOKED / 完整性失败──▶ 对应 LOCKED
NETWORK_LOCKED ──联网续租成功──▶ ACTIVE
REPLACED ──用户手动重新输码──▶ ACTIVE（接管回来）
```

### 换机流程

1. A 处于激活状态，B 提交同一个普通码：DO 把 `current_device` 改为 B，`revision+1`，立即给 B 签发租约，B 马上可用。
2. A 下一次心跳收到 `REPLACED`：Go 先关闭门禁（取消业务 context、清空待执行队列），再通知 UI 遮罩，显示「注册码已被其他地方使用」。
3. A 离线时：靠本地租约到期自行锁定；联网后续租得到 `REPLACED`，再把提示换成准确原因。
4. A 进入 `REPLACED` 后，心跳、重启、重连都**绝不**自动调用 `activate`。
5. 并发：A/B/C 同时激活时，由 DO 串行决定，最后一个生效。旧响应按 `revision` 丢弃，无法复活已被替换的会话。
6. 管理员码：B 激活不影响 A。

### 时间

- 运行中：用「收到租约时的单调时钟 + 剩余时长 − 请求耗时」计算截止时间，不依赖可回拨的墙钟。
- 启动时：本地租约用墙钟判断；同时记录最近一次服务器时间 `last_server_time`，如果本机墙钟早于它，视为时钟回拨，不放行本地租约，必须在线核验。
- 每个业务动作和数据返回前检查截止时间，不能只靠定时器准点触发锁定。

## P3　设备身份与凭据保护

1. 首次运行时生成 Ed25519 设备密钥对，私钥用 DPAPI（`CryptProtectData`，CurrentUser 作用域）加密后保存到 `%APPDATA%\Deep Legends\license\device.key`，通过 `golang.org/x/sys/windows` 调用，不引入 CGO。公钥摘要就是设备 ID。
2. 私钥不传给 renderer、不写入安装目录、不跟 portable 文件夹一起被复制。
3. 安装版和 portable 共用同一个设备密钥；升级、重装、迁移安装目录都不算新设备。卸载时如果用户选择「删除用户数据」，一并删除 `license\` 目录。
4. 系统重装、换 Windows 账户、DPAPI 解密失败时：生成新密钥，按新设备重新激活（普通码会把旧设备踢掉，符合规则）。
5. 本地租约文件 `lease.json` 和 `last_server_time` 存在同一目录下。复制到别的电脑无效，因为那台电脑的公钥不匹配。
6. TPM 不可导出密钥列为**可选后续增强**，第一期不做。
7. 不上传硬件序列号、MAC、电脑名、游戏账号、Riot Key 或游戏令牌。

## P4　Go 后端门禁与业务生命周期

1. 新增 `backend/license.go`（状态管理、心跳、租约校验）和 `backend/license_device_windows.go`（DPAPI 存取），由 Go 持有租约和设备凭据。Electron 和 renderer 只接收状态。初始状态为拒绝。
2. 路由显式分类、默认受保护。未授权时只允许访问：启动壳和静态壳资源、`/api/license/*`、脱敏诊断导出、隐私文本、更新和退出。`/api/license/status` 只返回状态枚举和提示文案，不返回召唤师、战绩、收藏等业务数据。
3. 授权成功前不启动 LCU 连接、游戏数据订阅、职业缓存预热、战绩轮询和自动化。更新检查、诊断和授权心跳独立运行。
4. 授权丢失时：统一取消业务 context，关闭业务 SSE/WS，清空待执行队列和在途回调。自动接受、选/禁英雄、领奖、符文/装备写入、游戏设置等副作用**在执行前再检查一次门禁**。
5. 锁定期间不推送业务数据，迟到的结果按授权代际丢弃；用户设置和缓存文件保留，不删除。
6. 重新激活后，按单一生命周期恢复服务，每项只启动一次；锁定期间积压的游戏写操作不补执行。
7. 直接运行 Go 后端、用浏览器打开 loopback、直接调 API 或 IPC、隐藏窗口时，都受同样的限制。发布版不提供 `--skip-license`、调试环境变量或「服务不可用就放行」的降级。测试通过依赖注入假服务完成，不把后门编译进产物。

### P4b　relay 授权（第二阶段，可与第一期分开发布）

relay 是唯一真正在服务端、且消耗开发者本人 Riot Key 的资源，值得纳入授权：

- 授权服务在租约中附带一个短期 `relay_token`（同一个 Ed25519 签名，`aud=relay`，有效期与租约相同）；relay Worker 内置同一个公钥，校验通过才转发。
- 兼容期：relay 先只记录「无令牌请求」的数量，确认新版本占比足够后再拒绝无令牌请求。是否以及何时断开旧版本由用户决定。
- 用户自带 Riot Key 直连的情况不经过 relay，但仍受 Go 门禁约束。

## P5　注册码界面与现有遮罩共存

1. 第一帧显示独立的授权层，遮住应用主体，底层只是不含业务数据的空壳。授权层不与 `startup-loading` 共用 `overlaySuppressed`、15 秒兜底或隐藏函数。
2. 沿用黑金风格、深浅主题和缩放规则。只包含：标题「激活 Deep Legends」、注册码输入框、「激活」按钮，以及处理中/错误状态。支持粘贴和 Enter 提交，提交过程中防止重复提交。没有关闭、跳过或稍后按钮；Esc、点击外部、路由切换都不能解除；正常退出窗口仍可用。
3. 统一管理主体的 `inert` 和焦点：授权锁和连接遮罩任意一个存在，都不能被另一个误移除 `inert`。授权层优先；授权有效后，原连接遮罩再按原规则出现。
4. 文案：无效码「注册码无效，请检查后重试」；被替换「注册码已被其他地方使用」；网络失败「无法连接激活服务，请联网后重试」；撤销「注册码已停用」；完整性失败「软件文件校验失败，请重新安装官方版本」。界面上不出现后台细节和说明性文字（遵守 R128 约定）。
5. 被替换时 Go 先关门禁，renderer 再遮罩并清空展示的数据；即使 renderer 崩溃，Go 也已经停用。
6. 注册码输入不进入埋点、错误上报或截图；激活成功后清空输入框，**不在本地保存明文码**。

## P6　安装包与运行时防篡改

目标：让普通的文件修改无法获得使用权限，并提高二进制破解的成本。**验收承诺不包括「无法破解」。**

### 必做（不需要证书）

1. **Electron fuses**：通过 electron-builder 的 `electronFuses` 配置（或在 `afterPack` 中调用 `@electron/fuses`）设置：`RunAsNode=false`、`EnableNodeOptionsEnvironmentVariable=false`、`EnableNodeCliInspectArguments=false`、`EnableEmbeddedAsarIntegrityValidation=true`、`OnlyLoadAppFromAsar=true`。用产物实际验证：修改 ASAR 或放一个 `resources/app` 目录后，程序必须拒绝启动。[ASAR Integrity](https://www.electronjs.org/docs/latest/tutorial/asar-integrity)、[Electron Fuses](https://www.electronjs.org/docs/latest/tutorial/fuses)
2. **后端摘要写入 ASAR**：在 `build-desktop.sh` 编完 `loot-service.exe` 之后计算其 SHA-256，生成 `desktop/backend-digest.cjs`（导出常量），这个文件随 ASAR 打包。`backendSpec` 在 spawn 之前流式计算实际文件的 SHA-256 并比对，不一致就报「软件文件校验失败，请重新安装官方版本」。信任链为：`Deep Legends.exe` 内嵌的 ASAR 摘要 → ASAR 内的 `main.cjs` 和摘要常量 → 后端 exe。**不要**用相邻的 `.sha256` 文件。对约 30 MB 的文件计算摘要，启动耗时增加约 50–100 ms，实施时实测并写入账本。
3. **Go 后端自身仍做授权检查**：即使绕过 Electron 直接运行后端，也拿不到授权。
4. **自定义安装器**：确认 `installer/` 的 payload 打包、解包和增量升级不会修改 ASAR、`Deep Legends.exe` 和后端 exe 的字节；升级后完整性校验仍能通过。
5. **更新链路**：更新清单用授权服务之外的另一把 Ed25519 key 签名，客户端内置其公钥后验签；不能只比对和清单放在一起、可被一并替换的 SHA256。
6. 生产包不包含 source map、真实码、测试管理员码、私钥或调试入口。`public`/`private` 是 Riot Key 分发模式，**不是**软件授权开关，两种包都必须带门禁。

### 可选（不阻塞上线）

7. Authenticode 代码签名（主程序、后端、安装器）。需要付费证书和受控签名环境；签名后可以减少 SmartScreen 拦截，但本身并不能强制拦截被篡改的程序。如果日后启用，顺序为：生成最终资源、摘要和 fuses → 签名 → 验证；签名之后不能再改动任何已签名文件。
8. 混淆 / garble：收益低，不建议投入。

### 残余边界（如实记录，不当作失败）

直接给 `Deep Legends.exe` 或 `loot-service.exe` 打二进制补丁、跳过校验分支、重写本地 LCU 功能的攻击者，仍然可能绕过本地授权。只有服务端资源（P4b 的 relay）能保持服务端边界。

| T04 | A 断网，B 接管 | A 在租约到期（≤15 分钟）时锁定，提示网络失败；A 联网后提示改为「已被其他地方使用」 |
| T05 | A/B/C 并发激活、重试、乱序响应 | 只有一个最终占用者；旧响应和旧心跳无法复活授权 |
| T06 | A 被踢后重启、重连、自动重试 | 保持锁定，不自动抢回；手动重新输码后可以接管回来 |
| T07 | 同机安装版与 portable 交替运行、升级 | 共用同一个设备身份，不会自己踢自己 |
| T08 | 管理员码在 A/B/C 三台机器上反复激活 | 全部可用、互不影响；普通码无法伪造成管理员类别；无法调用 `/admin` |
| T09 | 把安装目录、`%APPDATA%`、租约文件复制到另一台机器 | 在 B 上无法续租（DPAPI 无法解密，公钥也不匹配） |
| T10 | 回拨系统时间、休眠恢复、冻结进程 | 无法延长租约；恢复后先核验再返回数据 |
| T11 | 在自动接受、选禁、符文写入前，或流式响应过程中失去授权 | 拒绝新的副作用；恢复后不补执行 |
| T12 | 篡改签名、`kind`、`revision`、`expires_at`，重放旧请求 | 全部拒绝 |
| T13 | 修改 ASAR、加入 `resources/app`、替换后端 exe | 程序拒绝启动或拒绝放行；测试必须真的修改产物 |
| T14 | 二进制补丁等高级攻击 | 记录实际边界和残余风险，不写成「无法破解」 |
| T15 | 篡改更新清单或更新包、合法升级 | 非法更新不执行；合法升级后设备身份不变，**无需重新输码** |
| T16 | 授权服务不可达、Worker 额度耗尽 | 租约内继续使用；到期后锁定并提示联网；恢复后自动解锁 |
| T17 | 深浅主题、缩放、Tab/Esc/Enter、原连接遮罩 15 秒超时 | 授权层可完整使用；原遮罩消失时不会误解锁 |
| T18 | 检查仓库、产物、诊断包、Worker 日志 | 没有原码、私钥或令牌泄漏；隐私声明与实际行为一致 |
| T20 | 管理页：未登录/非本人邮箱访问 `/admin` 与 `/admin/api/*`；伪造或缺失 Access JWT | 全部拒绝；Worker 自己验 JWT；客户端接口凭据不能调用管理接口 |
| T21 | 管理页：批量生成、搜索、撤销、恢复、解除绑定、重置、删除未激活码 | 状态与 D1/DO 一致；撤销后客户端按 ≤60 秒/≤15 分钟锁定；已激活的码不能被删除；明文码只显示一次；操作留有记录 |
| T19 | 重复部署、单码轮换、管理员码泄漏演练 | 码池总量准确，已有绑定不被重置；旧管理员码轮换后无法再激活新设备，已激活设备在 ≤15 分钟内锁定 |
