## P1　构建页切换到其他玩家后，海克斯说明一直是加载骨架（海斗 / 斗魂）

### 根因（`backend/web/gameplay.js`）

- 海克斯说明只由 `ensureBuildData(match, tab)` 请求，它取的是 `matchSubject(...)`，也就是**本人**的海克斯 ID（约 4143 行）。
- 选择条点击（`bindMatchDetailControls` 里 `[data-build-player]` 的 click，约 4605 行）只写 `tab.buildPlayers` 后 `rerenderMatch`，没有给所选玩家请求说明。
- `renderBuildAugments` 对 `state.augmentDescriptions` 里没有记录的 ID 判为 `loading`，渲染骨架条。没有任何地方会再去请求，所以切到别人后说明**永远是骨架**。
- `r211.test.cjs` 的构建切换测试把 `renderBuildAugments` 换成了桩函数（`hex:${ids}`），所以没测出来。

### 修改

1. `renderBuild` 里拿到最终的 `subject`（所选玩家）后，对 `matchAugmentIDs(subject, 6)` 调 `ensureAugmentDescriptions`；或者在点击处理里对所选玩家调用，两处选一处，保证首次展开和切换都覆盖。
2. `ensureAugmentDescriptions` 每次最多补 6 个，斗魂一个人 6 个以内，不需要改上限；同一 ID 已在加载 / 已有结果时不重复请求（现有逻辑已保证）。
3. 请求完成后只重绘这一局（沿用现有 `rerenderMatch`）。

### 测试（Node）

- 用**真实的** `renderBuildAugments` 和 `ensureAugmentDescriptions`（只桩网络 `api`）：海斗局，本人海克斯 [1,2]，另一名玩家 [3,4]。点另一名玩家后发出一次 `ids=3,4` 的请求；返回后 DOM 里出现 3、4 的说明文字，没有 `.skel`。
- 再切回本人不发新请求。
- 变异：删掉新增的调用，上面第一条必须失败。

## P2　熟练度详情页：徽章盖在头像上，和总览横幅叠放顺序相反

### 现状（`backend/web/gameplay.css` 约 2051～2055 行）

- 总览横幅：头像 `.game-icon.is-summoner-mastery-icon` 是 `z-index: 2`，徽章 `.summoner-mastery-crest` 是 `z-index: 1`，徽章**在头像下面**，从头像下沿露出来（用户截图里的样子）。
- 详情页：`.mastery-details-crest` 设了 `z-index: 2`、`bottom: 0`，DOM 顺序又在头像后面，所以徽章**压在头像下巴上**。等级数字牌同样 `bottom: 0`，压住徽章底部约三分之一。

用户的要求是熟练度图标与总览横幅完全同一套，所以叠放顺序必须一致。

### 修改

1. 详情页和弹窗里的徽章 `z-index` 改为低于头像（与横幅一致：头像 2、徽章 1），徽章顶部藏在头像下沿后面。
2. 等级数字牌保持最上层，但只压住徽章最下沿（牌子高度的一半露在徽章外），不遮住中间的宝石。
3. 头像、徽章的相对位置按横幅的比例等比放大（横幅：头像 52px、徽章 42px、徽章顶距 36px；详情页头像 56px，其余按比例换算），不另调一套。

### 验收

## P3　赛后刷新：「近 N 场排位」和「英雄胜率」仍可能读到赛前缓存

### 根因（源码确认；10-04 日志里 6 局都是海斗，没有触发这条）

- `loadRecentRankedSampleQueue`（`backend/gameplay.go` 约 1745 行）先查自己的 `recentRankedSample` 缓存（**10 分钟**），没命中再用 `loadSGPMatchHistoryPage(...)`，这里没传 `NoCache`，会用 SGP 历史页缓存（5 分钟）。P8 的赛后重拉虽然带了 `expectGameId` 和 fresh 上下文，这两层缓存都没绕过。
- 后果：打完一局单双 / 灵活，赛后第一次重拉就判定 resolved，战绩列表更新了，但「近 N 场排位」卡片可能还是赛前的；而重拉已经结束，要等缓存过期后的下一次加载才会更新。
- 赛季统计的后台刷新 `startSeasonStatsRefresh`（`season_stats.go` 约 772 行）固定 `useHistoryCache=true`，赛后马上触发时也可能读到 5 分钟内的第一页缓存，新局要等下一轮才计入「英雄胜率」。

### 修改

1. 请求上下文是 fresh（`overviewFreshHistory(ctx)` 为真，即赛后重拉或手动刷新）时：
   - `loadRecentRankedSampleQueue` 跳过 `recentRankedSample` 缓存，并给 `loadSGPMatchHistoryPage` 传 `NoCache: true`；拿到结果照常写回缓存。
   - 由这次请求触发的赛季头部扫描用 `useHistoryCache=false`。
2. 普通打开总览、切筛选不受影响，仍然走缓存。

### 测试（Go）

- 构造：缓存里有赛前的 420 样本；fresh 请求 → 发出一次 q_420 上游请求，返回含新局的样本；非 fresh 请求 → 命中缓存、不发请求。
- 赛季头部扫描在 fresh 请求下 `sgp_history_cache_hits` 为 0。
