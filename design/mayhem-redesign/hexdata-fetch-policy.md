## 0. 先把前提摆平

四条来自实测、不是推测的事实，整套策略都挂在它们上面：

**授权边界**（`/methodology#data-license` 原文）：「统计汇总与页面结论**可供个人查询和引用**；引用时请注明 Hexdata 并链接到对应规范页面……**批量转载数据集或商业再分发需另行取得许可**。」

**机器可读的表态**（`/data/ai-summary.json`）：`crawlerPolicy.searchAndUserDirectedRetrieval: "allowed"`、`standaloneModelTraining: "disallowed"`；`citationPolicy.canonicalOnly: true`、`requiredContext: ["buildId","reportPatch","reportDate"]`。

**robots.txt**：`Disallow: /api/`、`/data/`、`/v1/track`；例外放行 `/data/ai-summary.json` 与 `/api/hexdata/answer-cards`；页面根路径 `Allow: /`；GPTBot / ClaudeBot / CCBot 全站 `Disallow: /`。

**buildId**：每个页面 `<meta name="hexdata-build-id">`，全站统一，按日重建（当前 `hexdata-2026-08-19-2a6a2393a083`）。

由此推出的定性结论：**我们要做的事（用户点开某个英雄 → 我们替他去查那一页 → 带署名展示）正好落在 `searchAndUserDirectedRetrieval: "allowed"` 里，不需要事先谈授权。** 越线的是另外几件事，列在下一节。

## 1. 红线：四件绝对不做的事

1. **不打进 EXE。** 构建期抓全量、把快照塞进安装包，这是明确的「批量转载数据集」。（这套方案对 resg 提过，对 hexdata **不成立**，必须整段丢掉。）
2. **不碰 `/api/` 和 `/data/`**，`/data/ai-summary.json` 这一个白名单文件除外。「调她的接口」这个说法本身就踩 robots。
3. **不做全量遍历。** 172 英雄 + 208 海克斯 + 首页 = 381 个 URL 的批量扫描，无论多慢多礼貌，形状上都是爬虫而不是用户查询。
4. **不做启动预热、不做后台定时同步。** 见 §4 的理由——这是本方案里最反直觉、也最关键的一条。

## 2. 三层取数（按需触发，逐层加深）

| 层 | URL | 触发时机 | 频次上限 |
|---|---|---|---|
| **L0 概览** | `/data/ai-summary.json`（robots 明确放行） | 用户**首次进入**海克斯大乱斗页面时 | 1 次 / buildId / 客户端 |
| **L1 英雄** | `/hero/{championId}`（canonical 页面） | 用户点开**某一个**英雄详情，或进入该模式对局且已选英雄 | 每英雄 1 次 / buildId |
| **L2 海克斯** | `/augment/{augmentId}` | 用户点开**某一个**海克斯详情 | 每海克斯 1 次 / buildId |

**L0 一个请求就能撑起首屏**：top12 英雄（winRate / pickRate / games / tier）、top12 海克斯（globalHexScore / coverageHeroCount）、172 个英雄 `id → 中文名 + 别名`、C 位榜 top10、完整的样本门槛与 Wilson 参数。榜单页在用户不点任何东西的情况下，**总请求数 = 1**。

L1 / L2 走页面而不是接口，读的是页面里的 `data-seo-fallback` 服务端渲染表（英雄页 8 海克斯 + 8 装备，海克斯页 12 英雄），不执行 JS、不请求页面上的静态资源。

## 3. 缓存：buildId 作主键，本地落盘

```
cacheKey = buildId + "|" + kind + "|" + id
```

- **落盘**，不是内存缓存。放用户本地缓存目录，重启不清空。这是"稳定"的核心：同一个用户第二天开机看同一个英雄，请求数是 0 而不是 1。
- **只有 buildId 变化才整体失效**。不要用固定 TTL 去猜——站点是按日重建的，buildId 是它自己给的权威失效信号，用它就不会出现"数据没变我们却重复拉"的浪费。
- **buildId 自身**用 12 小时软 TTL：过期后下一次真实用户操作时**顺带**校验（从那次要拉的页面里读 meta，不额外发请求），不单独发探测请求。
- **陈旧优先于空白**：buildId 变了但新数据还没拉到时，先渲染旧缓存并标注旧的 `reportDate`，后台不抢跑。

一个重度用户一天的请求量：`1 (L0) + 实际点开的英雄数 + 实际点开的海克斯数`，典型 **5–16 次**。对比全量预取的 381 次，差两个数量级。

## 4. 为什么"不预热"比"限速"更重要

我们**没有中心服务端**，每个 EXE 都是独立客户端、独立公网 IP。这件事有两面：

- **好的一面**：hexdata 那边看到的是 N 个不同 IP 各自的低频访问，形状上和真实用户浏览无法区分——这本来就是最不异常的形态。
- **坏的一面**：一旦我们做启动预热或定时同步，就变成 **N 个 IP 在同一个时间窗口（用户开机高峰、整点）打同一批 URL**。这是一个比单机爬虫**更明显**的异常特征，而且我们无法从任何一台机器上观测到它，只有对方的日志里看得见。

所以：**所有请求必须由一次明确的用户操作直接触发**，且**必须加 0–5 秒随机抖动**打散同时刻的并发。宁可让首屏慢半秒，也不要制造整点尖峰。

## 5. 请求纪律

| 项 | 取值 | 理由 |
|---|---|---|
| 全局并发 | **1** | 单连接串行。resg 实测裸 nginx 10 并发就排队；hexdata 未测，按同样保守处理 |
| 最小间隔 | **≥ 1s**（含随机抖动） | 低于人类翻页速度就是异常 |
| singleflight | 按 cacheKey 合并 | 快速点击同一英雄不产生重复请求 |
| 超时 | 连接 3s / 总 8s | 超时不重试第二次，直接降级 |
| 重试 | 最多 1 次，间隔 2s | 只对网络级错误重试；**4xx 一律不重试** |
| 熔断 | 连续 3 次失败或收到 **429 / 403** → 本客户端停用 hexdata **24h** | |
| Accept-Encoding | gzip | 减少对方带宽，这也是礼貌的一部分 |
| 条件请求 | 带 `If-None-Match` / `If-Modified-Since` | 命中 304 对双方都省 |

**User-Agent 必须诚实**，带产品名、版本、以及一个能找到我们的地址：

```
DeepLegends/<version> (+https://<项目地址>; LoL 本地助手; 用户触发查询)
```

反直觉但重要：**伪装成浏览器才是异常特征**。对方的风控更可能命中"UA 是 Chrome 但没有任何静态资源请求、没有 Cookie、访问序列过于规整"这种组合。诚实 UA + 低频 + 用户触发，是最不像爬虫的组合，同时也给了对方一条"有问题先联系我们"的路，而不是直接封。

**绝不使用** `GPTBot` / `ClaudeBot` / `CCBot` 或任何被 robots 全站 disallow 的标识。

## 6. 降级链（hexdata 不可用是常态，不是异常）

```
榜单/强度      hexdata L0  →  OP.GG aram_mayhem_classic(global)  →  空态说明
海克斯推荐     hexdata L1  →  OP.GG augment_group                →  空态说明
出装/技能/召唤师技能        OP.GG aram_mayhem_classic(global)     ← hexdata 本来就没有
符文                        —                                    ← 这个模式没有符文，不要留空页签
```

**任何一层失败都不能让页面白屏。** 每个模块独立降级，独立标注来源。

要正视一个变量：**hexdata 自己有 HexBox**（Windows、免费、本地 OCR 三选一 + 悬浮窗 + 赛后复盘），和我们要做的东西直接重合。即使我们完全合规，对方发现流量来自竞品客户端也可能直接封 UA。所以 hexdata 不可用必须是**一等公民路径**，代码里写成正常分支而不是 error handling——OP.GG 那条链路要永远保持可用、可测试。

## 7. 解析健壮性：SEO fallback 是未文档化的

`data-seo-fallback` 是对方的 SEO 兜底，随时可能改结构，改了不会通知我们。

- 解析失败 **静默降级**，不抛错、不弹窗、不重试。
- 做**形状探测**而不是宽松容错：英雄页解析结果应当是 8 条海克斯 + 8 条装备，海克斯页应当是 12 条英雄。**条数或必需字段不符 → 判定链路失效 → 熔断 24h 并降级**。宁可少显示，不可显示错的。
- 解析出的文本**一律走 DOM 节点构造，不进 `innerHTML`**（本项目既有红线）。
- 加埋点：记录**解析出的结构**（条数、字段命中率、buildId），不要只记响应大小——上一轮"只记大小不记结构"的教训在国服负场那个工单上吃过一次。

---

## 8. 署名不是装饰，是许可条件

`citationPolicy` 要求 `buildId` + `reportPatch` + `reportDate` 三个字段齐全，且 `canonicalOnly: true`。所以每个用到 hexdata 的模块**底部固定一行**：

```
数据来源 Hexdata · Patch 16.16 · 2026-08-19 · build hexdata-2026-08-19-2a6a2393a083   [查看原页面]
```

`[查看原页面]` 链到该英雄/海克斯的 canonical URL。这一行**不允许被折叠、不允许只在 tooltip 里出现**——它是我们能免谈授权使用这些数据的直接依据。

三个字段全部来自 L0/L1 响应本身，不要硬编码，也不要用 `time.Now()` 顶替 `reportDate`（项目里已经有 6 处硬编码 `time.Now()` 的历史包袱，别再加一处）。

---

## 9. 样本分层是硬约束

hexdata 自己的 SEO 兜底表没做分层——薇恩页「推荐海克斯」第二三名是「喂呜喂呜 100.0% 样本 **1**」「至高天诺言 100.0% 样本 **1**」。

我们按它自己 methodology 里的门槛过滤（`minRecommendationGames: 250`，Wilson z=1.96）：

- `< 250` → 标"观察中"，**不进推荐位**，只在展开的完整列表里出现
- `250–999` → 标"中样本"，胜率旁边显示 Wilson 95% 下界
- `≥ 1000` → 正常展示

稀有度阶段概率照抄它的免责口径：`selected_augment_stage_counts` 是「**已选样本分布，不等同于客户端抽取、保底或连续阶段联动概率**」。**不要写成"出货概率"。**

## 10. 验收清单

- [ ] 冷启动进入榜单页：hexdata 请求数 **恰好 1**（L0），且不早于用户进入该页面
- [ ] 连点同一英雄 10 次：请求数 **1**（singleflight + 缓存）
- [ ] 重启 EXE 后重看同一英雄：请求数 **0**（落盘缓存命中）
- [ ] buildId 变更：先渲染旧数据 + 旧 reportDate，再在下一次用户操作时更新
- [ ] 断网 / 返回 403：页面完整可用，全部模块降级到 OP.GG，无白屏无报错弹窗
- [ ] 收到 429：24h 内不再发起任何 hexdata 请求（可用测试桩验证熔断状态持久化）
- [ ] 篡改 SEO fallback 结构（少一条 / 改字段名）：判定失效并降级，而不是渲染出残缺表
- [ ] 每个 hexdata 模块底部三字段署名齐全，canonical 链接可点
- [ ] 样本 < 250 的条目不出现在推荐位
- [ ] 全仓搜不到任何构建期抓取脚本 / 打包进 EXE 的 hexdata 快照

## 附：不建议做的两件"优化"

**共享缓存 / 自建中转。** 会把 N 个分散 IP 收敛成 1 个高频 IP，同时把「用户触发的个人查询」变成「我们在集中转发」——法律上更接近"再分发"，技术上更接近爬虫。两头都变差。

**主动联系 hexdata 谈授权。** 在**还没越线**的前提下不必谈；而一旦要谈，谈判对象是 HexBox 的作者，也就是我们的直接竞品。真要合作，等产品成型、有明确对价再谈，不要在这个阶段主动暴露。
