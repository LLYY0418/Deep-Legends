## 根因（双重实证，两份日志互相印证）

### 1. 收藏库存一致性校验的机制（`catalog.go:843` `loadOwnedSkinInventory`）

四个数据源：

| 源 | 角色 |
|---|---|
| `/lol-champions/v1/inventories/{id}/skins-minimal` | 权威源 A |
| `/lol-champions/v1/inventories/{id}/champions` | 权威源 B |
| `/lol-inventory/v2/inventory/CHAMPION_SKIN` | 佐证源（presence） |
| `/lol-inventory/v1/inventory?inventoryTypes=CHAMPION_SKIN` | 佐证源（presence） |

逻辑：两个权威源如果不一致，必须有一个佐证源与其中一个**精确相等**才能定案，
否则直接判定 `"authoritative ownership sources disagree without a corroborating source"`
——**这是一个硬失败，不会重试出结果，只会一直重复同一个结论**。

### 2. 实测：购买皮肤前后的真实数值（两份日志各贡献一半证据）

**购买前**（`diagnostics-0d59fad4.jsonl`，01:19~01:20，当时 `refresh_succeeded`）：

```
skins-minimal=1138   champions=1140   v2-presence=1138   v1-presence=failed
```

权威源 A/B 本来就固定相差 2（这是**长期存在的结构性偏差**，不是购买触发的——
大概率是有 2 个皮肤 ID 只出现在 `champions` 端点、不出现在 `skins-minimal`，
具体是哪 2 个 ID 目前日志里没有埋点记录，无法确认）。当时能成功，
是因为 **v2-presence（1138）与 skins-minimal（1138）精确相等**，
靠这个佐证赢得了"支持票"，champions 端点只是被标 `warning` 不算失败。

**购买后**（`diagnostics.1-4aa5e2ef.jsonl`，02:13~02:18，`refresh_failed` × 62）：

```
skins-minimal=1139→1140   champions=1141→1142   v2-presence=1138（纹丝不动）   v1-presence=failed
```

`skins-minimal` 和 `champions` 都因为新皮肤各自 +1（相差还是 2，符合前面的结构性偏差），
但 **v2-presence 端点的缓存没有跟着刷新，卡在购买前的 1138**——
于是它既不等于 1139/1140，也不等于 1141/1142，**佐证票直接消失**，
两个权威源从"有仲裁"变成"平局无解"，硬失败。

`/lol-inventory/v1/...` 这个端点**从购买前到购买后、连续 64 次请求全部 `"request failed"`**，
在这个客户端版本里等同于报废，从来没有真正参与过仲裁——这不是本次新问题，
但目前代码仍然把它算作"四选二"里的一票，是个死权重。

### 3. 为什么会"一直读取中不停止"

`connection_manager.go:18` `snapshotRetryInterval = 5 * time.Second`，
`:149/236-243` 的 ticker **固定 5 秒重试一次，没有退避、没有上限、没有超时放弃**，
只要 `snapshotReady` 一直是 false 就永远重试。而上面这个"佐证票消失"的状态
**不是几秒钟能自愈的**——v2 端点缓存要等到什么时候刷新未知（可能是重开收藏页、
可能是客户端下次心跳，日志里 5 分钟、62 次都没等到它变化）。

于是：**结构性错误（4 个数据源永远凑不齐仲裁）× 无上限重试 = 用户看到的"一直转圈"**。
即使前端 `web/app.js:232-238` 有个 25 秒自动隐藏遮罩的兜底
（`startupFallbackTimer`），隐藏的只是弹窗本身，收藏页列表依然进不去、
显示"收藏信息还在准备中"的空态——对用户来说观感上还是"卡住了"。

## 改法

### A. 放宽仲裁规则，不要求佐证源精确相等（价值最高，改动可控）

`catalog.go:930-975` 的仲裁逻辑目前要求 presence 源的 ID 集合与权威源
**完全相等**（`equalIDSets`）。改成**容忍佐证源是权威源的子集**（缺几个新买的），
只要佐证源没有多出权威源没有的 ID（即 `extra==0`），
就可以判定"佐证源只是缓存滞后，仍然支持这个权威源"，而不是直接判平局。

```go
// corroboratingPresenceSuperset 已经实现了"佐证源包含权威源"的方向
// 现在缺的是反方向：佐证源是权威源的真子集（滞后）时的容忍判断
```

护栏：构造 fixture——权威源 A=1140（含新皮肤）、权威源 B=1142（结构性 +2）、
presence=1138（滞后，是 A 的真子集，extra=0）——断言仍能定案用 A，
且新皮肤 ID 不会被误判为"未拥有"（这点必须谨慎：**滞后的佐证源不能反过来
让新买的皮肤消失**，只能用来支持权威源，不能用来削减权威源的结果）。

### B. 重试策略加上限 + 失败态可见（不管 A 做不做都要做）

1. `snapshotRetryInterval` 改成指数退避（5s → 10s → 20s → 上限 60s），
   而不是死等 5 秒。
2. 加一个失败预算（比如连续失败 10 次 / 累计 2 分钟），到了之后：
   - 不再是"一直转圈"，改成明确文案：
     "收藏库存与客户端缓存暂时不一致（常见于刚购买皮肤后），
     已重试 N 次，将每 60 秒继续尝试；你也可以手动刷新。"
   - 如果本地有上一次成功的快照（`storage.saveSnapshot` 已经在存），
     优先展示"可能不是最新"的旧数据，而不是空白。
3. 前端遮罩加上重试次数/已用时长，不要只说"失败时会自动重试"这种无信息量的话。

### C. 诊断埋点补 ID 级别细节（不修问题，但下次能真正定位那 2 个结构性差异）

`markOwnershipSource` 目前只记 `missing`/`extra` 的**数量**，不记具体 ID
（[[deep-legends-ranked-winrate-lp]] 里吃过同样的亏："埋点要记结构不只记大小"）。
补上具体 ID 列表（脱敏后，不含 PUUID），才能查清楚"权威源永远相差 2"
这个结构性偏差到底是哪两个皮肤、是不是某类特殊皮肤（限定/彩蛋/客户端调试项）。

### D. `/lol-inventory/v1/...` 端点长期失败，建议直接降级

连续 64 次请求 100% 失败，大概率是这个客户端/游戏版本已经不支持这个端点。
建议：失败达到一定次数后不再计入仲裁候选（既减少无效请求，也让
"四选二"变成更真实的"三选二"，减少无谓的平局概率）。

---

## 执行顺序建议

1. **A**（放宽仲裁容忍度）—— 直接解决本次触发场景，价值最高
2. **B**（重试上限 + 失败态文案 + 用旧快照兜底）—— 即使 A 没覆盖到的其它冲突场景，也不会再无限转圈
3. **C**（ID 级埋点）—— 为下次同类问题做准备
4. **D**（v1 端点降级）—— 顺手清理
